# 5.2 Designing REST APIs

When a weather app shows tomorrow's forecast, it didn't compute it: it asked a weather service's server, in a format both sides agreed on. When a shop takes your card, its backend asks a payment provider the same way. Programs talk to programs constantly, and each conversation follows an agreement called an **API** (Application Programming Interface). Once other people build on an API, it's very hard to change, so designing it well matters more than almost any code behind it. This chapter teaches the conventions that make an HTTP API a pleasure — or a misery — to use, on a small to-do list API, and then applies them to the link shortener you're building.

## What you'll learn

- What an **API** is — a contract — and why changing one is so expensive.
- The **REST** style: **resources** named by URLs, **methods** as verbs, **status codes** as outcomes.
- How to shape **JSON** requests and responses consistently, including errors.
- **Pagination**, **filtering**, and **idempotency** — what happens when a request is retried.
- A checklist for reviewing any API design — then a real API designed with it, driven with curl.

---

## An API is a contract

An **API** is the set of requests a program accepts and the responses it promises to give back. For a web API: which URLs exist, which methods they accept, what the request bodies look like, and what comes back — including when things fail.

```mermaid
flowchart LR
    A["Mobile app"] --> API["the API<br/>(the contract)"]
    B["Browser extension"] --> API
    C["Another company's backend"] --> API
    API --> S["the service's code<br/>(free to change inside)"]
```

The API is a **promise**. The service's internals — code, database, cache — can change completely, and nobody notices, as long as the API behaves the same. But change the API itself — rename a field, change a status code, remove a URL — and every program built on it can break, often in places you don't control and can't see.

:::note[Everyday anchor]
An API is a restaurant menu. Customers order from the menu; they never walk into the kitchen. The kitchen can change its ovens, suppliers and staff as long as the dishes on the menu arrive as described. But quietly change what "the Tuesday special" means, or remove a dish, and regular customers get something they didn't order.
:::

## REST: resources, methods, status codes

Most web APIs follow a style called **REST** (Representational State Transfer). Stripped of theory, it's three habits that fit how HTTP already works ([chapter 1.5](../foundations/http-from-zero.mdx)):

1. **URLs name things (resources), not actions.** Nouns, not verbs.
2. **HTTP methods say what you want to do** with those things.
3. **Status codes say what happened.**

### 1. Resources and URLs

A **resource** is a thing your API deals with. A to-do app's main resource is a **task**. Resources come in **collections** (all tasks) and **items** (one task):

| URL | Means |
|---|---|
| `/tasks` | the collection of your tasks |
| `/tasks/42` | one task, the one with ID `42` |

Compare with action-style URLs people invent when they don't use REST: `/createTask`, `/getTaskInfo?id=42`, `/deleteTask`. Every new action needs a new URL, and there's no pattern to guess. REST's nouns-plus-methods keeps the menu small and predictable.

### 2. Methods as verbs

| Method + URL | Action | Success |
|---|---|---|
| `POST /tasks` | create a task | `201 Created` |
| `GET /tasks` | list your tasks | `200 OK` |
| `GET /tasks/{id}` | get one task | `200 OK` |
| `PATCH /tasks/{id}` | change part of a task (mark it done) | `200 OK` |
| `PUT /tasks/{id}` | replace a task completely | `200 OK` |
| `DELETE /tasks/{id}` | delete a task | `204 No Content` |

The same few methods work on every resource you'll ever add — `/projects`, `/users`, `/comments` — so a developer who learns one part of your API can guess the rest.

### 3. Status codes as outcomes

Use the code that matches reality ([chapter 1.5](../foundations/http-from-zero.mdx)), so clients, proxies, monitoring and retry logic all behave correctly:

| Situation | Status |
|---|---|
| Task created | `201 Created`, plus a `Location` header pointing at the new task |
| Task deleted | `204 No Content` (success, nothing to send back) |
| Body isn't valid JSON, or the title is empty | `400 Bad Request` |
| No or invalid credentials | `401 Unauthorized` |
| Task doesn't exist — *or belongs to someone else* | `404 Not Found` |
| The request clashes with current state (a name already taken) | `409 Conflict` |
| Too many requests too fast | `429 Too Many Requests`, plus `Retry-After` |
| Something broke on the server's side | `500 Internal Server Error` |

Notice the choice for someone else's task: **404, not 403**. Answering "403 Forbidden" would confirm that task 42 *exists* — leaking information to anyone probing IDs one by one. "404" says nothing ([chapter 7.4](../security/authorization-multi-tenancy.mdx)).

## Shaping the JSON

Requests and responses use **JSON** ([chapter 1.3](../foundations/bits-bytes-text-formats.mdx)), with `Content-Type: application/json`.

**Create a task:**

```http
POST /tasks
Authorization: Bearer $API_KEY
Content-Type: application/json

{"title": "buy milk"}
```

```http
HTTP/1.1 201 Created
Location: /tasks/42
Content-Type: application/json

{"id": 42, "title": "buy milk", "done": false, "created_at": "2026-10-29T09:15:02Z"}
```

**List tasks:**

```json
{
  "tasks": [
    {"id": 42, "title": "buy milk", "done": false, "created_at": "2026-10-29T09:15:02Z"},
    {"id": 41, "title": "call the bank", "done": true, "created_at": "2026-10-28T17:40:11Z"}
  ]
}
```

**Any error:**

```json
{"error": {"code": "invalid_title", "message": "title must be 1-200 characters"}}
```

The conventions behind those shapes:

- **One naming style everywhere.** `snake_case` (`created_at`) or `camelCase` (`createdAt`) — pick one. Mixing `createdAt` and `due_date` in one API is a small, permanent annoyance for every client.
- **Timestamps in ISO 8601, UTC** ([chapter 1.3](../foundations/bits-bytes-text-formats.mdx)): `2026-09-24T19:56:18Z`. Never `"24/09/26"`.
- **Return the created resource.** The client usually needs what the server generated (the `id`, `created_at`) — don't make it do a second request.
- **Wrap lists in an object** (`{"tasks": […]}`), not a bare array. Later you can add `"next_cursor"` or `"total"` alongside without breaking anyone.
- **One error shape for every error**, with a stable machine-readable `code` (programs switch on it) and a human `message` (people read it). [Chapter 5.3](./validation-errors-status-codes.mdx) builds this.
- **Don't expose internals.** No owner numbers, password hashes or stack traces in responses. In Go, a `json:"-"` struct tag keeps a field out of JSON entirely ([chapter 4.2](../go/types-structs-errors.mdx)).

## Pagination and filtering

`GET /tasks` can't return a million tasks in one response. **Pagination** returns them in pages:

- **Limit/offset**: `?limit=20&offset=40` — "20 items, skipping the first 40". Simple, but slow for deep pages (the database still walks past the skipped rows, [chapter 6.4](../data/indexes-and-performance.mdx)) and items shift if new ones arrive while you page.
- **Cursor**: `?limit=20&cursor=eyJjcmVhdGVkX2F0Ijo…` — the server returns an opaque `next_cursor` meaning "continue after the last item you saw". Fast and stable, so most large APIs use it.

**Filtering and sorting** use query parameters too: `GET /tasks?done=false&sort=-created_at`. Keep names consistent across endpoints.

## Idempotency: what happens when a request is retried?

Networks fail ([chapter 1.4](../foundations/networks-from-zero.mdx)). A client sends `POST /tasks`, the connection drops, and it never sees the response. **Did the task get created?** The client can't know. If it retries, it might create a duplicate.

An operation is **idempotent** if doing it twice has the same effect as doing it once:

| Method | Idempotent? | Why |
|---|---|---|
| `GET` | ✅ yes | Reading doesn't change anything (it's also **safe**) |
| `PUT` | ✅ yes | "Set this to X" twice leaves it as X |
| `DELETE` | ✅ yes | Deleting something already deleted leaves it deleted |
| `POST` | ❌ no | "Create a new one" twice creates two |
| `PATCH` | it depends | "set title to X" is; "add 1 to count" isn't |

This matters enormously for retries ([chapter 8.4](../distributed/rate-limiting-and-resilience.mdx)): clients and proxies may safely retry idempotent requests; retrying a `POST` blindly can double-charge a card or send an email twice.

The standard fix for important `POST`s is an **idempotency key**: the client generates a unique ID and sends it in a header (`Idempotency-Key: 7f3a…`). The server remembers the key with the result; a retry with the same key gets the original response instead of a second action. Payment APIs such as Stripe work this way.

:::info[In the real world]
Other API styles exist. **GraphQL** (one endpoint; the client asks for exactly the fields it wants) is popular with frontends that need flexible data. **gRPC** ([chapter 5.5](./api-contracts.mdx)) is common between backend services for speed and strict contracts. REST over JSON remains the default for public APIs because every language and tool speaks it — curl included.
:::

## An API design checklist

Before shipping any new endpoint, check:

- [ ] **Nouns in URLs**, methods for verbs; plural collections (`/tasks`), items by ID (`/tasks/{id}`).
- [ ] **Correct status codes**, including every error case.
- [ ] **Consistent naming** (one case style) and **ISO 8601 UTC** timestamps.
- [ ] **One error format**, with stable machine-readable codes.
- [ ] **Validation** of every input, with clear messages ([chapter 5.3](./validation-errors-status-codes.mdx)).
- [ ] **Authentication** and **authorization** on everything that isn't public ([Part 7](../security/security-literacy.mdx)).
- [ ] **Pagination** for anything that can grow.
- [ ] **Idempotency** considered for anything that creates or charges.
- [ ] **No internal details** leaked (IDs, stack traces, other users' existence).
- [ ] **Documented** — ideally as an OpenAPI description ([chapter 5.5](./api-contracts.mdx)).

:::warning[What can go wrong]
- **Verbs in URLs** (`/getLink`, `/deleteLink?id=`): the API grows into an unguessable pile of special cases.
- **`200 OK` with an error inside.** Monitoring, caches and clients all think it worked. Use real status codes.
- **Breaking changes without warning.** Renaming `created_at` to `createdAt` "for consistency" breaks every client in production. Additive changes (new optional fields) are safe; removals and renames need versioning ([chapter 5.5](./api-contracts.mdx)).
- **Leaking existence.** Different errors for "doesn't exist" and "not yours" let attackers enumerate your data.
- **Unbounded lists.** An endpoint that returns *everything* is fine on day one and an outage on day 400.
:::

## Apply it to snip: designing a link shortener's API

**snip**, the link shortener you build in this handbook, started in [chapter 5.1](./first-http-server.mdx) as v0, which spoke plain text. Here is its real API, designed with this chapter's rules. Its resource is a **link**, named by its **slug** (the short code):

| Method + URL | Action | Success |
|---|---|---|
| `POST /api/links` | create a link (optionally with a custom slug) | `201 Created` + `Location` |
| `GET /api/links` | list your links, newest first (`?limit=`, up to 100, default 20) | `200 OK` |
| `GET /api/links/{slug}` | one link, with its click count | `200 OK` |
| `DELETE /api/links/{slug}` | delete a link | `204 No Content` |
| `GET /{slug}` | **follow** a link | `302 Found` + `Location` |

The redirect lives at the root on purpose: short links should be short. It's part of the product, not the management API, so it needs no key.

The error statuses follow the generic table: `400` for invalid JSON, URLs or slugs; `401` without a valid API key; `404` for a slug that doesn't exist **or belongs to someone else**; `409` when a custom slug is taken; `429` when one key creates links too fast; `500` for anything on snip's side. And every error has one shape — `{"error": {"code": "slug_taken", "message": "that slug is already in use"}}` — so a client needs one piece of code to handle all of them.

Creating a link looks like this:

```http
POST /api/links
Authorization: Bearer $API_KEY
Content-Type: application/json

{"url": "https://go.dev/doc/", "slug": "godoc"}
```

```http
HTTP/1.1 201 Created
Location: /api/links/godoc
Content-Type: application/json

{"slug": "godoc", "url": "https://go.dev/doc/", "clicks": 0, "created_at": "2026-09-24T19:56:18.903Z", "short_url": "https://snip.example/godoc"}
```

- `snake_case` throughout (`created_at`, `short_url`), timestamps in UTC.
- The response includes `short_url`, the thing the client actually wanted, so there's no second request.
- The owner's internal ID never appears: snip's `Link` type hides it with `json:"-"`.
- Custom slugs give snip a natural form of idempotency: retrying a `POST` with the same `slug` returns `409 Conflict` rather than creating a duplicate. Random slugs don't have that protection — an `Idempotency-Key` header would be the next step.

The handlers live in `snip/internal/httpapi/server.go`; [chapter 5.3](./validation-errors-status-codes.mdx) walks through how they validate input and produce those errors.

## Lab

Free, on your own computer.

1. **Drive a small API.** The handbook's to-do API, `snip/examples/tasks`, follows this chapter's conventions:
   ```bash
   cd ~/code/zero-to-prod/snip
   go run ./examples/tasks                     # listens on :8081
   ```
   In a second terminal:
   ```bash
   curl -si -X POST localhost:8081/tasks -d '{"title":"buy milk"}'   # 201, Location: /tasks/1
   curl -s localhost:8081/tasks/1 | jq .                              # the task
   curl -s "localhost:8081/tasks?limit=5" | jq .                      # a list, wrapped in {"tasks": …}
   curl -si -X DELETE localhost:8081/tasks/1 | head -1                # 405: no DELETE route (yet)
   ```
   Notice the `Location` header on create, and the object around the list. Stop it with <kbd>Ctrl</kbd>+<kbd>C</kbd>.

2. **Apply it: start the reference snip** (in-memory) and copy its development key from the log line containing `api_key=`:
   ```bash
   cd ~/code/zero-to-prod/snip
   SNIP_LOG_FORMAT=text go run ./cmd/snip
   ```
   In a second terminal, save the key in a variable:
   ```bash
   KEY=snip_paste_your_key_here
   ```

3. **Create, read, list, delete.**
   ```bash
   curl -si -X POST localhost:8080/api/links -H "Authorization: Bearer $KEY" \
     -d '{"url":"https://go.dev/doc/","slug":"godoc"}'                 # 201 + Location header
   curl -s -X POST localhost:8080/api/links -H "Authorization: Bearer $KEY" \
     -d '{"url":"https://example.com"}' | jq .                         # a random slug
   curl -s -o /dev/null -w "%{http_code} → %{redirect_url}\n" localhost:8080/godoc   # follow it
   curl -s localhost:8080/api/links/godoc -H "Authorization: Bearer $KEY" | jq .clicks   # 1
   curl -s "localhost:8080/api/links?limit=10" -H "Authorization: Bearer $KEY" | jq '.links[].slug'
   curl -si -X DELETE localhost:8080/api/links/godoc -H "Authorization: Bearer $KEY" | head -1   # 204
   ```

4. **Walk the error table.** For each, predict the status code *before* running it:
   ```bash
   curl -s -X POST localhost:8080/api/links -d '{"url":"https://go.dev"}' | jq .       # no key
   curl -s -X POST localhost:8080/api/links -H "Authorization: Bearer $KEY" -d '{"url":"go.dev"}' | jq .
   curl -s -X POST localhost:8080/api/links -H "Authorization: Bearer $KEY" -d '{"url":"https://a.example","slug":"dup"}' >/dev/null
   curl -si -X POST localhost:8080/api/links -H "Authorization: Bearer $KEY" -d '{"url":"https://b.example","slug":"dup"}' | head -1
   curl -si localhost:8080/api/links/nope -H "Authorization: Bearer $KEY" | head -1
   ```
   Notice every error body has the same shape — `{"error": {"code": …, "message": …}}` — so a client needs one piece of code to handle all of them.

5. **Design exercise (no code).** snip wants a new feature: link **expiry** ("this link stops working after 7 days"). Write down: which URL and method would set it? What does the JSON look like (name, format)? What status does following an expired link return — `404` or `410 Gone`? Is your change backward-compatible for existing clients? Compare your answers with the checklist above.

<details>
<summary>Why is changing an existing API so much harder than changing the code behind it?</summary>

Because the API is a **promise to people you don't control**. Once apps, scripts and other companies' backends depend on `short_url` being a field, or on `409` meaning "slug taken", changing it breaks their software — often in production, often without them noticing until users complain. You can refactor snip's internals any day because nothing outside depends on them. Additive changes (new optional fields, new endpoints) are safe; renames, removals and changed meanings need a versioning plan and a deprecation period ([chapter 5.5](./api-contracts.mdx)).

</details>

<details>
<summary>Explain idempotency with an everyday example, and say which HTTP methods are idempotent.</summary>

Pressing a lift's call button is **idempotent**: pressing it five times has the same effect as once — one lift comes. Paying for coffee is **not**: tapping your card five times buys five coffees. `GET`, `PUT` and `DELETE` are idempotent (repeat them safely); `POST` is not (repeating can create or charge twice); `PATCH` depends on what it does. That's why retries — by clients, proxies or your own code — must be careful with `POST`, and why payment APIs use idempotency keys.

</details>
