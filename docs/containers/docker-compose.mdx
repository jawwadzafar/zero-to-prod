# 9.3 Docker Compose: the whole stack locally

snip is no longer one program. It's Postgres, Redis, two copies of the API, a worker, and nginx in front, plus Prometheus and Grafana when you want to watch it. Starting all of that with `docker run` means a page of commands: create a network, start each piece with the right name, environment, volume and ports, in the right order, and remember to tear it all down afterwards. **Docker Compose** replaces that page with one file that *describes* the whole system, and one command that makes it so. You've used it since chapter 8.3. This chapter explains every line of snip's `docker-compose.yml`, the networking that lets the pieces find each other, and the day-to-day commands, including the ones that delete your data.

## What you'll learn

- What Compose is for (and not for), and the shape of a **compose file**.
- **Services**, `image` vs `build`, **environment**, **ports**, and overriding the **entrypoint**.
- **Networking**: how containers find each other by **service name**, and why `localhost` is the classic mistake.
- **Volumes**: named volumes vs bind mounts, and the difference between `down` and `down -v`.
- **Startup order**: `depends_on`, **healthchecks**, and why apps must still retry.
- **Replicas, profiles and override files**, and the everyday command set.

## From a page of commands to one file

Here's roughly what it takes to start just Postgres and one snip by hand:

```bash
docker network create snipnet
docker volume create pgdata
docker run -d --name postgres --network snipnet -v pgdata:/var/lib/postgresql/data \
  -e POSTGRES_USER=snip -e POSTGRES_PASSWORD=snip -e POSTGRES_DB=snip postgres:16-alpine
docker build -t snip:dev .
docker run -d --name api --network snipnet -p 8080:8080 \
  -e SNIP_DATABASE_URL="postgres://snip:snip@postgres:5432/snip?sslmode=disable" snip:dev
```

Now add Redis, a second API copy, the worker and nginx, and remember it all next week. Compose turns this **imperative** list ("do this, then this") into a **declarative** description ("this is what should exist"). You describe the end state; `docker compose up` works out what to create, in what order, and on a later run what to *change*.

:::note[Everyday anchor]
Running containers by hand is phoning each musician before a concert: "you bring the cello, sit there, start after the violins". A compose file is the **score**: every part, who plays what, and in what order, written down once. Anyone can pick it up and get the same concert, and changing one line changes just that part.
:::

## snip's compose file, part by part

The whole file is `snip/docker-compose.yml`. We'll take it in pieces.

### Name and the database

```yaml
name: snip

services:
  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: snip
      POSTGRES_PASSWORD: snip          # local development only — never a real password
      POSTGRES_DB: snip
    volumes:
      - pgdata:/var/lib/postgresql/data  # keeps data across restarts
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U snip"]
      interval: 3s
      retries: 20
```

- **`name: snip`** is the **project name**. Compose prefixes everything it creates with it: containers `snip-postgres-1`, network `snip_default`, volume `snip_pgdata`. Two projects never collide.
- **`services:`** lists the containers to run. Each key (`postgres`) is a **service name**, which also becomes its **hostname** on the network (below).
- **`image:`** uses a ready-made image from a registry.
- **`environment:`** sets variables inside the container. The official Postgres image reads these on first start to create the user and database.
- **`volumes:`** mounts the named volume `pgdata` where Postgres keeps its files, so the data outlives the container (chapter 9.1).
- **`healthcheck:`** is a command Compose runs inside the container every 3 seconds. `pg_isready` succeeds once Postgres accepts connections, and then the container's status becomes `healthy`.

### Redis

```yaml
  redis:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 3s
      retries: 20
```

No volume: snip uses Redis as a cache and a queue, and losing it on `down` is acceptable in development. (Chapter 8.2 discussed what a lost queue means in production.)

### The API: build, shared environment, replicas

```yaml
  api:
    build: .
    environment: &snip-env
      SNIP_DATABASE_URL: postgres://snip:snip@postgres:5432/snip?sslmode=disable
      SNIP_REDIS_ADDR: redis:6379
      SNIP_BASE_URL: http://localhost:8080
    depends_on:
      postgres: { condition: service_healthy }
      redis: { condition: service_healthy }
    deploy:
      replicas: 2                     # two copies behind nginx (chapter 8.3)
```

- **`build: .`** builds the image from the Dockerfile in this directory (chapter 9.2) instead of pulling one. `docker compose up --build` rebuilds it.
- The database URL's host is **`postgres`**, the service name, not `localhost`. The Redis address is `redis:6379`.
- **`&snip-env`** is a YAML **anchor**: it names this block so it can be reused below with `*snip-env`. That's plain YAML, not a Compose feature, and it saves copying the same variables twice.
- **`depends_on` with `condition: service_healthy`**: don't start the API until Postgres and Redis report healthy.
- **`deploy.replicas: 2`** runs two identical containers, `snip-api-1` and `snip-api-2`.
- No `ports:`: the API copies are **not** reachable from your machine directly. Only nginx is. That's the reverse-proxy pattern of chapter 8.3.

### The worker: same image, different program

```yaml
  worker:
    build: .
    entrypoint: ["/usr/local/bin/snip-worker"]
    environment: *snip-env
    depends_on:
      api: { condition: service_started }  # the API runs migrations first
```

snip's image contains both programs (chapter 9.2). **`entrypoint:`** overrides the image's `ENTRYPOINT`, so this service runs the worker. `*snip-env` reuses the API's environment.

### nginx: the only door

```yaml
  nginx:
    image: nginx:1.27-alpine
    ports:
      - "8080:80"                     # your browser talks to nginx, nginx to the api copies
    volumes:
      - ./deploy/nginx/nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on: [api]
```

- **`ports: "8080:80"`** publishes container port 80 on your machine's port 8080. It's the only published port in the core stack.
- This volume is a **bind mount**: a *file from your project* (`./deploy/nginx/nginx.conf`) mounted into the container, read-only (`:ro`). Edit the file, run `docker compose restart nginx`, and the change is live without rebuilding anything.

### Profiles: optional services

```yaml
  prometheus:
    image: prom/prometheus:v3.5.0
    profiles: ["observability"]       # start with: docker compose --profile observability up
    ports: ["9090:9090"]
    volumes:
      - ./deploy/prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro

  grafana:
    image: grafana/grafana:12.1.0
    profiles: ["observability"]
    ...

volumes:
  pgdata:
```

Services with a **`profiles:`** entry only start when that profile is asked for. Everyday `docker compose up` stays lean, and `--profile observability` adds monitoring (chapter 13.2). The top-level **`volumes:`** section declares the named volume `pgdata` that Postgres uses.

## Networking: find each other by name

Compose creates a private network for the project (`snip_default`) and connects every service to it. On that network, Docker runs a small **DNS server**: each **service name resolves to the IP addresses of that service's containers**. So:

- snip reaches Postgres at `postgres:5432` and Redis at `redis:6379`.
- nginx reaches the API at `api:8080`, and gets **both** copies' addresses.
- Prometheus finds every API copy by looking up `api` (its config uses `dns_sd_configs` with `names: [api]`).

:::warning[What can go wrong]
**`localhost` inside a container means that container itself** (its own network namespace, chapter 9.1), not your machine and not another container. `SNIP_DATABASE_URL=postgres://...@localhost:5432/...` works when snip runs directly on your laptop next to a Postgres container with a published port. Inside Compose it fails with "connection refused". Use the **service name**. This is the single most common Compose mistake.
:::

Containers on the network talk to each other on the containers' **own** ports (`api:8080`), whether or not those ports are published. `ports:` is only for traffic from **outside**, your machine, into the network.

**DNS isn't load balancing.** Docker's DNS returns all the copies' addresses, but *which* one gets used is up to the client. In a test, a simple client given both addresses sent 3 of 4 requests to the same copy. That's why snip puts nginx in front, which deliberately spreads requests round robin (chapter 8.3). And nginx looks up `api` **only when it starts**, so after scaling you run `docker compose restart nginx` (chapter 8.6).

## Volumes: what survives

| Kind | Written as | What it is | Use for |
|---|---|---|---|
| **Named volume** | `pgdata:/var/lib/postgresql/data` | Storage managed by Docker, kept until you delete it | Database files and other data that must survive |
| **Bind mount** | `./deploy/nginx/nginx.conf:/etc/...:ro` | A file or directory from your machine, mounted in | Config files; source code during development |
| *(none)* | | The container's writable layer | Scratch data you're happy to lose |

And the commands that decide their fate:

| Command | Containers & network | Named volumes (your data) |
|---|---|---|
| `docker compose stop` | Stopped, kept | Kept |
| `docker compose down` | **Removed** | **Kept** |
| `docker compose down -v` | Removed | **Deleted** |

:::danger
**`docker compose down -v` deletes the database.** In development that's often what you want: a clean slate. Just be sure it's the project you think it is. The same habit on a machine that runs something real destroys real data.
:::

## Startup order and health

`depends_on` alone only controls **start order**: Compose starts Postgres's container before the API's. But a *started* Postgres container isn't *ready* Postgres. It spends a few seconds initialising, and an API that connects immediately gets "connection refused". Hence:

- **`condition: service_healthy`**: wait until the dependency's healthcheck passes.
- **`condition: service_started`**: just wait for it to start (snip's worker, which only needs the API to have begun its migrations).
- **`condition: service_completed_successfully`**: wait for a one-off job, like a migration container, to finish with exit code 0.

Even so, **your program should retry its connections** (chapter 8.1). In production nothing guarantees start order: a database restarts under a running app, or a network blips. Healthchecks make local startup smooth; retries make the app survive the real world. `docker compose up --wait` blocks until everything is running and healthy. It's ideal in scripts and CI.

## The everyday commands

Run these from the directory containing the compose file.

| Command | Does |
|---|---|
| `docker compose up -d` | Create and start everything in the background; on later runs, **recreate only services whose config changed** |
| `docker compose up -d --build` | Rebuild images from Dockerfiles first (needed after code changes) |
| `docker compose up -d --wait` | …and wait until everything is healthy |
| `docker compose ps` | List this project's containers and their health |
| `docker compose logs -f api` | Follow one service's logs (all copies, prefixed `api-1`, `api-2`) |
| `docker compose exec postgres psql -U snip` | Run a command in a running container |
| `docker compose run --rm api keys create me` | Start a **new**, one-off container of a service with a different command |
| `docker compose restart nginx` | Restart one service (e.g. after editing its bind-mounted config) |
| `docker compose up -d --scale api=4` | Change the number of copies |
| `docker compose --profile observability up -d` | Include profile services |
| `docker compose config` | Print the final, merged configuration: great for debugging |
| `docker compose down` / `down -v` | Remove containers and network / plus volumes |

A detail worth knowing: after you change `environment:` for a service and run `up -d` again, Compose **recreates just that service's containers** and leaves the rest running. Change code, though, and nothing happens until you add `--build`, because the running containers use the image built earlier.

### Overrides, .env and variables

- **`docker-compose.override.yml`**, if present next to `docker-compose.yml`, is **merged automatically**. Teams use it for personal tweaks (publish the API port for debugging, mount source code) without editing the shared file. It's often gitignored.
- **`-f`** picks files explicitly: `docker compose -f docker-compose.yml -f compose.ci.yml up`.
- **Variable substitution**: `image: snip:${SNIP_TAG:-dev}` takes `SNIP_TAG` from your shell or from a **`.env` file** next to the compose file, defaulting to `dev`. The `.env` file is for Compose's own substitution; it doesn't automatically become the containers' environment. Keep real secrets out of both (chapter 7.6).

## What Compose is (and isn't) for

Compose is excellent for **development**, **CI** (snip's CI runs this exact stack on every push: up, smoke test through nginx, scale to 4, count clicks) and **small single-server deployments**. It isn't a production platform for anything that must survive a machine dying. Compose runs everything on **one host**. It doesn't move containers to a healthy machine when one fails, roll out new versions gradually with health checks, autoscale, or manage secrets across a fleet. That's the job of an **orchestrator**, and Part 10 is Kubernetes. The ideas carry straight over: services, replicas, health, config from the environment, volumes.

:::warning[What can go wrong]
- **`localhost` in a connection string** inside Compose: use the service name.
- **Code changes not showing up**: you ran `up -d` without `--build`.
- **"Port is already allocated"**: something on your machine (often a previous stack, or a local Postgres) already uses the host port. Change the left side of `ports:`, or stop the other thing.
- **Data "randomly" disappearing**: someone ran `down -v`, or a database had no volume.
- **Healthy-but-not-ready**: a healthcheck that passes too early (a port is open, but migrations haven't run). Make healthchecks check what really matters.
- **Publishing database ports** (`5432:5432`) on a server that's reachable from the internet, with the development password.
:::

:::info[In the real world]
Most teams keep a compose file in the repository so a new engineer can run the whole system with `docker compose up` on their first day. It's often the first "does it work?" step in the README (as in snip's). CI pipelines use it to start real dependencies for integration tests, and **dev containers** (VS Code, GitHub Codespaces) use it to define an entire development environment. The file doubles as living documentation of what the system is made of.
:::

## Lab

Free, on your own computer with Docker. Steps 1–3 and 5–7 run in snip's CI on every push; step 4 was tested on a test machine.

:::danger
Steps 5 and 7 use `docker compose down -v`, which **deletes the project's volumes, including the database**. Run it only in the lab's `snip` directory, and never on a machine that holds data you care about.
:::

1. **Bring up the stack and look around.**
   ```bash
   cd ~/code/zero-to-prod/snip
   docker compose up -d --build --wait
   docker compose ps                     # postgres and redis "healthy"; api-1, api-2, worker, nginx
   docker compose config --services      # the services this file defines
   ```

2. **Use it end to end.**
   ```bash
   KEY=$(docker compose exec -T api snip keys create me | grep -o 'snip_[A-Za-z0-9]*')
   SNIP_API_KEY="$KEY" ./scripts/smoke.sh http://localhost:8080          # [smoke] PASS
   curl -s -X POST localhost:8080/api/links -H "Authorization: Bearer $KEY" -d '{"url":"https://go.dev","slug":"counted"}'
   for i in 1 2 3 4 5; do curl -s -o /dev/null localhost:8080/counted; done
   ```

3. **Look inside the data services.**
   ```bash
   docker compose exec postgres psql -U snip -c "SELECT slug, clicks FROM links ORDER BY slug"
   docker compose exec redis redis-cli XLEN snip:clicks        # click events in the stream
   docker compose logs worker | tail -5
   ```
   After a few seconds, `counted` shows 5 clicks: the API recorded each click in Redis, and the worker added them to Postgres (chapter 8.2).

4. **Change configuration, and watch what Compose recreates.** Add `SNIP_LOG_LEVEL: debug` under the API's `environment:` (inside the `&snip-env` block), then:
   ```bash
   docker compose up -d                  # "Recreate" for api (and worker: it shares the block); postgres and redis untouched
   ```
   Revert it and run `up -d` again.

5. **Volumes: `down` keeps data, `down -v` doesn't.**
   ```bash
   docker compose down                   # containers and network removed…
   docker volume ls | grep pgdata        # …but snip_pgdata is still there
   docker compose up -d --wait
   docker compose exec postgres psql -U snip -c "SELECT slug, clicks FROM links WHERE slug='counted'"   # still there
   ```

6. **Add monitoring with a profile.**
   ```bash
   docker compose --profile observability up -d
   ```
   Open [localhost:9090/targets](http://localhost:9090/targets): Prometheus has found both API copies by DNS and shows them `UP`. Chapter 13.2 does the rest.

7. **Clean up completely** with `docker compose --profile observability down -v`, and confirm with `docker volume ls` that `snip_pgdata` is gone.

<details>
<summary>Write a compose file for a Python web app with Postgres, where the app publishes port 8000 and the database keeps its data.</summary>

```yaml
name: myapp

services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: app          # development only
      POSTGRES_DB: app
    volumes:
      - dbdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 3s
      retries: 20

  web:
    build: .
    ports:
      - "8000:8000"
    environment:
      DATABASE_URL: postgresql://app:app@db:5432/app   # "db", the service name, not localhost
    depends_on:
      db: { condition: service_healthy }

volumes:
  dbdata:
```

Key points: the app reaches the database as `db`; only the web app publishes a port; the database has a named volume and a healthcheck; and the app waits for it to be healthy (and should still retry on its own).

<details>
<summary>A teammate says "let's deploy to production with docker compose up on one big server". When is that reasonable, and what would you warn them about?</summary>

**Reasonable** for small, internal or early-stage systems where some downtime is acceptable: a single well-sized server with Compose is simple, cheap and understandable.

**Warn them** that everything depends on that one machine (it's a single point of failure). Compose won't move containers elsewhere if the machine dies. Deploys replace containers without gradual, health-checked rollouts, so expect brief downtime unless you add that yourself. There's no autoscaling. Secrets need proper handling (not development passwords in the file). Backups of the volumes are entirely their job. Plan for monitoring, restarts on reboot (`restart: unless-stopped`), and TLS in front. When any of those becomes painful, it's time for an orchestrator or a managed platform (Parts 10–12).

</details>
