# 8.2 Queues & background work

You sign up for a website and the page says "Welcome! Check your inbox." The email arrives a few seconds later. That gap is deliberate. Sending an email means talking to an email provider that might be slow or briefly down, and nobody wants a signup page that hangs, or fails, because of it. So the website writes "send a welcome email to this person" on a to-do list and answers you at once; a separate program works through the list in the background. That to-do list is a **queue**, and the program is a **worker**. They're one of the most useful patterns in backend engineering. This chapter explains how queues work, the guarantees they do and don't give, and lets you drive one by hand in a terminal before you see a real worker counting clicks.

## What you'll learn

- **Why** queues: keeping slow work off the request path, absorbing bursts, and surviving outages.
- The anatomy: **producer**, **broker**, **consumer**, **acknowledgement** and **redelivery**, tried live with Redis Streams.
- **Consumer groups** and **batching**: how several workers share the load efficiently.
- What goes wrong: **duplicates**, **poison messages** and **dead-letter queues**, **backpressure** and a queue that grows forever.
- The **dual-write problem** and the **outbox pattern**, and a tour of RabbitMQ, Kafka, SQS and friends.

## Why put work on a queue?

A **queue** is a to-do list shared between programs: one side adds tasks, the other takes them off and does them. It gives you four things at once:

1. **Fast responses.** The request handler only has to *record* that work needs doing (a sub-millisecond append), then answer the user.
2. **Absorbing bursts.** A sale or a viral post can bring thousands of requests a second. The queue soaks them up; workers process them at whatever steady rate the database or the email provider can take.
3. **Surviving outages.** If the email provider is down for a minute, signups keep working; the tasks wait in the queue until workers can send them.
4. **Independent scaling.** Need more throughput? Run more workers. The web app doesn't change.

```mermaid
flowchart LR
    U["user"] -->|"POST /signup"| API["web app<br/>(producer)"]
    API -->|"1. 'Welcome!' now"| U
    API -->|"2. add task"| Q[("queue<br/>(broker)")]
    Q --> W1["worker 1<br/>(consumer)"]
    Q --> W2["worker 2<br/>(consumer)"]
    W1 & W2 -->|"send"| E["email provider"]
```

The user's arrow (1) never waits for the email provider; only the workers do.

:::note[Everyday anchor]
A restaurant doesn't make you stand at the kitchen door while your meal is cooked. The waiter writes your order on a ticket and pins it to the rail (the queue), then goes back to serving. Cooks (workers) take tickets from the rail in order. If a rush arrives, tickets pile up on the rail instead of customers piling up at the door. And on a busy night, you add another cook, not another rail.
:::

## The anatomy of a queue

| Part | Role | In the email example |
|---|---|---|
| **Producer** | Adds messages (events, jobs) | The signup handler |
| **Broker** | Stores messages durably until they're handled | Redis, RabbitMQ, Kafka, SQS… |
| **Consumer** | Takes messages and does the work | The email worker |
| **Acknowledgement (ack)** | The consumer telling the broker "done, you can forget this one" | An `ACK` command or API call |

The acknowledgement is the key to reliability. A broker hands a message to a consumer but **keeps it** until acknowledged. If the consumer crashes before acking, the message is still there to be delivered again. That's how queues give **at-least-once** delivery ([chapter 8.1](./distributed-survival-kit.mdx): every message arrives one or more times): nothing is lost, at the price of occasional duplicates.

## Drive a queue by hand with Redis Streams

You can see every part of that table in five minutes, with no code. **Redis** is an in-memory data store ([chapter 6.7](../data/redis-and-caching.mdx)), and one of its data types, a **stream**, is an append-only log built for exactly this. Start a throwaway Redis and open its command line:

```bash
docker run -d --name qlab redis:7-alpine      # a Redis server in a container
docker exec -it qlab redis-cli                # a prompt for typing Redis commands
```

### Produce: append messages

```text
> XADD emails * to ana@example.com template welcome     # * = let Redis choose the ID
"1793282586265-0"
> XADD emails * to bo@example.com template welcome
"1793282586313-0"
> XADD emails * to cy@example.com template receipt
"1793282586362-0"
> XLEN emails
(integer) 3
```

Each entry gets an ID made of the time it was added (in milliseconds) and a sequence number, so entries stay in order.

### Consume: a consumer group shares the work

Several workers should share the stream, with each message going to **exactly one** of them. They join a **consumer group**, which remembers which entries it has handed to which consumer, and which are still unacknowledged (**pending**):

```text
> XGROUP CREATE emails mailers 0                        # group "mailers", starting from the beginning
OK
> XREADGROUP GROUP mailers alice COUNT 2 STREAMS emails >   # worker "alice" asks for 2 new (">") messages
1) "1793282586265-0" … ana@example.com …
2) "1793282586313-0" … bo@example.com …
> XREADGROUP GROUP mailers bob COUNT 2 STREAMS emails >     # worker "bob" gets what's left
1) "1793282586362-0" … cy@example.com …
```

```mermaid
flowchart LR
    S[("emails<br/>e1 e2 e3")] --> G{"consumer group<br/>'mailers'"}
    G -->|"e1, e2"| W1["alice"]
    G -->|"e3"| W2["bob"]
```

No message went to both. Run two copies of a worker and they divide the work automatically.

### Acknowledge, or be redelivered

Bob sends his email and acknowledges it. Alice, say, crashes before finishing hers:

```text
> XACK emails mailers 1793282586362-0                    # bob: "done"
(integer) 1
> XPENDING emails mailers - + 10                         # what's handed out but not acked?
1) "1793282586265-0"  "alice"  idle 253 ms  delivered 1 time
2) "1793282586313-0"  "alice"  idle 253 ms  delivered 1 time
```

Alice's two messages aren't lost: they're pending, waiting for an ack that will never come from her. Another worker can take them over once they've sat idle long enough (here, 1,000 ms):

```text
> XAUTOCLAIM emails mailers bob 1000 0-0 COUNT 10        # bob claims anything idle over 1 s
1) "1793282586265-0" … ana@example.com …
2) "1793282586313-0" … bo@example.com …
> XPENDING emails mailers - + 10
1) "1793282586265-0"  "bob"  …  delivered 2 times
2) "1793282586313-0"  "bob"  …  delivered 2 times
```

That's at-least-once delivery in front of you. Notice the delivery count went to 2: if alice actually *had* sent those emails and crashed just before acknowledging, ana and bo now get two welcome emails each. You'll meet the cure (idempotency) below. Leave with `exit` and remove the container with `docker rm -f qlab`.

:::info[If you've written code]
Every broker has the same three verbs under different names. RabbitMQ: `basic.publish`, `basic.consume`, `basic.ack`. Amazon SQS: `SendMessage`, `ReceiveMessage`, `DeleteMessage` (SQS's "ack" is deleting the message, and its "redelivery" is the message reappearing after a **visibility timeout**). Kafka has no per-message ack; a consumer commits an **offset**, "I've processed everything up to here".
:::

## Batching: let the queue save your database work

A worker doesn't have to take messages one at a time. Reading 500 at once and handling them together often turns 500 pieces of work into a few. Say each message is "page X was viewed". Instead of 500 `UPDATE pages SET views = views + 1` statements, the worker sums them in memory and writes `views = views + 230` for one page and `+ 270` for another: **two** writes. The database does a fraction of the work, and on a popular page it stops fighting over one row's lock 500 times ([chapter 6.5](../data/transactions.mdx)). The cost is a short delay before the number updates. Queues make this kind of **aggregation** natural, because the work is already waiting in a pile.

## What can go wrong with queues

### Duplicates

At-least-once means a message can be processed twice, as you saw. Sometimes that's acceptable (a page-view count off by one after a crash). When duplicates matter (emails, charges), make processing **idempotent** ([chapter 8.1](./distributed-survival-kit.mdx): doing it twice has the same effect as once). Record each processed message ID in the database, in the same transaction as the work, and skip IDs already seen.

### Ack too early, and you lose messages

The opposite mistake: acknowledge first, then do the work. A crash in between loses the message for good, because the broker was told to forget it. That's **at-most-once**, usually by accident. The rule: **ack after the work is done**.

### Poison messages and dead-letter queues

A **poison message** is one that can never be processed: malformed data, or a bug triggered by one specific input. If the worker retries it forever, it blocks everything behind it (or burns CPU endlessly). The standard answer is a **dead-letter queue** (DLQ): after N failed attempts (the delivery count you saw in `XPENDING`), move the message aside for a human to inspect, and carry on. Managed brokers such as SQS have this built in (`maxReceiveCount`); with Redis Streams you write it yourself.

### Backpressure and unbounded queues

If producers add messages faster than consumers process them, the queue **grows**. Brief growth is the point: that's absorbing a burst. Sustained growth means you need more workers, faster processing, or to shed load. That pressure flowing back from a slow consumer is called **backpressure**. Two numbers to watch ([chapter 13.2](../observability/metrics.mdx)):

- **Queue depth / lag**: how many messages are waiting (`XLEN`, and the group's `lag` in `XINFO GROUPS`).
- **Oldest message age**: how far behind the consumers are.

And a queue must have a **bound**. Redis keeps streams in memory; a stream nobody consumes grows until Redis runs out. `XADD … MAXLEN ~ 1000000` caps it at about a million entries by trimming the **oldest**. Whether losing the oldest messages during a long outage is acceptable depends entirely on what they are.

## The dual-write problem and the outbox pattern

A common need: *"when an order is placed, save it to the database **and** publish an `order.placed` event"* (for the warehouse, analytics, or an email). The obvious code writes to both:

```go
store.CreateOrder(ctx, order)   // 1. write to the database
queue.Publish("order.placed")   // 2. publish to the queue: what if this fails? Or we crash between the two?
```

If the process crashes between the two lines, the database has the order but the event is never sent. Reverse the order and the event can go out for an order that was never saved. Two systems, no shared transaction: that's the **dual-write problem** ([chapter 6.8](../data/choosing-a-datastore.mdx) warned about it).

The **outbox pattern** fixes it using what you already have, a database transaction ([chapter 6.5](../data/transactions.mdx)):

1. In the **same transaction** as the business change, insert the event into an **`outbox`** table.
2. A separate **relay** process reads unsent rows from `outbox`, publishes them to the queue, and marks them sent.

```mermaid
flowchart LR
    A["web app"] -->|"BEGIN; INSERT order; INSERT outbox event; COMMIT"| DB[("database<br/>orders + outbox")]
    R["relay"] -->|"read unsent events"| DB
    R -->|"publish"| Q[("queue")]
    R -->|"mark sent"| DB
```

The order and its event are now committed together or not at all. The relay may publish an event twice (if it crashes after publishing but before marking it sent), at-least-once again, so consumers stay idempotent. Tools that stream the database's change log directly (**change data capture**, for example Debezium) are a heavier-duty version of the same idea.

## A tour of brokers

| Broker | Model | Strengths | Typical use |
|---|---|---|---|
| **Redis Streams** | Append-only log with consumer groups | Simple, very fast, already in many stacks | Moderate-volume events and jobs |
| **RabbitMQ** | Classic message queues with routing | Flexible routing, per-message acks, mature | Task queues, workflows between services |
| **Apache Kafka** (and Redpanda) | Distributed, partitioned, replayable log | Enormous throughput, long retention, replay history | Event streaming, analytics pipelines, change data capture |
| **Amazon SQS** (and Google Pub/Sub) | Fully managed queue / pub-sub | No servers to run; scales automatically; built-in DLQs | Cloud-native job queues and fan-out |
| **NATS** | Lightweight messaging (+ JetStream for persistence) | Tiny, fast, simple | Service messaging, edge systems |

Two shapes to recognise: a **job queue** (each message is a task done once by one worker, then gone: RabbitMQ, SQS) and an **event log** (messages are facts kept for a period, which many different consumers can read and even replay: Kafka, Redis Streams). Many teams also use a database-backed job library (for Go, **River** uses Postgres) until volume demands a dedicated broker.

:::warning[What can go wrong]
- **Doing slow work in the request path.** The user waits, and a dependency blip becomes a user-facing error.
- **Acking before the work is done.** A crash loses the message (at-most-once by accident).
- **Non-idempotent consumers.** At-least-once delivery turns into double emails, double charges.
- **Nobody reclaims pending messages.** A crashed consumer's messages sit unacknowledged forever (see snip's bug below).
- **No dead-letter queue.** One poison message blocks or burns the whole pipeline.
- **Unbounded queues, unmonitored lag.** Memory runs out, or users see results hours late without anyone noticing.
- **Dual writes.** Database and queue drift apart. Use an outbox.
:::

## Apply it to snip

snip, the URL shortener built through this handbook, counts clicks exactly this way. When someone follows a snip link, the visitor needs the redirect; nobody is waiting for the click count. So the API (producer) appends a click event to a Redis stream (broker) called `snip:clicks`, redirects at once, and `snip-worker` (consumer) adds the clicks to Postgres in batches.

```mermaid
flowchart LR
    V["visitor"] -->|"GET /viral"| API["snip API"]
    API -->|"1. redirect now"| V
    API -->|"2. XADD click event"| Q[("Redis stream<br/>snip:clicks")]
    Q --> W1["snip-worker 1"]
    Q --> W2["snip-worker 2"]
    W1 & W2 -->|"batched UPDATE"| DB[("Postgres")]
```

### Producing: one fast append

The redirect handler calls `RecordClick`, which appends an event to the stream (`snip/internal/clicks/stream.go`):

```go
// Record appends one event. XADD is a single fast Redis command, so the
// redirect barely waits for it.
func (r *Recorder) Record(ctx context.Context, slug string) error {
	return r.rdb.XAdd(ctx, &redis.XAddArgs{
		Stream: StreamKey,              // "snip:clicks"
		MaxLen: maxLen,                 // 1,000,000
		Approx: true,
		Values: map[string]any{"slug": slug, "at": time.Now().UnixMilli()},
	}).Err()
}
```

It's the `XADD … MAXLEN ~ 1000000` you saw above, from Go. If this append fails (Redis is down), the redirect **still succeeds**: snip logs a warning and counts a `snip_click_record_errors_total` metric ([chapter 5.4](../apis/structuring-a-real-service.mdx)). Losing a click is better than failing a visitor.

### Consuming: the three reads you did by hand

The worker's main step, `ProcessOnce`, uses a consumer group called `workers`. It reads a batch, sums the clicks per slug, writes the sums, then acknowledges the batch (`snip/internal/clicks/stream.go`, trimmed):

```go
// 1. Our own events that were delivered but never acked (we crashed or
//    failed mid-batch last time): retry them first.
msgs, err := c.read(ctx, "0")
// 2. Events another worker took and never acked, for longer than
//    claimIdle (a minute): take them over.
if len(msgs) == 0 {
	msgs, _, err = c.rdb.XAutoClaim(ctx, &redis.XAutoClaimArgs{
		Stream: StreamKey, Group: Group, Consumer: c.name,
		MinIdle: c.claimIdle, Start: "0-0", Count: c.batch,
	}).Result()
}
// 3. New events (">"), waiting up to 2s for some to arrive.
if len(msgs) == 0 {
	msgs, err = c.read(ctx, ">")
}

counts := map[string]int64{}
for _, m := range msgs {
	counts[m.Values["slug"].(string)]++          // aggregate: 500 clicks → a few UPDATEs
}
for slug, n := range counts {
	dst.AddClicks(ctx, slug, n)                   // atomic: clicks = clicks + n (chapter 6.5)
}
c.rdb.XAck(ctx, StreamKey, Group, ids...)          // only now: "done"
```

Every idea from this chapter is in those lines:

- **Batching.** 500 click events for one viral link become **one** `UPDATE … SET clicks = clicks + 500`.
- **Ack after the work.** Events are acknowledged only after Postgres has the counts. A crash in between means the batch is redelivered: at-least-once. For click counts, a rare small overcount is an accepted trade-off, and the code says so in a comment.
- **Reclaiming pending events**, in the same order you did by hand: first its **own** pending entries (start ID `"0"`), then **other workers'** entries idle for over a minute (`XAUTOCLAIM`), then new ones (`">"`).

That middle step was missing for a long time, and the bug is worth understanding. Each worker's name includes its process ID, so it's unique. When a worker crashed mid-batch, its replacement (a new process, or a new pod in Kubernetes) had a **different** name, so it never asked for the dead worker's pending entries, and nobody else did either. Those clicks were never counted, and sat in Redis's pending list forever. The code's comment said crashes caused "a small over-count"; in fact the crash case caused a permanent *under*-count. A test now replays it: a worker takes three events and "dies" without acknowledging them, and a differently named worker must count all three once they've been idle long enough. **When you rely on a queue's redelivery, check who actually redelivers.**

### The rest of the worker

- **Poison messages**: clicks on a link deleted in the meantime are skipped (`links.ErrNotFound` isn't worth retrying). A production version would add a dead-letter stream for anything that fails more than N times.
- **The bound**: if workers are down long enough to exceed a million events, the oldest clicks are trimmed and lost. That's deliberate: protecting Redis's memory (and with it snip's cache and rate limits) matters more than perfect counts during a long outage.
- **The loop**: `snip/cmd/snip-worker/main.go` runs `ProcessOnce` until it's told to stop ([chapter 4.5](../go/concurrency.mdx)'s signal context), with exponential backoff and jitter when processing fails ([chapter 8.1](./distributed-survival-kit.mdx)). Run one worker or ten; the consumer group divides the work.

   ```bash
   go run ./cmd/snip-worker &
   ```

   All 50 counted, as a handful of batched `UPDATE`s, not 50.

<details>
<summary>A worker crashes mid-batch and is replaced by a new one with a different name. Days later, some messages were never processed. What would you check first?</summary>

Check the **pending list**: `XPENDING <stream> <group>` (or the broker's equivalent, such as in-flight messages in SQS). Messages delivered to the dead consumer and never acknowledged stay pending under *its* name. If no live consumer ever claims them (with `XAUTOCLAIM`, or reading its own pending entries with ID `0`), they're stuck forever, and nothing errors: the queue's depth looks fine, because they've already been delivered.

The fix is to have every worker periodically claim entries idle longer than a sensible time (snip uses a minute), and to alert on pending count and oldest-pending age. The rule: **redelivery isn't automatic until something does it.**

</details>

<details>
<summary>How does batching in a click-counting worker reduce database load? Give numbers.</summary>

Without batching, 5,000 clicks per second on a viral link would mean 5,000 `UPDATE` statements per second, all fighting over **the same row's lock** ([chapter 6.5](../data/transactions.mdx)): slow and contended. snip's worker reads up to 500 events at a time and **sums them per slug** first, so a batch of 500 clicks on one link becomes **one** `UPDATE links SET clicks = clicks + 500`. At 5,000 clicks per second that's about 10 updates per second instead of 5,000: a 500× reduction in writes and lock contention, for a delay of at most a couple of seconds in the displayed count.

</details>

<details>
<summary>snip's stream is capped at about a million events. When is that a good trade-off, and when would it be unacceptable?</summary>

It's good for **click counts**: if workers are down so long that more than a million clicks pile up, losing the oldest ones slightly undercounts some links, but it protects Redis's memory, and with it snip's cache and rate limiting, which keep the actual product working. It would be **unacceptable** for anything where every message matters: orders, payments, audit events. Those need a broker with durable, larger storage (Kafka, SQS), a much longer retention period, and alerts on lag well before any limit is reached.

</details>
