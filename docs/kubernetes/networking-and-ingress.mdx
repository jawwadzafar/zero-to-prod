# 10.3 Networking: Services, DNS, Gateways & policies

Pods come and go, and every new one gets a new IP address ([chapter 10.2](./core-objects.mdx)). Yet a web app always has to find its database, a rolling update must not drop requests, and users outside the cluster need one stable address to type into a browser. This chapter explains the layers that make that work. First the **Pod network**, where every Pod can reach every other. Then **Services**: stable names and addresses in front of changing Pods. Then **DNS**, which turns names into those addresses. Then **Gateways and Ingress**, the front door from outside. And finally **NetworkPolicies**, which turn "everything can talk to everything" into "only what should". You'll put a small web server behind a real Gateway and lock it down with a policy, and then do the same for snip and prove its database accepts connections only from snip.

## What you'll learn

- The Kubernetes **network model**: one flat network, an IP per Pod.
- **Services**: ClusterIP, NodePort, LoadBalancer and headless, and how kube-proxy and **EndpointSlices** make them work.
- **Cluster DNS** and service discovery: `echo`, `echo.demo`, `echo.demo.svc.cluster.local`.
- Getting traffic in: **Ingress**, the newer **Gateway API**, and `port-forward` for debugging.
- **NetworkPolicies**: default-deny, and allowing only what's needed.

---

## The Pod network

Kubernetes' network model makes three promises:

1. **Every Pod gets its own IP address.**
2. **Every Pod can reach every other Pod** by that IP, on any node, without NAT (address translation).
3. Agents on a node (like the kubelet) can reach all Pods on that node.

How that's achieved is left to a **CNI plugin** (Container Network Interface, the plug-in slot for Pod networking): kindnet in kind, Calico, Cilium, or your cloud's own (for example, AWS's VPC CNI gives Pods real addresses in your cloud network, [chapter 12.2](../cloud/cloud-networking.mdx)). From your app's point of view it's simple: one big flat network, where containers in a Pod share an IP and everything else is reachable. And because Pod IPs change constantly, **nothing should ever depend on a Pod's IP**. That's what Services are for.

## Services: a stable front for changing Pods

:::note[Everyday anchor]
A Service is a company's **main phone number**. Customers always dial the same number. Behind it, the switchboard forwards each call to whichever staff member is at their desk right now (ready Pods). Staff join, leave and change desks (Pods replaced, new IPs); the number never changes. Someone on a break (not ready) doesn't get calls.
:::

A **Service** gives a set of Pods (chosen by a label selector) one stable virtual IP address and DNS name, and load-balances connections across whichever of those Pods are **ready**. Here is the one from [chapter 10.2](./core-objects.mdx)'s `echo.yaml`, in front of three copies of the `http-echo` web server:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: echo
spec:
  selector:
    app: echo                        # the Pods behind this Service
  ports:
    - name: http
      port: 80                       # what clients connect to
      targetPort: http               # the container port named "http" (5678)
```

Three boxes show the idea:

```mermaid
flowchart LR
  C["Client Pod"] -->|"echo:80"| S["Service echo<br/>(stable virtual IP)"]
  S --> P1["Pod 10.244.0.7:5678"]
  S --> P2["Pod 10.244.0.9:5678"]
```

The client only ever knows `echo:80`. Which Pods sit behind it, and on which IPs, can change every minute.

How it works underneath:

- The **EndpointSlice** controller watches Pods matching the selector and keeps a list of the **ready** ones' IPs and ports. This is how a failing readiness probe ([chapter 10.2](./core-objects.mdx)) takes a Pod out of rotation.
- **kube-proxy** on every node watches Services and EndpointSlices and programs the node's packet filtering (iptables or nftables rules, or IPVS) so a connection to the Service's virtual IP is redirected to one of the endpoints. Some CNIs, like Cilium, replace kube-proxy with eBPF programs (small programs loaded into the kernel) doing the same job.
- Load balancing happens **per connection**, not per request. A client that keeps one HTTP/2 or keep-alive connection open ([chapter 5.4](../apis/structuring-a-real-service.mdx)) sticks to one Pod. That's fine for many small clients, and a known surprise for gRPC between two services.

```bash
kubectl -n demo get svc echo                                                    # the ClusterIP
kubectl -n demo get endpointslices -l kubernetes.io/service-name=echo -o wide   # the ready Pod IPs behind it
```

### Service types

| Type | Reachable from | How | Use for |
|---|---|---|---|
| **ClusterIP** (default) | Inside the cluster only | A virtual IP in the cluster's service range | Almost everything: internal services, databases |
| **NodePort** | Outside, via any node's IP | Opens the same high port (30000–32767) on every node | Rarely directly; building block for load balancers |
| **LoadBalancer** | Outside, via a cloud load balancer | The cloud provider creates a real load balancer pointing at the nodes | Exposing one service directly in the cloud |
| **Headless** (`clusterIP: None`) | Inside | No virtual IP: DNS returns the Pod IPs themselves | StatefulSets, where clients need a *specific* Pod (`postgres-0.postgres`) |
| **ExternalName** | Inside | A DNS alias (CNAME) to an outside name | Giving an external database a cluster-internal name |

On kind, `LoadBalancer` Services stay `<pending>` forever, because no cloud is there to create a load balancer. (The kind project offers `cloud-provider-kind` to simulate one.) For local work you use `port-forward`, or a Gateway reached through a port-forward, as in the lab.

## DNS: service discovery by name

Every cluster runs a DNS server (**CoreDNS**, in `kube-system`), and every Pod is configured to use it. Each Service gets a name:

```text
echo.demo.svc.cluster.local
└┬─┘ └┬─┘ └──────┬────────┘
 │    │          └ the cluster's domain
 │    └ namespace
 └ service name
```

Pods also get **search domains**, so shorter names work:

| From a Pod in… | Name | Resolves? |
|---|---|---|
| `demo` | `echo` | Yes: same namespace |
| any namespace | `echo.demo` | Yes |
| anywhere | `echo.demo.svc.cluster.local` | Yes, fully qualified |
| `monitoring` | `echo` | **No** (it looks for `echo` in `monitoring`) |

It's the same idea as Compose's service names ([chapter 9.3](../containers/docker-compose.mdx)): you configure an app with `http://echo` or `db:5432`, never an IP. Try it from inside the cluster:

```bash
kubectl -n demo run dns --rm -it --image=alpine:3.22 --restart=Never -- \
  sh -c 'nslookup echo.demo.svc.cluster.local; wget -qO- http://echo'
```

The `nslookup` shows the full name resolving to the Service's ClusterIP; the `wget` to plain `echo` works thanks to the search domains. (busybox's `nslookup` may not apply search domains itself, so give it the full name.)

## Getting traffic in from outside

A ClusterIP Service is invisible outside the cluster. Three ways in, from debugging to production:

**1. `kubectl port-forward`** tunnels a port on your machine through the API server to a Pod or Service. It's perfect for debugging, and not a way to serve users: it runs on your laptop and goes through the API server.

**2. Ingress** is the original Kubernetes object for HTTP routing: "requests for `shop.example.com` go to Service `web`". An **Ingress controller** (a reverse proxy running in the cluster, [chapter 8.3](../distributed/reverse-proxies-and-nginx.mdx)) reads Ingress objects and configures itself. Ingress works, and you'll meet it in many existing clusters, but it's limited: routing beyond host and path, TLS details and timeouts all live in controller-specific **annotations** that differ per controller. The long-popular community **ingress-nginx** controller has been **retired** (its maintainers ended support in March 2026), and new setups are steered towards the Gateway API.

**3. The Gateway API** is Ingress's successor: a set of standard objects with richer, portable routing, split by role:

```mermaid
flowchart LR
  GC["GatewayClass<br/>(which implementation)<br/>cluster admin"] --> GW["Gateway<br/>(a listener: port 80, TLS…)<br/>platform team"]
  GW --> R["HTTPRoute<br/>(hosts, paths → Services)<br/>app team"]
  R --> S["Service echo"] --> P["echo Pods"]
```

Read it left to right: a cluster admin installs an implementation once, a platform team opens listeners, and each app team attaches its own routes without touching the others. For `echo`:

```yaml title="gateway.yaml"
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata:
  name: eg
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller   # Envoy Gateway, one of many implementations
---
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: web
  namespace: demo
spec:
  gatewayClassName: eg
  listeners:
    - name: http
      protocol: HTTP
      port: 80
---
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: echo
  namespace: demo
spec:
  parentRefs:
    - name: web                         # attach to the Gateway above
  hostnames:
    - echo.localhost
  rules:
    - matches:
        - path: { type: PathPrefix, value: / }
      backendRefs:
        - name: echo                    # the Service
          port: 80
```

The Gateway API is implemented by many controllers (Envoy Gateway, NGINX Gateway Fabric, Traefik, Istio, Cilium, and the clouds' own load balancers), and the objects are the same for all of them. In the cloud, creating a Gateway typically provisions a real load balancer with a public IP. HTTPRoutes also support header matching, traffic splitting by weight (for canary releases, [chapter 11.3](../shipping/delivery-and-deployment.mdx)), redirects, and header changes, all without annotations.

## NetworkPolicies: who may talk to whom

By default, the flat network means **any Pod can connect to any Pod**, in any namespace. If an attacker gets code running in *any* container, your database is one connection away. A **NetworkPolicy** restricts traffic to the Pods it selects, like a firewall defined with labels: least privilege ([chapter 7.4](../security/authorization-multi-tenancy.mdx)), for the network.

:::note[Everyday anchor]
An office building where every door is unlocked is convenient until someone walks in off the street. NetworkPolicies are badge readers: the server room's door opens only for badges labelled "IT", whatever floor you're on.
:::

The standard pattern is **deny by default, then allow what's needed**:

```yaml title="policy.yaml"
# Deny all incoming traffic to every Pod in the namespace…
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: default-deny-ingress, namespace: demo }
spec:
  podSelector: {}                      # {} selects every Pod
  policyTypes: ["Ingress"]
---
# …then let echo accept connections only from Pods labelled role=frontend.
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: echo-from-frontend, namespace: demo }
spec:
  podSelector:
    matchLabels: { app: echo }
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector:
            matchLabels: { role: frontend }
      ports:
        - port: 5678                   # the Pod's port, not the Service's 80
```

Things to know:

- Policies are **additive allow-lists**. Once any policy selects a Pod for a direction (ingress or egress), only traffic some policy allows is permitted in that direction.
- Policies see **Pod** ports and IPs, after the Service has done its translation. That's why the rule says `5678`, not `80`.
- Enforcement depends on the **CNI plugin**. Calico and Cilium enforce policies, and recent kind versions do too. On a CNI that doesn't, policies are silently ignored. Test that yours are enforced (the lab does).
- **Egress** policies (what a Pod may connect *out* to) are powerful too: a compromised Pod that can't open connections to the internet can't easily send your data out. Remember to allow DNS (port 53 to CoreDNS), or nothing will resolve.

:::info[In the real world]
Larger platforms add a **service mesh** (Istio, Linkerd, Cilium's mesh). Sidecar or node proxies give every connection mutual TLS ([chapter 7.1](../security/security-literacy.mdx)), retries, per-request load balancing (fixing the gRPC problem above) and detailed traffic metrics, without changing the application. It's powerful and adds real operational weight. Most teams start with Services, a Gateway and NetworkPolicies, and add a mesh only when they need what it offers.
:::

## Apply it to snip

snip, the link shortener you build in this handbook, uses every layer above. Its manifests are in `snip/deploy/k8s/`.

**Services and DNS.** The API's Service (`snip/deploy/k8s/base/api.yaml`) is the same shape as `echo`'s: port `80` in front of the container port named `http`, which is snip's `8080`. Postgres and Redis each have a ClusterIP Service too, so snip's configuration refers to them by name, exactly as in Compose:

```yaml title="snip/deploy/k8s/base/config.yaml (excerpt)"
data:
  SNIP_REDIS_ADDR: redis:6379        # the Service "redis" in the same namespace
---
stringData:
  SNIP_DATABASE_URL: postgres://snip:snip-dev-only@postgres:5432/snip?sslmode=disable
```

Inside the `snip` namespace, `postgres` and `redis` resolve through the search domains; from another namespace you'd write `postgres.snip`.

**The Gateway.** `snip/deploy/k8s/gateway/gateway.yaml` is the same three objects as `gateway.yaml` above: the `eg` GatewayClass, a Gateway named `snip` in the `snip` namespace, and an HTTPRoute sending host `snip.localhost` to Service `api` on port 80, except the web UI ([chapter 16.6](../frontend/a-ui-for-snip.mdx)), which goes to Service `web`:

```yaml title="snip/deploy/k8s/gateway/gateway.yaml (excerpt)"
  rules:
    - matches:
        - path:
            type: PathPrefix
            value: /app
      backendRefs:
        - name: web                     # the web UI (chapter 16.6)
          port: 80
    - matches:
        - path:
            type: PathPrefix
            value: /
      backendRefs:
        - name: api                     # everything else: short links and the API
          port: 80
```

Both rules match `/app/`, so which wins? The Gateway API settles it by **specificity, not order**: an exact path beats a prefix, and a longer prefix beats a shorter one, whatever order the rules are written in. And `PathPrefix` compares whole path segments, not characters: `/app` matches `/app`, `/app/` and `/app/assets/index.js`, but not `/apple`, which stays a short link. snip refuses the slug `app`, so no link can hide behind the UI. The browser sees one origin for the page and the API, as it does through compose's nginx.

:::warning[What can go wrong]
Unlike the nginx configuration in [chapter 8.3](../distributed/reverse-proxies-and-nginx.mdx), snip's route sends **every** path except `/app` to snip, including `/metrics`, so the metrics are public through the Gateway. Production setups serve metrics on a **separate port** that no Service or route exposes, and scrape that port from inside the cluster. It's a good exercise: add a `SNIP_METRICS_ADDR` setting to snip, and scrape it in `deploy/prometheus/prometheus.yml`.
:::

**NetworkPolicies.** `snip/deploy/k8s/base/networkpolicy.yaml` follows the deny-then-allow pattern: `default-deny-ingress` for the namespace, `api-from-anywhere` opening the API's port 8080 (so the Gateway and your port-forwards work), `web-from-anywhere` doing the same for the web UI's nginx, and two policies letting only snip's own Pods reach the databases:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: postgres-from-snip
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: postgres
  policyTypes: ["Ingress"]
  ingress:
    - from:
        - podSelector:
            matchExpressions:
              - { key: app.kubernetes.io/name, operator: In, values: [api, api-canary, worker] }
      ports:
        - port: 5432
```

`redis-from-snip` is the same for port 6379. (`api-canary` is there for [chapter 11.3](../shipping/delivery-and-deployment.mdx)'s canary release.)

## Lab

Free, on your kind cluster from [chapter 10.1](./why-orchestration.mdx). Steps 1–4 use only `echo`; step 5 applies them to snip, deployed in [chapter 10.2](./core-objects.mdx)'s lab. The snip steps run in snip's CI on a fresh kind cluster.

1. **A Service and its endpoints.** Put `echo` in its own namespace (save `echo.yaml` from [chapter 10.2](./core-objects.mdx) first):
   ```bash
   kubectl create namespace demo
   kubectl -n demo apply -f echo.yaml
   kubectl -n demo rollout status deploy/echo
   kubectl -n demo get svc echo                                                    # the stable ClusterIP
   kubectl -n demo get endpointslices -l kubernetes.io/service-name=echo -o wide   # three Pod IPs
   kubectl -n demo get pods -l app=echo -o wide                                    # the same IPs
   ```
   Delete one Pod and list the EndpointSlice again: one IP is replaced, the ClusterIP never changes.

2. **Resolve names from inside the cluster**, with the `nslookup`/`wget` command from "DNS: service discovery by name". Then try the short name from *another* namespace: `kubectl run dns2 --rm -it --image=alpine:3.22 --restart=Never -- wget -qO- -T 3 http://echo` fails (no `echo` in `default`), while `http://echo.demo` works.

3. **Install a Gateway implementation and route to echo.** Envoy Gateway installs with Helm, Kubernetes' package manager ([chapter 10.6](./helm.mdx) explains it; `brew install helm`, or see [helm.sh](https://helm.sh/docs/intro/install/)):
   ```bash
   helm install eg oci://docker.io/envoyproxy/gateway-helm --version v1.9.3 \
     -n envoy-gateway-system --create-namespace --wait
   kubectl apply -f gateway.yaml                                   # the three objects above
   kubectl -n demo wait --for=condition=Accepted gateway/web --timeout=120s
   kubectl -n demo get gateway web          # PROGRAMMED False on kind: no load balancer to give it an address
   ```
   On a cloud cluster the Gateway would become **Programmed**, with a public address from a cloud load balancer. kind has no load balancer, so the Gateway is accepted and its proxy runs, but it never gets an external address. Envoy Gateway runs the proxy as a Service in its own namespace. Forward a port to it and send requests with and without the route's hostname:
   ```bash
   kubectl -n envoy-gateway-system wait --for=condition=Ready pod -l gateway.envoyproxy.io/owning-gateway-name=web --timeout=120s
   SVC=$(kubectl -n envoy-gateway-system get svc -l gateway.envoyproxy.io/owning-gateway-name=web -o name)
   kubectl -n envoy-gateway-system port-forward "$SVC" 8888:80 &
   curl -s -H "Host: echo.localhost" localhost:8888/                                    # hello from v1
   curl -s -o /dev/null -w "%{http_code}\n" -H "Host: other.example" localhost:8888/    # 404: no route for that host
   ```

4. **Lock echo down, and prove it.** Apply `policy.yaml`, then knock from a Pod without the right label and from one with it:
   ```bash
   kubectl apply -f policy.yaml
   kubectl -n demo run intruder --rm -it --image=alpine:3.22 --restart=Never -- \
     sh -c 'wget -qO- -T 3 http://echo || echo "intruder: blocked"'
   kubectl -n demo run friend --labels=role=frontend --rm -it --image=alpine:3.22 --restart=Never -- \
     wget -qO- -T 3 http://echo                                    # hello from v1
   ```
   Now the Gateway request from step 3 fails too: the Envoy proxy has no `role=frontend` label. That's deny-by-default doing its job. Clean up with `kubectl delete namespace demo`.

5. **Apply it to snip.** snip's base already includes its NetworkPolicies (applied in [chapter 10.2](./core-objects.mdx)). Add its Gateway, then repeat the checks:
   ```bash
   cd ~/code/zero-to-prod/snip
   kubectl -n snip get svc,networkpolicy
   kubectl apply -f deploy/k8s/gateway/gateway.yaml
   kubectl -n snip wait --for=condition=Accepted gateway/snip --timeout=120s
   kubectl -n envoy-gateway-system wait --for=condition=Ready pod -l gateway.envoyproxy.io/owning-gateway-name=snip --timeout=120s
   SVC=$(kubectl -n envoy-gateway-system get svc -l gateway.envoyproxy.io/owning-gateway-name=snip -o name)
   kubectl -n envoy-gateway-system port-forward "$SVC" 8888:80 &
   curl -s -H "Host: snip.localhost" localhost:8888/healthz        # {"status":"ok"}
   curl -sI -H "Host: snip.localhost" localhost:8888/app/ | grep -i content-security   # the web UI, from the web Pods
   kubectl -n snip run intruder --rm -it --image=alpine:3.22 --restart=Never -- \
     sh -c 'nc -z -w 3 postgres 5432 && echo "postgres: OPEN" || echo "postgres: blocked"; wget -qO- -T 3 http://api/healthz'
   ```
   ```text
   postgres: blocked
   {"status":"ok"}
   ```
   An unrelated Pod can reach the API (it's meant to be public) but not the database. snip itself still works (run the smoke test again), because its API and worker are allowed through.

<details>
<summary>Trace a request from a user's browser to a snip Pod in a cloud cluster using a Gateway.</summary>

1. The browser resolves `snip.example.com` via public DNS to the **cloud load balancer's** public IP (DNS, [chapter 1.4](../foundations/networks-from-zero.mdx)), which was created for the Gateway.
2. The load balancer forwards the connection to the **Gateway implementation's proxy** Pods (for example, Envoy), running in the cluster. With TLS, it terminates here ([chapter 8.3](../distributed/reverse-proxies-and-nginx.mdx)).
3. The proxy matches the request's host and path against **HTTPRoutes** attached to the Gateway, and picks the backend Service `api` in namespace `snip`.
4. The proxy sends the request to one of the Service's **ready endpoints**, a specific snip Pod IP, often directly from the EndpointSlice rather than via the ClusterIP.
5. The packet crosses the **Pod network** (the CNI) to the node running that Pod, and is delivered to snip's container on port 8080. NetworkPolicy allows it, because port 8080 on API Pods is open.
6. snip handles it (maybe calling `redis:6379` and `postgres:5432` through their Services, resolved by CoreDNS), and the response returns the same way.

</details>

<details>
<summary>Why doesn't a Service spread requests evenly for a gRPC client, and what are the options?</summary>

kube-proxy balances **connections**, not requests. gRPC uses HTTP/2, which sends many requests over **one long-lived connection**. So a gRPC client connects once to one Pod, and every request goes there, however many other Pods exist. New Pods added by scaling get nothing from existing clients.

Options: **client-side load balancing**, using a **headless Service** so DNS returns all Pod IPs, with the gRPC client spreading requests across them (gRPC supports this); a **proxy that balances per request** (a Gateway/Envoy in front, or a service mesh sidecar); or periodically **recycling connections** (a maximum connection age on the server) so clients reconnect and spread out over time.
