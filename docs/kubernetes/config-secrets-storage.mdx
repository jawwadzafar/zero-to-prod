# 10.4 Config, Secrets & storage

A container image should be the same in every environment ([chapter 9.2](../containers/writing-dockerfiles.mdx)). What changes between your laptop, staging and production is **configuration** (which database, which log level) and **secrets** (the database password, API keys). And some containers, like databases, need **storage** that outlives any one container. [Chapter 7.6](../security/secrets-management.mdx) set the rules: config lives in the environment, secrets never live in code or images. This chapter shows how Kubernetes delivers each: **ConfigMaps** and **Secrets** for configuration, and **PersistentVolumes** for data. It also covers the uncomfortable truth about what a Kubernetes Secret really protects, and what teams do about it. You'll try each on a small standalone example, then see how snip gets its settings and keeps its Postgres data.

## What you'll learn

- **ConfigMaps**: configuration as environment variables or files, and what happens when it changes.
- **Secrets**: how they differ from ConfigMaps, why **base64 is not encryption**, and how to protect them properly.
- Keeping real secrets out of Git: **External Secrets**, **Sealed Secrets**, and cloud secret stores.
- **Volumes**, **PersistentVolumeClaims**, **StorageClasses** and **access modes**.
- How a database keeps its data when its Pod is deleted, shown with snip's Postgres.

## ConfigMaps: configuration, delivered

:::note[Everyday anchor]
A ConfigMap is the **settings sheet** taped inside a shop's back office. The staff (containers) are the same people in every branch; each branch's sheet says its opening hours and which supplier to call. Change the sheet and the staff follow it, but only once they've read it again.
:::

A **ConfigMap** holds non-sensitive key/value configuration. Here's one for the `echo` web server from [chapter 10.2](./core-objects.mdx), which answers every request with the text in its `ECHO_TEXT` variable:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: echo-config
data:
  ECHO_TEXT: "hello from a ConfigMap"
  LOG_FORMAT: json                   # any number of keys
```

A Pod can use it in two ways:

- **As environment variables**: `envFrom: [configMapRef: {name: echo-config}]` in the container turns every key into a variable. You can also pick single keys with `env[].valueFrom.configMapKeyRef`. This suits programs that read their settings from the environment, as most modern services do.
- **As files**: mount the ConfigMap as a volume, and each key becomes a file. That suits whole config files: an `nginx.conf`, a `prometheus.yml`.

```yaml
# inside a Pod template
containers:
  - name: echo
    envFrom:
      - configMapRef: { name: echo-config }        # every key → an environment variable
    volumeMounts:
      - { name: conf, mountPath: /etc/app }        # every key → a file in /etc/app
volumes:
  - name: conf
    configMap: { name: echo-config }
```

:::warning[What can go wrong]
**Environment variables are read once, at start.** Change a ConfigMap and running Pods keep the old values until they restart. Mounted files *do* update (after a delay of up to a minute or so), but only if the program re-reads them. The reliable way to roll out new configuration is to trigger a rollout: `kubectl rollout restart deploy/echo`. Better still, make config changes part of the Pod template, so changing them automatically rolls out a new version. Kustomize's `configMapGenerator` and Helm checksum annotations ([chapter 10.6](./helm.mdx)) do exactly this by putting a hash of the content in the name or an annotation.
:::

## Secrets: like ConfigMaps, handled more carefully

A **Secret** has the same shape and the same uses (env vars or files) as a ConfigMap, but is meant for sensitive values:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: demo-db
type: Opaque
stringData:                          # plain text in; Kubernetes stores it base64-encoded
  DATABASE_URL: postgres://app:s3cret@db:5432/app
```

What Kubernetes does differently for Secrets:

- They can be restricted separately with **RBAC** (role-based access control): many people and tools may read ConfigMaps but not Secrets.
- Mounted as files, they live in memory (tmpfs) on the node, never written to its disk.
- The API server can **encrypt them at rest** in etcd, if the cluster is configured to (managed clusters usually are, or offer it).

And what it **doesn't** do: hide them. Look at how a Secret is stored:

```bash
kubectl get secret demo-db -o jsonpath='{.data.DATABASE_URL}'; echo
```

```text
cG9zdGdyZXM6Ly9hcHA6czNjcmV0QGRiOjU0MzIvYXBw
```

That's **base64** ([chapter 1.3](../foundations/bits-bytes-text-formats.mdx)), an *encoding*, not encryption. Anyone can reverse it:

```bash
kubectl get secret demo-db -o jsonpath='{.data.DATABASE_URL}' | base64 -d; echo
# postgres://app:s3cret@db:5432/app
```

:::danger
**Anyone who can read a Secret through the API, or create a Pod in its namespace (which can mount it), has the secret.** And a Secret written as YAML and committed to Git is a password in Git, base64 or not. Scanners that search public repositories for leaked keys find them within minutes ([chapter 7.6](../security/secrets-management.mdx)).
:::

### Keeping real secrets out of Git

Manifests belong in Git ([chapter 11.4](../shipping/gitops.mdx) builds everything on that). The secret values must not. Three common patterns:

| Pattern | How it works | Git contains |
|---|---|---|
| **External Secrets Operator** | A controller reads values from a real secret store (AWS Secrets Manager, Google Secret Manager, Azure Key Vault, HashiCorp Vault) and creates Kubernetes Secrets from them | An `ExternalSecret` saying *which* secret to fetch, never the value |
| **Sealed Secrets** / **SOPS** | Values are encrypted with a key only the cluster (or your KMS, a cloud key service) can decrypt | Encrypted values, safe to commit |
| **Secrets Store CSI driver** | Mounts values from the external store directly into Pods as files, optionally syncing to Secrets | A description of what to mount |

All three keep the source of truth in a system built for secrets, with audit logs, access control and **rotation** ([chapter 7.6](../security/secrets-management.mdx)). With cloud workload identity ([chapter 12.4](../cloud/iam.mdx)), the Pod proves its identity to the cloud without any stored credential at all. That's the best kind of secret: one that doesn't exist.

## Storage: data that outlives Pods

A container's filesystem disappears with the container ([chapter 9.1](../containers/what-a-container-is.mdx)). Kubernetes attaches storage through **volumes**:

| Volume type | Lifetime | Use for |
|---|---|---|
| `emptyDir` | As long as the **Pod** (survives container restarts, not rescheduling) | Scratch space, caches, sharing files between containers in a Pod |
| `configMap` / `secret` | Tied to that object | Config files and credentials |
| **PersistentVolumeClaim** | **Independent** of any Pod | Databases and anything that must survive |

### PersistentVolumes, claims and StorageClasses

:::note[Everyday anchor]
Renting a storage unit: you fill in a form saying "10 m², ground floor" (the **claim**). The company has a policy for how new units are built when it runs out (the **StorageClass**). The unit itself, with your boxes in it, is the **PersistentVolume**. You can move house as often as you like; the unit and its contents stay where they are until you cancel.
:::

Three objects separate "I need storage" from "here is a disk":

```mermaid
flowchart LR
  POD["Pod"] -->|mounts| PVC["PersistentVolumeClaim<br/>1Gi, ReadWriteOnce"]
  PVC -->|bound to| PV["PersistentVolume<br/>(an actual disk)"]
  SC["StorageClass<br/>(how to make disks)"] -.->|provisions on demand| PV
```

- A **PersistentVolumeClaim** (PVC) is a *request*: "1 GiB, mountable read-write by one node". Apps write claims.
- A **PersistentVolume** (PV) is an actual piece of storage: a cloud disk (EBS, Persistent Disk), a network filesystem, or a directory on a node.
- A **StorageClass** describes *how* to create PVs on demand. When a claim appears, its **provisioner** creates a matching disk automatically. kind ships a `standard` class that uses a directory on the node; clouds provide classes backed by their disks, with different speeds and prices.

The smallest real example is a claim and a Pod that writes to it:

```yaml title="storage.yaml"
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: notes
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 100Mi
---
apiVersion: v1
kind: Pod
metadata:
  name: writer
spec:
  containers:
    - name: writer
      image: busybox:1.37
      command: ["sh", "-c", "date >> /data/log.txt; cat /data/log.txt; sleep 3600"]   # append a line, show the file
      volumeMounts:
        - { name: data, mountPath: /data }
  volumes:
    - name: data
      persistentVolumeClaim: { claimName: notes }    # the claim above
```

Delete the Pod and create it again, and the file still has the first line: the claim, and the disk behind it, never went away. (The lab does exactly this.)

**Access modes** say how a volume can be mounted:

| Mode | Meaning | Typical backing |
|---|---|---|
| `ReadWriteOnce` (RWO) | Read-write by **one node** at a time | Cloud block disks: most common, fastest |
| `ReadOnlyMany` (ROX) | Read-only by many nodes | Shared reference data |
| `ReadWriteMany` (RWX) | Read-write by many nodes | Network filesystems (NFS, EFS, Filestore): slower |
| `ReadWriteOncePod` | Read-write by **one Pod** | Strict single-writer guarantees |

The **reclaim policy** decides what happens to the disk when the claim is deleted: `Delete` (the default for dynamic provisioning, so the data is gone) or `Retain` (the disk is kept for manual recovery). For anything precious, know which one you have.

### StatefulSets: one disk per copy

A Deployment's copies are interchangeable, so they can't each own a disk. A **StatefulSet** ([chapter 10.2](./core-objects.mdx)) can: instead of naming one claim, it carries a **volumeClaimTemplate**, and creates one claim per Pod: `data-db-0` for Pod `db-0`, `data-db-1` for `db-1`. When `db-0` is deleted, the StatefulSet recreates `db-0`, which mounts **the same claim**. Deleting the StatefulSet doesn't delete the claims either: data is deliberately harder to lose than Pods.

:::warning[What can go wrong]
- **A PVC is not a backup.** A disk can be corrupted, a table dropped, a claim deleted. Databases need real backups (dumps or snapshots, tested by restoring them). [Chapter 6.8](../data/choosing-a-datastore.mdx)'s advice applies unchanged.
- **Zone lock-in**: a cloud block disk lives in one availability zone ([chapter 12.2](../cloud/cloud-networking.mdx)), so a Pod using it can only run on nodes in that zone. If that zone's nodes are full or down, the Pod stays `Pending`.
- **Running production databases in Kubernetes yourself** takes real expertise: backups, failover, upgrades, tuning. Most teams use a **managed database** ([chapter 12.3](../cloud/compute-storage-databases.mdx)) and keep Kubernetes for stateless workloads, or use a mature **operator** (CloudNativePG for Postgres) that automates those jobs.
:::

:::info[In the real world]
A common production shape is: application config in ConfigMaps generated from files in Git; secrets pulled from the cloud's secret manager by the External Secrets Operator, with workload identity instead of stored credentials; databases managed by the cloud; and PersistentVolumes only for the few stateful things that must run in-cluster, each with a backup policy that has actually been tested.
:::

## Apply it to snip

snip, the link shortener you build in this handbook, reads every setting from `SNIP_*` environment variables and refuses to start with a bad one ([chapter 7.6](../security/secrets-management.mdx)). Its manifests split those settings by sensitivity (`snip/deploy/k8s/base/config.yaml`):

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: snip-config
data:
  SNIP_REDIS_ADDR: redis:6379
  SNIP_BASE_URL: http://localhost:8080
  SNIP_LOG_LEVEL: info
---
apiVersion: v1
kind: Secret
metadata:
  name: snip-db
type: Opaque
stringData:
  SNIP_DATABASE_URL: postgres://snip:snip-dev-only@postgres:5432/snip?sslmode=disable
---
# Redis requires this password (redis.yaml), so a Pod that gets past the
# NetworkPolicy still can't rewrite the cache or the click queue (chapter 7.6).
apiVersion: v1
kind: Secret
metadata:
  name: snip-redis
type: Opaque
stringData:
  SNIP_REDIS_PASSWORD: snip-dev-only    # a development password: never commit real ones (chapter 10.4)
```

The database URL is in a Secret because it contains a password. The API's Deployment pulls in all three with `envFrom` (one `configMapRef`, two `secretRef`s, [chapter 10.2](./core-objects.mdx)). The passwords are **development-only** values, committed so the labs work out of the box; a real deployment would replace these Secrets with `ExternalSecret`s.

The Redis password is used twice. snip reads it as `SNIP_REDIS_PASSWORD`. And Redis itself is started with it, from the same Secret, in `snip/deploy/k8s/base/redis.yaml`:

```yaml
          command: ["sh", "-c", 'exec redis-server --requirepass "$REDISCLI_AUTH"']
          env:
            - name: REDISCLI_AUTH           # redis-cli (the probe, kubectl exec) logs in with it too
              valueFrom:
                secretKeyRef: { name: snip-redis, key: SNIP_REDIS_PASSWORD }
```

`secretKeyRef` picks one key out of a Secret into one variable, where `envFrom` takes them all. Why does a cache inside the cluster need a password at all, when a NetworkPolicy ([chapter 10.3](./networking-and-ingress.mdx)) already decides which Pods may reach it? Because a policy is one layer, and layers fail: a network plugin that doesn't enforce policies, a rule widened by mistake, or one compromised Pod that the policy allows. With a password, reaching Redis is no longer enough to rewrite where a short link points.

snip's Postgres is a StatefulSet with a volumeClaimTemplate (`snip/deploy/k8s/base/postgres.yaml`, trimmed):

```yaml
kind: StatefulSet
metadata:
  name: postgres
spec:
  template:
    spec:
      containers:
        - name: postgres
          image: postgres:18-alpine
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql   # Postgres 18 keeps its files in 18/docker inside it, clear of the volume's lost+found
  volumeClaimTemplates:                     # one PersistentVolumeClaim per replica: data-postgres-0
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 1Gi
```

So Pod `postgres-0` always mounts claim `data-postgres-0`, and every link snip stores survives the Pod being deleted, rescheduled or upgraded.

## Lab

Free, on your kind cluster from [chapter 10.1](./why-orchestration.mdx). Steps 1–3 are standalone, in a scratch namespace; step 4 applies them to snip, deployed in [chapter 10.2](./core-objects.mdx)'s lab, and runs in snip's CI.

1. **Configure echo from a ConfigMap, and change it.**
   ```bash
   kubectl create namespace cfg && kubectl config set-context --current --namespace=cfg   # work in cfg
   kubectl apply -f echo.yaml                                          # echo from chapter 10.2
   kubectl create configmap echo-config --from-literal=ECHO_TEXT="hello from a ConfigMap"
   kubectl set env deploy/echo --from=configmap/echo-config            # wire the key in (this rolls out)
   kubectl rollout status deploy/echo
   kubectl port-forward svc/echo 8080:80 & sleep 2; curl localhost:8080   # hello from a ConfigMap
   kubectl patch configmap echo-config --type merge -p '{"data":{"ECHO_TEXT":"changed!"}}'
   curl localhost:8080                                                 # still the old text: env is read at start
   ```
   Now `kill %1`, run `kubectl rollout restart deploy/echo` and `kubectl rollout status deploy/echo`, start the port-forward again, and curl: `changed!`.

2. **See what a Secret really hides.**
   ```bash
   kubectl create secret generic demo-db --from-literal=DATABASE_URL='postgres://app:s3cret@db:5432/app'
   kubectl get secret demo-db -o jsonpath='{.data.DATABASE_URL}'; echo               # looks secret
   kubectl get secret demo-db -o jsonpath='{.data.DATABASE_URL}' | base64 -d; echo   # isn't
   ```

3. **Prove data survives its Pod.** Save `storage.yaml` from "PersistentVolumes, claims and StorageClasses", then:
   ```bash
   kubectl apply -f storage.yaml
   kubectl wait --for=condition=Ready pod/writer --timeout=60s
   kubectl get pvc notes                         # Bound  100Mi  RWO  standard
   kubectl logs writer                           # one line
   kubectl delete pod writer && kubectl apply -f storage.yaml    # a brand-new Pod, same claim
   kubectl wait --for=condition=Ready pod/writer --timeout=60s
   kubectl logs writer                           # two lines: the first one survived
   ```
   Clean up and go back to the default namespace: `kubectl config set-context --current --namespace=default && kubectl delete namespace cfg`.

4. **Apply it to snip.** Read its configuration, then prove its links survive a database Pod deletion:
   ```bash
   kubectl -n snip get configmap snip-config -o yaml
   kubectl -n snip get secret snip-db -o jsonpath='{.data.SNIP_DATABASE_URL}' | base64 -d; echo
   kubectl -n snip exec deploy/redis -- env -u REDISCLI_AUTH redis-cli ping   # NOAUTH: no password, no entry
   kubectl -n snip get pvc                           # data-postgres-0  Bound  1Gi  RWO  standard
   kubectl -n snip exec postgres-0 -- psql -U snip -c "INSERT INTO links (slug, url, owner_id) SELECT 'survivor', 'https://go.dev', id FROM api_keys LIMIT 1"
   kubectl -n snip delete pod postgres-0
   kubectl -n snip wait --for=condition=Ready pod/postgres-0 --timeout=120s
   kubectl -n snip exec postgres-0 -- psql -U snip -c "SELECT slug, url FROM links WHERE slug='survivor'"
   ```
   The new `postgres-0` mounted the same claim, so the row is still there. (If the INSERT says `INSERT 0 0`, there's no API key yet: create one first with `kubectl -n snip exec deploy/api -- snip keys create me`.) To roll out a config change to snip, the move is the same as step 1: `kubectl -n snip patch configmap snip-config …`, then `kubectl -n snip rollout restart deploy/api`.

<details>
<summary>Design how a production database password should reach an app's Pods on a cloud Kubernetes cluster (take snip as the example).</summary>

- The password lives in the cloud's **secret manager** (e.g. AWS Secrets Manager), created and **rotated** there, never in Git or in an image.
- The **External Secrets Operator** runs in the cluster with a cloud identity (workload identity, [chapter 12.4](../cloud/iam.mdx)) allowed to read only snip's secrets. An `ExternalSecret` in Git says "create Kubernetes Secret `snip-db` from secret manager entry `prod/snip/db`".
- The resulting Kubernetes Secret is readable (via **RBAC**) only by the operator and snip's namespace, and the cluster **encrypts Secrets at rest**.
- snip's Deployment reads `snip-db` through `envFrom`, exactly as in the dev manifests. The app doesn't change.
- On rotation, the operator refreshes the Secret, and a rollout restart (or a reloader tool) picks up the new value. Better still, the database uses short-lived credentials or IAM authentication, so there's no long-lived password at all.

</details>

<details>
<summary>Why do most teams run Postgres outside Kubernetes (a managed database), even though a StatefulSet can run it?</summary>

A StatefulSet gives Postgres a stable name and a persistent disk. That's necessary, but far from sufficient for a production database. You also need automated **backups** and point-in-time recovery, **replication and failover** when the primary's node dies, careful **version upgrades**, performance tuning, monitoring, and disk growth. A managed service (RDS, Cloud SQL, Azure Database) does all of that, run by specialists, with an SLA. Doing it yourself in Kubernetes is possible (operators like CloudNativePG automate much of it), but it's a significant ongoing responsibility, and mistakes lose data. Teams without dedicated database expertise usually choose managed, and keep their clusters stateless.

</details>
