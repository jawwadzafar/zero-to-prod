# 6.6 Postgres from Go

Typing SQL at a `psql` prompt is one person asking one question. A web service is different: thousands of requests a second, arriving on many goroutines at once, each needing an answer in a few milliseconds, some of them sent by people actively trying to break in. The SQL is the same as in [chapter 6.2](./sql-from-zero.mdx). What changes is everything around it: how the program connects, how it shares connections, how values get into a query without becoming part of it, and how the program's tables come to exist on every machine. This chapter teaches those moves on a small notes app you can run in two minutes, then shows the same moves in a real service.

## What you'll learn

- What a **connection string** holds, and why services share a few connections through a **connection pool** instead of opening one per request.
- The three ways to run SQL from Go with **pgx** (`QueryRow`, `Query`, `Exec`), and how **`Scan`** copies columns into Go variables.
- **Placeholders** (`$1`, `$2`): the one habit that makes **SQL injection** impossible. You'll run an injection attack and watch it work, then watch it fail.
- **Translating database errors** ("no rows", "duplicate key") into errors your program understands.
- **Migrations**: numbered SQL files that ship with the code and run once each, in order, on every database.
- How a real service, snip, applies all of this. You'll restart it and watch its data survive.

## A program talks to Postgres over a network connection

Postgres is a server ([chapter 1.6](../foundations/what-a-server-is.mdx)): a long-running program listening on port **5432**. Your Go program is a client, exactly like `psql`. It opens a TCP connection ([chapter 1.4](../foundations/networks-from-zero.mdx)), logs in, sends SQL as text, and reads rows back.

```mermaid
flowchart LR
    G["your Go program"] -->|"SQL text + values"| D["driver<br/>(pgx)"] -->|"TCP :5432"| P[("PostgreSQL")]
```

The piece in the middle is a **driver**: a library that speaks Postgres's wire protocol for you. In Go, the most widely used one is **pgx** (`github.com/jackc/pgx/v5`).

Everything the driver needs to find and log in to the database goes into one **connection string**, a URL:

```text
postgres://postgres:learn@localhost:5432/postgres?sslmode=disable
└─scheme─┘ └──user──┘└pw─┘ └──host──┘└port┘└─db───┘└──options───┘
```

`sslmode=disable` turns off encryption, which is fine on your laptop and wrong anywhere else ([chapter 7.1](../security/security-literacy.mdx)). Because the string holds a password, it comes from an **environment variable** (`DATABASE_URL` here), never from the source code.

## A connection pool shares a few connections between many requests

Opening a connection is slow: a TCP handshake, often a TLS handshake, a login, and some memory reserved on the database server for each one. That costs several milliseconds, which is longer than the query you wanted to run. Postgres also caps how many connections it accepts at once (`max_connections`, 100 by default).

So services open a few connections once and **share** them. A request **borrows** a connection, runs its query, and **returns** it for the next request. That shared set is a **connection pool**.

```mermaid
flowchart LR
    R1["request 1"] --> P
    R2["request 2"] --> P
    R3["request 3"] --> P
    P["connection pool<br/>(at most 5 open,<br/>lent out and returned)"] --> DB[("PostgreSQL :5432")]
```

If every connection is lent out, the next request **waits** until one comes back. That wait is the point: it keeps the database at a load it can handle.

:::note[Everyday anchor]
A connection pool is a company car pool. Buying a car for every trip would be absurdly slow and expensive, so the company keeps five cars that staff sign out, drive and return. If all five are out, you wait a few minutes for one to come back, which is far better than the car park overflowing.
:::

Here is the pool in the notes app. The example lives in `snip/examples/pgnotes/notes.go`; it stores notes with a unique title and a body, and knows nothing about any bigger project:

```go
// Open creates a pool for databaseURL (postgres://user:pass@host:5432/db)
// and checks that the database answers, so a wrong password fails now rather
// than on the first real query.
func Open(ctx context.Context, databaseURL string) (*Notes, error) {
	cfg, err := pgxpool.ParseConfig(databaseURL)
	if err != nil {
		return nil, fmt.Errorf("parse database URL: %w", err)
	}
	cfg.MaxConns = 5 // at most 5 connections open at once; requests beyond that wait their turn
	pool, err := pgxpool.NewWithConfig(ctx, cfg)
	if err != nil {
		return nil, err
	}
	if err := pool.Ping(ctx); err != nil {
		pool.Close()
		return nil, fmt.Errorf("ping: %w", err)
	}
	return &Notes{pool: pool}, nil
}
```

- **`pgxpool`** is pgx's pool. Creating it opens connections lazily, as they're needed.
- **`MaxConns`** is the cap. Without it, pgxpool uses 4 or the number of CPU cores, whichever is larger. You can also set it in the URL with `?pool_max_conns=20`.
- **`Ping`** makes the program **fail fast**: a wrong password or a stopped database is reported at startup, in one clear line, and not on the first user's request.

The pool is safe to use from many goroutines at once ([chapter 4.5](../go/concurrency.mdx)). You create it once, when the program starts, and pass it to everything that needs the database.

:::warning[Bigger pools are not faster]
Every copy of your service has its own pool. Ten copies with 20 connections each is 200 connections, already over Postgres's default limit of 100, and new connections start failing with `too many clients already`. Size pools deliberately (pool size × copies must fit under `max_connections`, with room for admin tools), and at large scale put a **connection pooler** such as PgBouncer between the services and the database ([chapter 8.6](../distributed/scaling.mdx)).
:::

## Three calls: one row, many rows, or no rows

pgx gives you a different call depending on what you expect back.

### QueryRow: exactly one row

```go
// Get returns the note with this title: QueryRow, for exactly one row.
func (n *Notes) Get(ctx context.Context, title string) (Note, error) {
	var note Note
	err := n.pool.QueryRow(ctx,
		`SELECT id, title, body, created_at FROM notes WHERE title = $1`, title,
	).Scan(&note.ID, &note.Title, &note.Body, &note.CreatedAt)
	if errors.Is(err, pgx.ErrNoRows) {
		return Note{}, ErrNotFound
	}
	return note, err
}
```

Four things to notice:

- **`ctx` comes first**, always. It's the request's context ([chapter 4.5](../go/concurrency.mdx)). If the caller gives up or a deadline passes, pgx cancels the query on the database too, so a hung query can't hold a connection forever.
- **`$1` is a placeholder.** The value `title` travels separately from the SQL. The next section shows why that matters so much.
- **`Scan(&note.ID, …)` copies each column, in order, into the variable at that address.** The `&` hands Scan somewhere to write ([chapter 4.2](../go/types-structs-errors.mdx)). pgx converts types for you: `bigint` becomes `int64`, `text` becomes `string`, `timestamptz` becomes `time.Time`. Columns are matched by **position**, not by name.
- **`pgx.ErrNoRows`** means the query found nothing. The function turns it into the program's own `ErrNotFound`, so code that calls `Get` never needs to import pgx.

### Query: many rows

```go
// List returns up to limit notes, newest first: Query, for many rows.
// CollectRows scans every row and closes the result, which hands the
// connection back to the pool.
func (n *Notes) List(ctx context.Context, limit int) ([]Note, error) {
	rows, err := n.pool.Query(ctx,
		`SELECT id, title, body, created_at FROM notes ORDER BY created_at DESC, id DESC LIMIT $1`, limit)
	if err != nil {
		return nil, err
	}
	return pgx.CollectRows(rows, scanNote)
}
```

`Query` returns a stream of rows that's still attached to a borrowed connection. **That connection stays checked out until the rows are closed.** `pgx.CollectRows` reads every row, scans each one with the function you give it (`scanNote` holds the same `Scan` call as `Get`), builds a slice, and closes the rows. If you loop over rows by hand instead, write `defer rows.Close()` on the next line, every time.

### Exec: no rows back

```go
// Delete removes the note with this title: Exec, when no rows come back.
func (n *Notes) Delete(ctx context.Context, title string) error {
	tag, err := n.pool.Exec(ctx, `DELETE FROM notes WHERE title = $1`, title)
	if err != nil {
		return err
	}
	if tag.RowsAffected() == 0 {
		return ErrNotFound
	}
	return nil
}
```

For `INSERT`, `UPDATE` and `DELETE` you usually only need **how many rows changed**. Zero rows deleted means there was nothing with that title, so the function reports `ErrNotFound` without a separate "does it exist?" query (which would race anyway, [chapter 6.5](./transactions.mdx)).

| Call | Use when | You get back |
|---|---|---|
| `QueryRow` | exactly one row expected | one row to `Scan`, or `pgx.ErrNoRows` |
| `Query` | zero or more rows | rows to loop over, then **close** |
| `Exec` | nothing to read back | a tag with `RowsAffected()` |

## Placeholders: the value travels separately from the query

It's tempting to build SQL by gluing strings together. The notes app keeps one function that does exactly that, so you can watch it fail:

```go
// FindUnsafe is the WRONG way, kept so you can watch it fail (chapter 6.6
// lab): it glues the title into the SQL text. A title such as
// x' OR '1'='1 rewrites the query and returns every note. Never do this.
func (n *Notes) FindUnsafe(ctx context.Context, title string) ([]Note, error) {
	query := "SELECT id, title, body, created_at FROM notes WHERE title = '" + title + "'"
	rows, err := n.pool.Query(ctx, query)
	// …
}
```

Now someone asks for the note titled `x' OR '1'='1`. The glued string becomes:

```sql
SELECT id, title, body, created_at FROM notes WHERE title = 'x' OR '1'='1'
```

The input's quote character **closed** the string early, and the rest of the input became SQL. `'1'='1'` is always true, so the query returns **every note**, including other people's. Worse inputs can read other tables or change data. This is **SQL injection**, for decades one of the most exploited holes on the web ([chapter 7.5](../security/web-attacks.mdx)).

With a placeholder (`WHERE title = $1`, value passed separately), the SQL text and the value reach Postgres as **two separate things**. Postgres parses the query's structure first, then slots the value in as pure data. `x' OR '1'='1` is just an odd title that no note has. Here are both, run against the same table:

```text
$ go run ./examples/pgnotes/cmd get "x' OR '1'='1"
error: note not found
$ go run ./examples/pgnotes/cmd find-unsafe "x' OR '1'='1"
string-built query returned 4 note(s):
11   private      not for you
12   secret       not for you
…
```

:::danger[The one rule]
**Every value from outside your code goes into SQL through a placeholder.** Never concatenate or `fmt.Sprintf` input into a query string. Escaping quotes by hand is not a substitute: people have been getting it wrong for thirty years. (Placeholders work for *values*. Table and column names can't be placeholders; if those must vary, pick them from a fixed list in your code.)
:::

## Turn database errors into your program's errors

Postgres reports every failure with a five-character **SQLSTATE code**. The notes table has `title TEXT NOT NULL UNIQUE`, so adding a second note with the same title fails with code `23505`, *unique violation*. `Add` translates it:

```go
// uniqueViolation is the SQLSTATE code Postgres sends for a duplicate key.
const uniqueViolation = "23505"

// Add inserts a note. RETURNING sends back the values Postgres filled in
// (the id and the timestamp) in the same round trip.
func (n *Notes) Add(ctx context.Context, title, body string) (Note, error) {
	note := Note{Title: title, Body: body}
	err := n.pool.QueryRow(ctx,
		`INSERT INTO notes (title, body) VALUES ($1, $2) RETURNING id, created_at`,
		title, body,
	).Scan(&note.ID, &note.CreatedAt)
	var pgErr *pgconn.PgError
	if errors.As(err, &pgErr) && pgErr.Code == uniqueViolation {
		return Note{}, ErrDuplicate
	}
	return note, err
}
```

- **`RETURNING id, created_at`** asks Postgres to send back the values it filled in (the next id from the sequence, the default timestamp) in the same round trip, so there's no second query.
- **`errors.As`** ([chapter 5.3](../apis/validation-errors-status-codes.mdx)) checks whether the error is a `*pgconn.PgError`, and if so gives you its fields, including `Code`.
- **No "is this title free?" check comes first.** Two requests could both check, both see "free", and both insert. The `UNIQUE` constraint is the only judge that can't race: exactly one insert wins, and the other gets `ErrDuplicate` ([chapter 6.5](./transactions.mdx)).

Why translate at all? Because the code that calls `Add` (an HTTP handler, a CLI) should decide what a duplicate *means* to a user, like "409 Conflict" or "pick another title", without knowing what SQLSTATE is. The database details stay in one file.

Codes worth recognising:

| SQLSTATE | Means | Usual response |
|---|---|---|
| `23505` | unique violation | "already exists" (409 in an API) |
| `23503` | foreign key violation | the thing you reference doesn't exist |
| `23514` | check violation | invalid data got past validation |
| `40P01` | deadlock detected | retry the transaction |
| `40001` | serialization failure | retry the transaction |

## Migrations: the schema ships with the code

The notes app creates its table with `CREATE TABLE IF NOT EXISTS` at startup. That works for exactly one version of the schema. The day you add a column, `IF NOT EXISTS` sees the old table and does nothing, and your new code crashes on a column that isn't there.

Real services use **migrations** ([chapter 6.3](./designing-schemas.mdx)): each schema change is a numbered SQL file, committed to Git next to the code that needs it.

```text
migrations/
├── 0001_create_notes.sql      CREATE TABLE notes (…)
├── 0002_add_tags.sql          ALTER TABLE notes ADD COLUMN tags text[] …
└── 0003_index_created.sql     CREATE INDEX …
```

A **migration runner** applies them. Every runner does the same four things:

1. Keep a table in the database recording which versions have run (often `schema_migrations`).
2. Take a **lock**, so two copies of the program starting at once don't both run `0002`.
3. Apply every file not yet recorded, **in order**, each inside a **transaction** with the insert that records it. A failing migration leaves nothing half-applied.
4. Release the lock.

```mermaid
flowchart LR
    S["program starts"] --> L["take lock"] --> M["apply new files in order,<br/>each in one transaction"] --> U["release lock,<br/>start serving"]
```

Most teams use a tool for this: **golang-migrate**, **goose** or **Atlas** in Go, **Flyway** or **Liquibase** on the JVM, or the one built into their framework. In Go you can also compile the SQL files *into* the binary with `//go:embed`, so the program and the schema it expects can never get separated. You'll see a small hand-written runner doing exactly that in the snip section below.

Two rules hold whichever runner you use. Never edit a migration that has already run somewhere: other databases won't re-run it, so add a new one. And on a live system, change columns with **expand, then contract** ([chapter 6.3](./designing-schemas.mdx)), because old and new code run side by side during a deploy.

A third habit comes from security. Creating and altering tables needs far more power than reading and writing rows, and the login that creates a table **owns** it: it can alter it, drop it, or remove the protections on it. So production setups often run migrations as their own step, signed in as an owner login, and let the running program sign in as a second login that may only read and write rows. [Chapter 7.4](../security/authorization-multi-tenancy.mdx) shows why that matters; you'll see snip's version below.

:::info[If you've written code]
Many languages lean on an **ORM** (object-relational mapper) such as Prisma, SQLAlchemy, Hibernate or GORM, which generates SQL from objects. ORMs speed up simple create/read/update/delete code, but hide what SQL runs, which is how N+1 queries ([chapter 6.4](./indexes-and-performance.mdx)) sneak in. Go culture leans towards writing SQL directly, as in this chapter, or generating type-safe Go from SQL with **sqlc**. Whatever you use, learn to read the SQL it produces.
:::

:::warning[What can go wrong]
- **SQL built from strings.** SQL injection. Placeholders, always.
- **Leaking rows.** `pool.Query` without closing the rows keeps a connection checked out. After a few requests the pool is empty and every request hangs waiting for a connection. Use `CollectRows`, or `defer rows.Close()`.
- **No deadline on queries.** A query stuck behind a lock holds its connection forever. Pass a context that carries a timeout.
- **Scanning in the wrong order.** `Scan` matches columns by position. Reorder the `SELECT` without reordering the `Scan`, and values land in the wrong fields, or fail on a type mismatch.
- **Too many connections.** Pool size × number of copies must fit within `max_connections`.
- **Checking before inserting.** "If it's free, insert it" races. Insert, and translate the unique-violation error.
:::

## Apply it to snip

snip, the link shortener you build in this handbook ([chapter 0.3](../start/meet-snip.mdx)), keeps its links and API keys in Postgres. All of its database code is one file, `snip/internal/store/postgres/postgres.go`, and every move in it is one you've now seen. It implements snip's `Store` interface ([chapter 4.3](../go/packages-modules-interfaces.mdx)), so the rest of snip can't tell it apart from the in-memory store used in tests.

### The pool

```go
// Store wraps a pgx connection pool. Every change it makes to links or keys
// also appends an audit_events row in the same transaction (see record).
type Store struct {
	pool *pgxpool.Pool
}

// Open connects to databaseURL (e.g. postgres://user:pass@host:5432/db) and
// checks the connection works.
func Open(ctx context.Context, databaseURL string) (*Store, error) {
	pool, err := pgxpool.New(ctx, databaseURL)
	if err != nil {
		return nil, fmt.Errorf("postgres: parse config: %w", err)
	}
	if err := pool.Ping(ctx); err != nil {
		pool.Close()
		return nil, fmt.Errorf("postgres: ping: %w", err)
	}
	return &Store{pool: pool}, nil
}
```

The URL comes from `SNIP_DATABASE_URL`. snip leaves the pool size at pgx's default and lets operators set `pool_max_conns` in the URL, because the right size depends on how many copies run ([chapter 8.6](../distributed/scaling.mdx)).

### The redirect lookup and the list

```go
func (s *Store) Get(ctx context.Context, slug string) (links.Link, error) {
	var l links.Link
	err := s.pool.QueryRow(ctx,
		`SELECT slug, url, owner_id, clicks, created_at FROM links WHERE slug = $1`, slug,
	).Scan(&l.Slug, &l.URL, &l.OwnerID, &l.Clicks, &l.CreatedAt)
	if errors.Is(err, pgx.ErrNoRows) {
		return links.Link{}, links.ErrNotFound
	}
	return l, err
}
```

`Get` runs on every redirect; the `slug` primary key gives it an index for free. `ListByOwner` is the `Query` + `CollectRows` pattern with `WHERE owner_id = $1 ORDER BY created_at DESC LIMIT $2`, which is exactly the query [chapter 6.4](./indexes-and-performance.mdx)'s composite index was built for.

### Ownership inside the query

```go
// Delete removes the link and records who deleted it in one transaction: if
// the audit row can't be written, the link isn't deleted either (chapter 6.5).
func (s *Store) Delete(ctx context.Context, slug string, ownerID int64) error {
	return pgx.BeginFunc(ctx, s.pool, func(tx pgx.Tx) error {
		var url string
		err := tx.QueryRow(ctx,
			`DELETE FROM links WHERE slug = $1 AND owner_id = $2 RETURNING url`, slug, ownerID,
		).Scan(&url)
		if errors.Is(err, pgx.ErrNoRows) {
			return links.ErrNotFound
		}
		if err != nil {
			return err
		}
		return record(ctx, tx, ownerID, audit.LinkDeleted, slug, map[string]string{"url": url})
	})
}
```

`AND owner_id = $2` puts the **ownership check inside the statement**. Deleting someone else's link matches no row, so `RETURNING url` returns nothing, and `Delete` returns `ErrNotFound`: the "404, not 403" rule from [chapter 5.2](../apis/designing-rest-apis.mdx), enforced in one atomic statement with no gap between checking and deleting.

The rest is snip's **audit trail**, a table that records every change to links and keys. `pgx.BeginFunc` starts a transaction, runs the function inside it, and commits if the function returns `nil` or rolls back if it returns an error. `record` inserts the `audit_events` row (who, what, which request, and the URL the link pointed to) through the same `tx`. So the delete and its record commit together or not at all ([chapter 6.5](./transactions.mdx)).

### Duplicate slugs

```go
// uniqueViolation is Postgres's error code for a duplicate key.
const uniqueViolation = "23505"

func (s *Store) Create(ctx context.Context, l links.Link) (links.Link, error) {
	err := pgx.BeginFunc(ctx, s.pool, func(tx pgx.Tx) error {
		err := tx.QueryRow(ctx,
			`INSERT INTO links (slug, url, owner_id, created_at)
			 VALUES ($1, $2, $3, $4)
			 RETURNING clicks, created_at`,
			l.Slug, l.URL, l.OwnerID, l.CreatedAt,
		).Scan(&l.Clicks, &l.CreatedAt)
		if err != nil {
			return err
		}
		return record(ctx, tx, l.OwnerID, audit.LinkCreated, l.Slug, map[string]string{"url": l.URL})
	})
	var pgErr *pgconn.PgError
	if errors.As(err, &pgErr) && pgErr.Code == uniqueViolation {
		return links.Link{}, links.ErrSlugTaken
	}
	return l, err
}
```

The notes app's `Add`, with a different table, plus the same audit write as `Delete`. A duplicate slug fails the `INSERT`, the function returns that error, `BeginFunc` rolls back and hands it on, and no audit row is written for a link that was never created. `ErrSlugTaken` then means two things higher up: the HTTP layer answers **`409 Conflict`** for a custom slug, and the `Service` quietly retries with a new random slug when it generated one itself ([chapter 4.2](../go/types-structs-errors.mdx)).

### Embedded migrations, behind a lock

snip's migrations live in `snip/internal/store/postgres/migrations/` (starting with `0001_init.sql`) and are compiled into the binary:

```go
//go:embed migrations/*.sql
var migrationFiles embed.FS
```

`Migrate`, in the same file, is a small hand-written runner doing the four steps from the migrations section. Its lock is a Postgres **advisory lock**: a named lock with no row attached, meaning "only one of us may do this at a time" ([chapter 6.5](./transactions.mdx)):

```go
// Serialise concurrent migrators (e.g. two pods starting at once).
conn, err := s.pool.Acquire(ctx)
if err != nil {
	return nil, err
}
defer conn.Release()
if _, err := conn.Exec(ctx, `SELECT pg_advisory_lock(7412)`); err != nil {
	return nil, err
}
defer conn.Exec(context.Background(), `SELECT pg_advisory_unlock(7412)`) //nolint:errcheck
```

Notice `Acquire`: an advisory lock belongs to one **connection**, so `Migrate` borrows a single connection from the pool and does all its work on it. Running each statement on whatever connection the pool hands out would take the lock on one connection and run migrations on others. When three copies of snip start at once on Kubernetes, the first takes the lock and migrates; the other two wait, then find every version already recorded in `schema_migrations`.

### Two logins: one changes the schema, one serves

`snip migrate` applies the migrations and exits; `snip serve` (and `snip keys`) also check on start. Which login does the work depends on one setting:

- **`SNIP_DATABASE_URL` alone**: one login migrates and serves. That's this chapter's lab, and fine on a laptop.
- **`SNIP_MIGRATE_DATABASE_URL` as well**: migrations run as that login, the schema's owner, and `SNIP_DATABASE_URL` becomes the app's own login, `snip_app`, which may read and write rows but never change the schema ([chapter 7.4](../security/authorization-multi-tenancy.mdx)). `snip migrate` creates that login, with the password in its URL, after migrating.

Every deployment in this handbook runs `snip migrate` as a separate step with the owner's login (a one-shot Compose service, a Kubernetes init container, an ECS container that must succeed before the API starts), and gives the API only `snip_app`'s. When that API starts, it still calls `Migrate`, which first asks whether anything is pending:

```go
	if pending, err := s.pending(ctx, names); err != nil || !pending {
		return []int{}, err // empty, not nil, so "nothing to do" logs as []
	}
```

`pending` only reads `schema_migrations`, which `snip_app` may do, so a current schema costs one query and no special rights. If a migration *is* pending and the login can't apply it, snip stops with `permission denied … run "snip migrate" with SNIP_MIGRATE_DATABASE_URL set to the schema owner's login`, rather than serving against a schema its code doesn't expect.

## Lab

Free, on your own computer, using Docker ([chapter 0.2](../start/set-up-your-machine.mdx)). Steps 1–3 use the standalone notes app; step 4 applies it to snip. Run the Go commands from the `snip/` folder of your copy of the repository.

1. **Start Postgres and run the notes app.**
   ```bash
   docker run -d --name pg-lab -e POSTGRES_PASSWORD=learn -p 5432:5432 postgres:18-alpine   # a throwaway Postgres
   export DATABASE_URL="postgres://postgres:learn@localhost:5432/postgres?sslmode=disable"
   cd ~/code/zero-to-prod/snip
   go run ./examples/pgnotes/cmd add groceries "eggs, flour"     # added note 1 at …
   go run ./examples/pgnotes/cmd add ideas "learn SQL"
   go run ./examples/pgnotes/cmd list                            # newest first
   go run ./examples/pgnotes/cmd add groceries "again"           # error: … already exists
   ```
   Notice the last line. The `UNIQUE` constraint refused the row, and `Add` turned SQLSTATE `23505` into a sentence a person can read.

2. **Watch the same data from the database's side.**
   ```bash
   docker exec -it pg-lab psql -U postgres -c 'SELECT * FROM notes;'       # the rows the app wrote
   docker exec -it pg-lab psql -U postgres -c "SELECT count(*) FROM pg_stat_activity WHERE datname = 'postgres';"   # open connections right now
   ```
   The second command counts connections. Run it while nothing is running, and it shows only the `psql` you're using: the notes app closed its pool on exit.

3. **Run an injection attack, then watch a placeholder stop it.**
   ```bash
   go run ./examples/pgnotes/cmd find-unsafe "x' OR '1'='1"   # string-built SQL: returns EVERY note
   go run ./examples/pgnotes/cmd get "x' OR '1'='1"           # placeholder: note not found
   ```
   Same input, same table. The only difference is whether the value was glued into the SQL text or sent separately.

4. **Apply it to snip: links that survive a restart.** snip uses the same database (its tables don't clash with `notes`):
   ```bash
   export SNIP_DATABASE_URL="$DATABASE_URL"
   go run ./cmd/snip migrate            # "migrations applied" versions=[1,2,3]
   go run ./cmd/snip migrate            # again: versions=[] — nothing left to do
   go run ./cmd/snip keys create me     # prints your snip_… key — copy it
   export KEY=snip_paste_it_here
   go run ./cmd/snip &                  # start snip in the background (chapter 1.2)
   sleep 3
   curl -s -X POST localhost:8080/api/links -H "Authorization: Bearer $KEY" \
     -d '{"url":"https://go.dev/doc/","slug":"godoc"}' | jq .
   kill %1                              # stop snip (graceful shutdown)
   go run ./cmd/snip &                  # start it again
   sleep 3
   curl -si localhost:8080/godoc | head -2                   # 302: the link SURVIVED the restart
   curl -si "localhost:8080/x'%20OR%20'1'='1" | head -1      # 404: the attack is only a strange slug
   docker exec -it pg-lab psql -U postgres -c 'SELECT * FROM schema_migrations;'
   docker exec -it pg-lab psql -U postgres -c 'SELECT id, name, left(key_hash, 12) AS hash FROM api_keys;'
   ```
   Compare with [chapter 5.1](../apis/first-http-server.mdx), where snip kept links in memory and a restart wiped everything. Notice also that `api_keys` stores only a hash of your key, never the key itself ([chapter 7.2](../security/authentication.mdx) explains why). Finish with the integration tests ([chapter 4.4](../go/testing.mdx)), which run against this real database, then clean up:
   ```bash
   SNIP_TEST_DATABASE_URL="$DATABASE_URL" go test ./examples/pgnotes/ ./internal/store/postgres/ -v
   kill %1; docker rm -f pg-lab
   ```

<details>
<summary>Walk through what happens, step by step, when snip handles <code>DELETE /api/links/godoc</code> from a user who doesn't own it.</summary>

1. The `requireKey` middleware authenticates the key and puts the owner (say ID 7) into the request context ([chapter 5.4](../apis/structuring-a-real-service.mdx)).
2. The handler calls `Service.Delete(ctx, 7, "godoc")`.
3. The Postgres store borrows a connection from the pool, begins a transaction and runs `DELETE FROM links WHERE slug = $1 AND owner_id = $2 RETURNING url` with `godoc` and `7`.
4. The row belongs to another owner, so **zero rows** match and `RETURNING` gives nothing back: `Scan` reports `pgx.ErrNoRows`.
5. The store returns `links.ErrNotFound`, so the transaction rolls back with no audit row written; the HTTP layer answers `404 not_found`.

The ownership check and the delete are one atomic statement, so there's no moment where someone else could slip in, and the response reveals nothing about whether `godoc` exists.

</details>

<details>
<summary>Why embed migration files in the binary instead of reading them from disk at runtime?</summary>

So the program and its schema **can never get out of sync**. The binary that expects the `links` table carries exactly the SQL that creates it. There's no separate folder to forget to copy onto the server or into the container ([chapter 9.2](../containers/writing-dockerfiles.mdx)), no risk of running version 12 of the code against version 11's files, and the container image stays one self-contained file. The cost: changing the schema means building a new binary, which you'd do anyway, because the code that uses a new column ships in the same commit.

</details>
