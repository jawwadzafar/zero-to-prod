# 6.7 Redis & caching

Open a popular product page and the server asks the database the same question it answered a millisecond ago for someone else: *what does this product cost?* The answer hasn't changed, yet the database does the work again, thousands of times a second. The fastest query is the one you never run. A **cache** remembers recent answers somewhere fast, so most requests never reach the database at all. The tool nearly everyone uses for that is **Redis**. This chapter teaches caching on one deliberately slow function you can run on your laptop, then applies it to a real service, and explains the quip that there are only two hard things in computer science, one of which is **cache invalidation**.

## What you'll learn

- What a **cache** is: a copy of answers kept close at hand, measured by its **hit ratio**.
- What **Redis** is: an in-memory server with rich **data types**, atomic commands and **expiry**.
- **Cache-aside** (the most common pattern) and its cousins read-through, write-through and write-behind.
- **TTLs**, **invalidation** and the race that bites even when you do it in the right order.
- Failure modes: **stampedes**, a **down cache**, **eviction** when memory runs out, and why the cache is never the **source of truth**.
- How snip caches its redirects, and the other jobs Redis does there.

## A cache keeps recent answers close at hand

:::note[Everyday anchor]
If the database is the library's archive (complete, permanent, carefully catalogued, in the basement), a cache is the librarian's desk: a small pile of the books people asked for recently, within arm's reach. Most requests are answered from the desk. When a book isn't there, the librarian walks down to the archive, and leaves a copy on the desk for the next person.
:::

A cache sits between your program and something slow: a database query, a call to another service, an expensive calculation. When the program needs an answer it asks the cache first.

- The cache has it: a **hit**. Answered in well under a millisecond.
- The cache doesn't: a **miss**. The program asks the slow source, then stores the answer in the cache for next time.

```mermaid
flowchart LR
    A["program"] -->|"1. ask"| C["cache<br/>(fast, small)"]
    C -.->|"2. miss: ask"| S[("source<br/>(slow, complete)")]
```

The number that tells you whether a cache is worth having is the **hit ratio**: hits ÷ all lookups. At 95%, only 1 request in 20 reaches the source. At 30%, you've added a moving part and saved little.

Caches exist at every layer: your browser caches images, a CDN (content delivery network) caches whole pages near the user ([chapter 8.6](../distributed/scaling.mdx)), a program can keep a map in its own memory. This chapter is about a **shared** cache: one server that every copy of your service uses, so an answer fetched by one copy is a hit for all of them. That server is usually Redis.

## Redis: a data structure server in memory

**Redis** is a server ([chapter 1.6](../foundations/what-a-server-is.mdx), default port **6379**) that keeps all its data **in memory**, the fast "countertop" from [chapter 1.1](../foundations/what-a-computer-does.mdx). A typical command takes well under a millisecond, and one Redis server handles on the order of 100,000 simple commands per second.

At its simplest it's a giant **key–value map** ([chapter 4.2](../go/types-structs-errors.mdx)'s map, as a network service):

```text
SET price:tea "3.50"      → OK
GET price:tea             → "3.50"
DEL price:tea             → (integer) 1
```

The `price:` part is a convention, not a feature: a **prefix** that groups related keys, so one Redis can hold several kinds of data without collisions.

Values can also be richer **data types**, each with its own atomic commands:

| Type | Is | Handy commands | Typical use |
|---|---|---|---|
| **String** | text, a number or bytes | `SET`, `GET`, `INCR`, `EXPIRE` | caches, counters |
| **Hash** | a small map of fields | `HSET`, `HGET`, `HINCRBY` | an object, such as a user session |
| **List** | ordered list | `LPUSH`, `RPOP` | simple queues |
| **Set** | unordered, unique members | `SADD`, `SISMEMBER` | "who has seen this?" |
| **Sorted set** | members ordered by a score | `ZADD`, `ZRANGE` | leaderboards, "top 10" |
| **Stream** | an append-only log of entries | `XADD`, `XREADGROUP`, `XACK` | reliable queues ([chapter 8.2](../distributed/queues-and-background-work.mdx)) |

Two properties make Redis special for backends:

- **Every command is atomic.** Redis runs commands one at a time, so `INCR counter` from a thousand clients at once never loses an update: [chapter 6.5](./transactions.mdx)'s lost update, solved by design.
- **Keys can expire.** Give a key a **TTL** (time to live) and Redis deletes it on its own when the time is up. `SET price:tea "3.50" EX 30` lives for 30 seconds.

### Is Redis a database?

Partly. Redis *can* save to disk (periodic snapshots called **RDB**, and an append-only log called **AOF**), but it is memory-first, and depending on configuration a crash can lose the last second or more of writes. When memory fills it may also throw keys away (see eviction, below). So the rule in most systems is: **the database holds the truth; Redis holds copies and short-lived data** that can be lost and rebuilt.

:::info[In the real world]
In 2024 Redis changed its licence away from open source, and the Linux Foundation forked the last open version as **Valkey**, which AWS, Google Cloud and others now offer as managed services. Redis 8 (2025) added an open-source licence option (AGPL) again. For everything in this chapter the two behave the same: same commands, same protocol, same client libraries.
:::

## Cache-aside: check the cache, fall back to the source

The most common caching pattern is **cache-aside** (also called lazy loading). The *application* does all the work: check the cache; on a miss, read the source and fill the cache.

```mermaid
sequenceDiagram
    participant A as App
    participant R as Redis (cache)
    participant S as Source (truth)
    A->>R: GET price:tea
    alt hit
        R-->>A: "3.50"
    else miss
        R-->>A: (nil)
        A->>S: look up tea
        S-->>A: "3.50"
        A->>R: SET price:tea "3.50" EX 30
    end
```

Here it is in Go, from a standalone example in `snip/examples/cacheaside/cacheaside.go`. The "source" is a function that sleeps 300 ms to stand in for a slow query; it knows nothing about any bigger project:

```go
// Get returns the value for key and whether the cache answered.
func (c *Cache) Get(ctx context.Context, key string) (value string, hit bool, err error) {
	v, err := c.Redis.Get(ctx, c.Prefix+key).Result()
	if err == nil {
		return v, true, nil // hit
	}
	cacheBroken := !errors.Is(err, redis.Nil) // redis.Nil is a plain miss; anything else means Redis is unwell

	load := func() (any, error) {
		v, err := c.Source.Get(ctx, key)
		if err == nil && !cacheBroken {
			_ = c.Redis.Set(ctx, c.Prefix+key, v, c.jitteredTTL()).Err() // best effort: a failed fill only costs a future miss
		}
		return v, err
	}
	// … (load runs directly, or through request coalescing: see stampedes below)
}
```

- **`redis.Nil` is not an error.** It's go-redis telling you the key doesn't exist: a miss. Any *other* error means Redis itself is in trouble.
- **A broken cache is treated as a miss.** The answer still comes from the source. A cache should make a system faster, never make it fail.
- **Filling the cache is best effort.** If the `SET` fails, the next request misses again. Nothing is lost, because the cache only ever holds copies.

Run it (the lab shows how) and you see the whole point in three lines:

```text
1. Three reads of the same key
   tea = 3.50   MISS (asked the source)  300.634ms
   tea = 3.50   HIT  (from Redis)        61µs
   tea = 3.50   HIT  (from Redis)        44µs
```

Same answer, thousands of times faster. (Your timings will differ; the gap won't.)

### The other patterns, in one table

| Pattern | Who fills the cache | Writes go | Good for |
|---|---|---|---|
| **Cache-aside** | the app, on a miss | to the source; the app deletes the cached copy | most read-heavy services; the default |
| **Read-through** | the cache library itself, on a miss | to the source | the same idea, hidden behind one `Get` call |
| **Write-through** | the app writes cache *and* source together | both, every time | data read right after it's written |
| **Write-behind** | the cache, which writes to the source later | cache first, source in the background | absorbing write bursts; risks losing writes |

Read-through is cache-aside with the logic moved into a library: the example's `Cache.Get` is exactly that from the caller's point of view. Write-behind makes the cache briefly the only holder of a write, which is why it's rare outside specialised systems.

## The hard part: keeping the cache honest

A cache holds **copies**. The moment the original changes, the copy is wrong, or **stale**. Every cache design answers two questions: how stale is acceptable, and how do we limit it?

### TTL: an upper bound on staleness

Give every entry a TTL. Whatever else goes wrong, a copy can't outlive it. Short TTLs mean fresher data and more load on the source; long TTLs mean the opposite. There's no universally right value: it depends on how often the data changes and how bad a stale answer is. A stale product description for five minutes is fine; a stale account balance is not.

The example adds a little randomness to each TTL:

```go
// jitteredTTL adds up to 10% at random, so keys cached together don't all
// expire together.
func (c *Cache) jitteredTTL() time.Duration {
	if c.TTL <= 0 {
		return 0
	}
	return c.TTL + time.Duration(rand.Int64N(int64(c.TTL)/10+1))
}
```

Without **jitter**, a thousand entries filled in the same second (say, right after a deploy) all expire in the same second, and the source takes a thousand misses at once.

### Invalidation: delete the copy when the truth changes

Waiting for a TTL isn't always acceptable. When the price changes, you want the old price gone now. So the code that changes the data also **invalidates**: it deletes the cached copy, and the next read misses and fetches the new value.

```go
// Put writes the truth first, then deletes the cached copy. The other order
// leaves a gap in which a reader can re-cache the old value.
func (c *Cache) Put(ctx context.Context, key, value string) error {
	c.Source.Put(key, value)
	return c.Redis.Del(ctx, c.Prefix+key).Err()
}
```

**Order matters.** Delete the copy first, and a request arriving between the two steps misses, reads the *old* value from the source, and caches it again, now with a fresh TTL. Change the truth first, then delete the copy.

Why delete instead of writing the new value into the cache? Because two concurrent writers can update the source in one order and the cache in the other, leaving the cache with the older value. Deleting can't go wrong that way: the next reader fetches whatever the source holds.

### Even the right order has a gap

Here's a race that survives "truth first, then delete". A reader is slow; a writer is fast:

```mermaid
sequenceDiagram
    participant R as Slow reader
    participant W as Writer
    participant S as Source
    participant C as Cache
    R->>C: GET → miss
    R->>S: read → old value
    W->>S: write new value
    W->>C: DEL (nothing there yet)
    R->>C: SET old value, for the full TTL
    Note over C: stale until the TTL runs out
```

The reader fetched the old value a moment *before* the write, and stored it a moment *after* the delete. The delete had nothing to remove. The usual defences:

- **Keep TTLs as the backstop.** The stale copy dies eventually. This is often enough.
- **Leave a tombstone.** Instead of deleting, the writer stores a short-lived marker ("just changed"), and readers fill the cache only if the key is empty (`SET … NX`). The slow reader's late fill finds the marker and does nothing. You'll see a real service do exactly this below.
- **Version the values.** Store a version number with each copy and refuse to overwrite a newer version with an older one.

The general lesson: **whenever readers fill a cache and writers invalidate it, ask what happens when a slow read finishes after a fast write.**

:::info[In the real world]
*"There are only two hard things in computer science: cache invalidation and naming things"* is attributed to Phil Karlton. The joke lands because it's true: invalidation is easy with one cache and one writer, and fiendish with many copies, many writers, and messages that arrive out of order. Large systems accept some staleness, bounded by TTLs, rather than chase perfect freshness.
:::

### Two smaller decisions

- **Negative caching.** A lookup for something that *doesn't* exist misses every time, so a bot requesting millions of random keys sails past the cache to the source. Caching "not found" briefly (say 30 seconds) fixes that, at the cost of a new item appearing late.
- **Keys must include everything the answer depends on.** If the price depends on the country, the key is `price:tea:GB`, not `price:tea`. Cache a personalised answer under a shared key and one user sees another user's data: a privacy incident, not a performance bug.

## When caches go wrong

### Cache stampede

A popular key expires. In the next instant, hundreds of requests miss **at the same time**, and every one of them asks the source for the same answer: precisely the load the cache existed to prevent. This is a **cache stampede** (or *thundering herd*).

The fix is **request coalescing**: when many requests miss on the same key at once, one fetches and the rest wait for its answer. In Go, `golang.org/x/sync/singleflight` does exactly that, and the example uses it when `Coalesce` is on:

```go
	var res any
	if c.Coalesce {
		res, err, _ = c.group.Do(key, load) // concurrent misses for the same key wait for one load
	} else {
		res, err = load()
	}
```

The example's last step expires the key and fires 100 concurrent requests, first without coalescing, then with it:

```text
3. Stampede, coalescing=false: 100 concurrent misses sent 100 lookup(s) to the source (320ms)
3. Stampede, coalescing=true: 100 concurrent misses sent 1 lookup(s) to the source (301ms)
```

Same wait for the users, a hundred times less work for the source. Two related fixes: **jittered TTLs** (above) stop many keys expiring together, and **refresh-ahead** renews popular entries shortly *before* they expire. Note that `singleflight` coalesces within **one process**. With twenty copies of a service, up to twenty requests still reach the source; coalescing across copies needs a short lock in Redis itself (a `SET … NX` "I'm fetching this" key).

### A down cache

The example treats a Redis error as a miss, and a test (`TestBrokenCacheIsAMiss`) points it at a port where nothing listens to prove the answers still come back. That keeps the service up when Redis is down. But think about what then happens to the source: if it was sized assuming 95% of reads never reach it, it suddenly gets twenty times its usual load. A cache that the system can't survive without has quietly become a **critical dependency**, and a Redis outage becomes a database outage. Know how your system behaves with an empty or missing cache *before* production teaches you; rate limits, load shedding or a circuit breaker on the fallback path ([chapter 8.4](../distributed/rate-limiting-and-resilience.mdx)) are the usual protection.

### Eviction: a full cache forgets

Memory is finite. Redis's `maxmemory` setting caps it, and `maxmemory-policy` says what happens at the cap:

| Policy | At the memory limit |
|---|---|
| `noeviction` (the default) | refuses new writes with an error |
| `allkeys-lru` | throws away the **least recently used** keys |
| `allkeys-lfu` | throws away the **least frequently used** keys |
| `volatile-lru`, `volatile-ttl`, … | only considers keys that have a TTL |

For a pure cache, `allkeys-lru` or `allkeys-lfu` is the usual choice: forgetting old copies is fine. For a Redis that also holds queues or rate-limit counters, eviction can silently drop data you needed, which is one reason large systems run separate Redis instances for caching and for everything else. Either way, the lesson is the same: **a cache may forget anything at any time**. That's its contract.

:::warning[What can go wrong]
- **No TTL.** Entries live forever, staleness is unbounded, and memory fills up.
- **Forgetting to invalidate** on update or delete. Users see old data until the TTL runs out.
- **Invalidating before writing the source.** A racing request re-caches the old value.
- **Personalised data under a shared key.** One user sees another's data.
- **Every key expiring at once.** A stampede. Jitter TTLs and coalesce misses.
- **Cache as source of truth.** Data lost on restart or eviction. Anything that matters goes to the database.
:::

## Apply it to snip

snip, the link shortener you build in this handbook ([chapter 0.3](../start/meet-snip.mdx)), has one very hot read: every click on a short link asks "where does this slug go?". The answer almost never changes, and a few links get most of the clicks, which is the perfect shape for a cache. snip uses cache-aside in front of Postgres, with Redis as the cache.

### The read path

The business logic is in `snip/internal/links/service.go` (shown with its tracing lines from [chapter 13.3](../observability/tracing.mdx) removed):

```go
// Resolve finds the URL for slug: cache first, then the store (filling the
// cache on the way out). Cache errors are never fatal — a broken cache makes
// snip slower, not broken.
func (s *Service) Resolve(ctx context.Context, slug string) (ResolveResult, error) {
	cacheBroken := false
	if s.cache != nil {
		u, ok, err := s.cache.GetURL(ctx, slug)
		if err != nil {
			cacheBroken = true
		}
		if err == nil && ok {
			return ResolveResult{URL: u, CacheHit: true}, nil
		}
	}
	l, err := s.store.Get(ctx, slug)
	if err != nil {
		return ResolveResult{}, err
	}
	// If the cache just failed, don't wait on it a second time: during an
	// outage every call costs a timeout (chapter 13.5).
	if s.cache != nil && !cacheBroken {
		_ = s.cache.SetURL(ctx, slug, l.URL) // best effort
	}
	return ResolveResult{URL: l.URL}, nil
}
```

Every move from the example is here: hit returns early, a broken cache counts as a miss and is skipped on the way out, the fill is best effort. A few snip-specific details:

- **The cache is optional.** The `Service` only knows a `Cache` interface ([chapter 4.3](../go/packages-modules-interfaces.mdx)). With no `SNIP_REDIS_ADDR` there's no cache at all, and every redirect reads Postgres.
- **Keys are namespaced** `snip:url:<slug>`. The same Redis holds rate-limit counters (`snip:rl:…`) and the click stream (`snip:clicks`).
- **The TTL is `SNIP_CACHE_TTL`**, default **1 hour**. Links never change after they're created, so a long TTL costs almost nothing in freshness.
- **Hits and misses are counted** as `snip_redirects_total{cache="hit|miss"}` ([chapter 13.2](../observability/metrics.mdx)), so the hit ratio is a graph, not a guess.

### Deletes, and the race from earlier

When an owner deletes a link, it must stop redirecting immediately; waiting an hour for the TTL would be unacceptable if the link turned out to point at a phishing page. `Service.Delete` writes the truth first, then invalidates:

```go
func (s *Service) Delete(ctx context.Context, ownerID int64, slug string) error {
	if err := s.store.Delete(ctx, slug, ownerID); err != nil {
		return err
	}
	if s.cache != nil {
		_ = s.cache.Delete(ctx, slug)
	}
	return nil
}
```

For a long time that was all snip did, and it had exactly the slow-reader race from the diagram above: a redirect reads the link from Postgres a moment before the delete, and fills the cache a moment after the eviction, so the deleted link redirects for another hour. A careful review found it. The fix is the **tombstone** defence, in `snip/internal/cache/redis.go`:

```go
// tombstone marks a slug as just deleted. It reads as a miss, and because
// SetURL only fills empty keys, it stops a redirect that looked the link up
// just before the delete from putting it back in the cache just after.
const (
	tombstone    = ""
	tombstoneTTL = time.Minute // far longer than any in-flight lookup
)

// SetURL fills the cache only if the key is empty (SET NX): links never
// change, so there's nothing to overwrite except a tombstone, which must win.
func (c *Redis) SetURL(ctx context.Context, slug, url string) error {
	return c.rdb.SetNX(ctx, key(slug), url, c.ttl).Err()
}

// Delete replaces the entry with a short-lived tombstone rather than just
// removing it (see tombstone above).
func (c *Redis) Delete(ctx context.Context, slug string) error {
	return c.rdb.Set(ctx, key(slug), tombstone, tombstoneTTL).Err()
}
```

`GetURL` treats the empty tombstone value as a miss. The late fill from the slow redirect finds the key occupied and does nothing. "Only fill an empty key" is safe here because snip links never change, so there's never a newer value that `NX` would wrongly refuse. The test `TestLateFillCannotResurrectADeletedLink` (in `redis_test.go`) replays the race: delete, then a late fill, then a lookup, which must miss. It fails on the old code and passes on the new.

### What snip deliberately doesn't do

- **No negative caching.** Unknown slugs go to Postgres every time. The primary-key lookup is cheap, and rate limiting ([chapter 8.4](../distributed/rate-limiting-and-resilience.mdx)) deals with bots guessing slugs.
- **No request coalescing.** A stampede on one viral slug is a burst of identical primary-key lookups, which Postgres answers comfortably at snip's scale. If profiling ever said otherwise, `singleflight` around `store.Get` is a few lines.

### Redis's other jobs in snip

The same Redis does two more jobs, each covered properly later:

- **Rate limiting** ([chapter 8.4](../distributed/rate-limiting-and-resilience.mdx)): a counter per API key per minute, increased with atomic `INCR` and expired with a TTL, shared by every copy of snip, which a counter in one process's memory couldn't be.
- **The click queue** ([chapter 8.2](../distributed/queues-and-background-work.mdx)): each redirect appends an event to the stream `snip:clicks` with `XADD`; a worker reads batches, updates Postgres, and acknowledges them. Redirects stay instant; counting happens in the background.

## Lab

Free, on your own computer, using Docker. Steps 1–2 are standalone; step 3 applies it to snip. Run the Go commands from the `snip/` folder of your copy of the repository.

1. **Talk to Redis directly.**
   ```bash
   docker run -d --name cache-lab -p 6379:6379 redis:7-alpine    # a throwaway Redis
   docker exec -it cache-lab redis-cli                           # its command-line client
   ```
   At the `127.0.0.1:6379>` prompt:
   ```text
   SET price:tea "3.50" EX 30
   GET price:tea
   TTL price:tea               (seconds left: run it again and watch it count down)
   INCR visits                 (1, 2, 3… atomic, however many clients call it)
   ZADD top 910 launch 388 sale 42 docs
   ZREVRANGE top 0 1 WITHSCORES      (the two highest scores)
   CONFIG GET maxmemory-policy       (noeviction: the default)
   KEYS *                      (fine on a laptop; never on a big production Redis, which it would scan whole)
   ```
   Wait 30 seconds and `GET price:tea` again: `(nil)`. It expired by itself. Type `quit` to leave.

2. **Cache a slow function, and cause a stampede.** In a second terminal, watch every command Redis receives:
   ```bash
   docker exec -it cache-lab redis-cli MONITOR
   ```
   In the first terminal:
   ```bash
   cd ~/code/zero-to-prod/snip
   go run ./examples/cacheaside/cmd           # talks to localhost:6379
   ```
   Notice three things. The first read takes about 300 ms and the next two well under 1 ms. After the price changes, `MONITOR` shows a `del` and the next read misses again. And in the stampede, coalescing turns 100 source lookups into 1. Look for the `set … px …` lines in `MONITOR`: the TTL is in milliseconds because the jitter made it a non-round number.

3. **Apply it to snip.** Start Postgres as in [chapter 6.6](./postgres-from-go.mdx)'s lab, then:
   ```bash
   export SNIP_DATABASE_URL="postgres://postgres:learn@localhost:5432/postgres?sslmode=disable"
   export SNIP_REDIS_ADDR=localhost:6379
   go run ./cmd/snip keys create me       # copy the key it prints
   KEY=snip_paste_it_here
   go run ./cmd/snip &                    # the API, now with a cache
   sleep 3
   curl -s -X POST localhost:8080/api/links -H "Authorization: Bearer $KEY" -d '{"url":"https://go.dev","slug":"cached"}' >/dev/null
   for i in 1 2 3; do curl -s -o /dev/null localhost:8080/cached; done   # follow it three times
   curl -s localhost:8080/metrics | grep snip_redirects_total             # 1 miss, 2 hits
   curl -s -X DELETE localhost:8080/api/links/cached -H "Authorization: Bearer $KEY"
   curl -si localhost:8080/cached | head -1                               # 404 immediately
   ```
   In `MONITOR`, the first follow shows a `get` (miss) then `set snip:url:cached https://go.dev ex 3600 nx`; the next two only a `get` (hits); each click also adds an `xadd snip:clicks`. The delete shows `set snip:url:cached "" ex 60`: the tombstone, not a `del`.

   Finally, **kill the cache**: `docker stop cache-lab`, then follow a link that exists. It still redirects (from Postgres, a little slower), and snip logs warnings, not errors. Clean up: `kill %1; docker rm -f cache-lab`.

<details>
<summary>How would you choose a TTL for a cache? Use snip's redirect cache as the example.</summary>

You're trading **freshness** against **load on the source**. Ask how often the data changes, and how bad a stale answer is. A snip redirect never changes after creation, and deletes invalidate immediately (with a tombstone), so the TTL only bounds staleness in rare edge cases, such as a failed eviction. That argues for a **long** TTL: an hour keeps the hit ratio high and Postgres quiet. If snip added link *editing*, stale redirects would become possible after every edit, and you'd want either careful invalidation or a much shorter TTL. Then measure: the hit ratio (`snip_redirects_total`) and the database load tell you whether the choice is working.

</details>

<details>
<summary>The example and snip both ignore cache errors and fall back to the source. Why is that the right choice, and when might it not be?</summary>

Because the cache only exists to **speed things up**: every answer it could give is also in the source. Failing a request because Redis is unavailable would turn an optimisation into an outage. Treating an error as a miss keeps the service working, only slower, while the errors still show up in logs and metrics.

It stops being right when the cache has become **load-bearing**: if the database can't survive full traffic without it, silently falling through during a Redis outage overloads the database and takes it down too. Then the fallback needs protection, such as rate limiting, load shedding or a circuit breaker ([chapter 8.4](../distributed/rate-limiting-and-resilience.mdx)), and the system's capacity plan has to include "cache empty".

</details>
