# 7.6 Secrets management

Every web service needs a password to reach its database, a key to call the payment provider, maybe a token for the email service. Where do those values live? In the code? In a config file? On the server? In Git? Every answer has been tried, and every wrong answer has caused real breaches: keys committed to public repositories and scraped by bots within minutes, passwords baked into container images anyone could download, credentials printed in logs read by a hundred people. **Secrets management** is the discipline of keeping these values where only the right programs can read them, changing them regularly, and knowing what to do the day one leaks. This chapter covers the whole lifecycle, from a `.env` file on your laptop to secret managers and identity-based access in the cloud, and ends by tracing one real password through a real service (snip, the URL shortener this handbook builds) from laptop to production.

## What you'll learn

- What counts as a **secret**, and the places secrets must **never** go.
- **Environment variables** and **`.env` files**: the right way to use them, and their limits.
- **Secret managers** (Vault, cloud secret stores) and **Kubernetes Secrets** — including why "Secret" doesn't mean "encrypted".
- **Rotation**, **least privilege**, and **leak detection** before and after a commit.
- The **leaked-secret playbook**, and **workload identity** — the best secret being no secret at all.
- How one real service (snip) applies all of it, from a throwaway local password to AWS Secrets Manager.

---

## What counts as a secret

A **secret** is any value that grants access or proves identity. A typical web service holds several:

| Secret | What it unlocks |
|---|---|
| The database connection string (it contains the password) | Every row in the database |
| Users' API keys ([chapter 7.2](./authentication.mdx)) | That user's data |
| Token-signing private keys ([chapter 7.3](./oauth-and-oidc.mdx)) | The power to mint valid tokens for anyone |
| Cloud credentials ([chapter 12.4](../cloud/iam.mdx)) | Potentially the whole infrastructure |
| TLS private keys ([chapter 7.1](./security-literacy.mdx)) | Impersonating your site |
| Third-party API keys (email, payments, AI) | Your account — and your bill |

Configuration that *isn't* secret — ports, log levels, feature flags, the site's public URL — can live in plain config. The distinction matters because secrets need special handling and plain config shouldn't be buried in it.

## Where secrets must never go

- **Source code and Git.** Everyone with repository access gets the secret, and **Git keeps it in history forever** ([chapter 3.1](../git/git-mental-model.mdx)), because every commit is a saved snapshot, even after you delete the line. Public repositories are scanned by bots continuously: in published honeypot experiments, AWS keys pushed to public GitHub were found and used within minutes ([Comparitech](https://www.comparitech.com/blog/information-security/github-honeypot/), [Orca Security, 2023](https://orca.security/resources/press-releases/orca-security-2023-honeypotting-in-the-cloud-report/)).
- **Container images.** An `ENV DB_PASSWORD=…` or a copied `.env` file in a Dockerfile ends up in every layer and every registry the image is pushed to ([chapter 9.4](../containers/images-in-production.mdx)). Anyone who can pull the image can unpack every layer.
- **Logs and error messages.** Logs are copied to many systems and read by many people ([chapter 5.4](../apis/structuring-a-real-service.mdx)). Never log full connection strings, tokens or keys.
- **URLs.** Query strings are logged by servers and proxies and saved in browser history ([chapter 7.2](./authentication.mdx)).
- **Chat, tickets and wikis.** Pasting a key into Slack "just this once" copies it into another system's history, search index and backups.
- **The frontend.** Anything shipped to a browser or mobile app is public ([chapter 1.6](../foundations/what-a-server-is.mdx)). Frontend "secret" keys aren't secrets.

:::info[In the real world]
In 2016, attackers got into a private GitHub repository used by Uber engineers, found an AWS access key written in the code, and used it to download data on 57 million riders and drivers from cloud storage. The US Federal Trade Commission's case describes exactly this chain: a credential in code, code in a repository, a repository with too-weak access controls ([FTC, 2018](https://www.ftc.gov/news-events/news/press-releases/2018/04/uber-agrees-expanded-settlement-ftc-related-privacy-security-claims)). A private repository is not a vault.
:::

:::note[Everyday anchor]
A secret is a house key. You don't tape it to the front door (code), post photos of it online (Git), hand a copy to every delivery driver (logs), or leave spares in the car (images). You keep it on your person, give copies only to people who need them, and change the locks the moment one goes missing.
:::

## Environment variables and .env files

An **environment variable** is a named value the operating system hands to a program when it starts ([chapter 2.2](../linux/users-permissions-processes.mdx)). A program that reads its configuration, secrets included, from environment variables has no passwords in its code. That's the **Twelve-Factor** approach (a widely used set of rules for building services), and it's a big improvement over secrets in code: the same build runs everywhere, and each environment supplies its own values at runtime.

```bash
DATABASE_URL='postgres://app:devpass@localhost:5432/app' \
  python3 -c 'import os; print(os.environ["DATABASE_URL"])'   # the program sees the value; its code contains none
```

On your laptop, typing `export DATABASE_URL=…` every time gets old, so developers use a **`.env` file**, which a tool (Docker Compose, `direnv`, or a library such as `dotenv`) loads into the environment for you:

```text
# .env — local development only. NEVER COMMIT THIS FILE.
DATABASE_URL=postgres://app:devpass@localhost:5432/app?sslmode=disable
PAYMENTS_API_KEY=sk_test_not_a_real_key
```

The rules that make this safe:

- **`.env` is in `.gitignore`** ([chapter 3.1](../git/git-mental-model.mdx)) — before the first commit.
- **Commit a `.env.example`** with placeholder values and comments (`DATABASE_URL=postgres://app:CHANGE_ME@…`), so teammates know which variables exist.
- **Development secrets are throwaway.** The password for the database in your local Docker setup can be `devpass`, as long as no real environment ever reuses it.

Environment variables have limits, though. They're visible to anything that can inspect the process (`/proc/<pid>/environ` on Linux, for the same user or root), often dumped by crash reporters and debug pages, and inherited by every child process. For production, they're the **delivery mechanism**, not the **storage**: the real secret lives in a secret manager and is injected at runtime.

## Secret managers

A **secret manager** is a service built to store secrets safely and hand them out to authorised programs:

- Secrets are **encrypted at rest** (with keys managed by a key management service, often backed by hardware).
- Access is governed by **fine-grained permissions** — *this* service may read *this* secret, nothing else.
- Every read is **audited** — who accessed what, when.
- **Versioning** and **rotation** are built in.

Common choices: **HashiCorp Vault** / **OpenBao** (self-hosted or managed), **AWS Secrets Manager** and **SSM Parameter Store**, **Google Secret Manager**, **Azure Key Vault**, **1Password** / **Doppler** / **Infisical** for teams.

```mermaid
flowchart LR
    SM[("Secret manager<br/>encrypted, audited")] -->|"read at startup<br/>(only this app is allowed)"| P["Platform / sidecar /<br/>startup script"]
    P -->|"inject as env var or file"| S["Your app<br/>DATABASE_URL=…"]
    S --> DB[("Database")]
```

The thing to notice: the application usually doesn't even know the secret manager exists. The platform (Kubernetes, the cloud's task runner, a small startup script) fetches the secret and injects it as an environment variable or a file. The app reads `DATABASE_URL`, exactly as it did on your laptop.

You can try a real secret manager locally, for free. HashiCorp Vault has a development mode that runs entirely in memory:

```bash
docker run -d --name vault-lab -e VAULT_DEV_ROOT_TOKEN_ID=lab-root hashicorp/vault:latest   # dev mode: in memory, NOT for real use
sleep 2
v() { docker exec -e VAULT_ADDR=http://127.0.0.1:8200 -e VAULT_TOKEN=lab-root vault-lab vault "$@"; }  # shorthand for the commands below
v kv put secret/app database_url='postgres://app:devpass@db:5432/app'   # store a secret (version 1)
v kv put secret/app database_url='postgres://app:newpass@db:5432/app'   # rotate it (version 2)
v kv get -field=database_url secret/app                                  # the current value
v kv get -version=1 -field=database_url secret/app                       # the old version is kept
docker rm -f vault-lab                                                     # clean up
```

In production the token wouldn't be a fixed `lab-root`: the app's platform identity (see workload identity, below) logs in to Vault and receives a short-lived token that may read only `secret/app`.

## Kubernetes Secrets: not what the name suggests

Kubernetes (a system that runs containers across many machines) has an object called a **Secret** ([chapter 10.4](../kubernetes/config-secrets-storage.mdx)) for handing values like a database URL to containers. But by default, its values are only **Base64-encoded** — which [chapter 1.3](../foundations/bits-bytes-text-formats.mdx) showed is not protection at all. Anyone who can read the Secret object, or the cluster's datastore, can read the value.

To make Kubernetes Secrets genuinely safe:

- Enable **encryption at rest** for the cluster's datastore (managed Kubernetes services offer this, often by default or with a switch).
- Restrict **who can read Secrets** with RBAC ([chapter 10.4](../kubernetes/config-secrets-storage.mdx)) — reading a Secret should be rare and privileged.
- Keep the source of truth in a **secret manager**, and sync it into the cluster with a tool like **External Secrets Operator**, or mount it directly with the **Secrets Store CSI driver**.
- If secrets must live in Git for GitOps ([chapter 11.4](../shipping/gitops.mdx)), store them **encrypted** — with **SOPS** or **Sealed Secrets** — never plain.

## Rotation and least privilege

**Rotation** means replacing secrets regularly, and *immediately* after any suspected exposure. A secret that's never rotated is valid for every copy that's ever been made — in old laptops, backups, former employees' notes. Design for rotation from the start:

- **Support two valid secrets at once** during a change: create the new one, deploy it everywhere, then revoke the old one. A system where each client may hold several API keys allows this naturally: create a new key, switch, revoke the old one.
- **Prefer short-lived credentials**: tokens that expire in minutes or hours ([chapter 7.3](./oauth-and-oidc.mdx)) instead of passwords that last years. Vault and cloud providers can issue **dynamic** database credentials, generated on demand and expired automatically.

**Least privilege** ([chapter 2.2](../linux/users-permissions-processes.mdx)), giving each program only the access it needs, applies to secrets too: an app's database user should have exactly the permissions the app needs on its own tables, not superuser rights on the whole server. If the app's credentials leak, the damage stops there.

## Catching leaks early

People make mistakes; tools catch them:

- **Pre-commit scanning**: tools like **gitleaks** or **trufflehog** scan changes for things that look like secrets (known key formats, high-entropy strings) and block the commit.
- **Push protection and secret scanning**: GitHub scans repositories for known secret formats and can **block pushes** containing them — and partners like cloud providers are notified automatically so they can revoke leaked keys. This is why recognisable prefixes like `ghp_` (GitHub) or `sk_live_` (Stripe) are so valuable ([chapter 7.1](./security-literacy.mdx)).
- **CI scanning** ([chapter 11.2](../shipping/ci-with-github-actions.mdx)) as a second net, and **image scanning** for secrets baked into containers ([chapter 9.4](../containers/images-in-production.mdx)).

## When a secret leaks: the playbook

It will happen eventually. The order matters:

1. **Revoke or rotate the secret first.** Not "delete the commit" — the secret is already out. Make the leaked value useless: revoke the key, change the password, disable the credential.
2. **Deploy the replacement** to everything that needs it.
3. **Investigate**: check audit logs for use of the leaked secret between the leak and the revocation. What was accessed? Was anything changed?
4. **Clean up** the source: remove it from the code, rewrite history if the repository is public (tools: `git filter-repo`, BFG), and ask services where it was pasted to purge it. This comes *after* revocation, because cleanup never reaches every copy.
5. **Learn**: why did it leak, and what check would have caught it? Add that check ([chapter 13.5](../observability/incidents-and-postmortems.mdx)'s postmortems).

:::danger
Deleting a leaked secret from the latest commit does **not** un-leak it. It's in Git history, in every clone, in CI logs, possibly in forks and in scrapers' databases. **Assume it's compromised and revoke it.**
:::

## The best secret is no secret: workload identity

Every stored secret is something that can leak. The modern goal is to have **fewer of them**. Cloud platforms and Kubernetes can give a running program an **identity** directly:

- On AWS, an EC2 instance or Kubernetes pod gets an **IAM role** ([chapter 12.4](../cloud/iam.mdx)); the platform hands the program short-lived credentials automatically, rotated every hour or so. There's no access key to store anywhere.
- CI systems like GitHub Actions can prove their identity to a cloud provider with a signed **OIDC token** ([chapter 7.3](./oauth-and-oidc.mdx)), so deployments need no long-lived cloud keys ([chapter 11.2](../shipping/ci-with-github-actions.mdx)).
- Databases increasingly accept these identities too (for example, IAM authentication for AWS RDS).

When a credential is short-lived, automatically issued and tied to *which program is running where*, there's nothing long-lived to steal. That's where modern secrets management is heading.

## Apply it to snip: one password, laptop to production

snip, the URL shortener this handbook builds, needs exactly the secrets above: a Postgres connection string (`SNIP_DATABASE_URL`, password inside), a Redis password (`SNIP_REDIS_PASSWORD`) and its users' API keys. Here is each idea from this chapter in its real files.

**Configuration from the environment.** snip reads every setting from `SNIP_*` environment variables ([chapter 5.4](../apis/structuring-a-real-service.mdx)), so no password is in its Go code.

**Throwaway development secrets, labelled as such.** From `snip/docker-compose.yml`:

```yaml
      POSTGRES_PASSWORD: snip          # local development only — never a real password
```

**A password even on the cache.** Redis answers anyone who can connect unless you give it a password, and snip's Redis holds where every short link points. Anything that could reach it on the network could repoint a popular link to a phishing page without touching the database or the API. So every snip deployment starts Redis with a password (`--requirepass`) and snip sends it as `SNIP_REDIS_PASSWORD`; empty means "no password", which keeps throwaway lab containers working. In the cloud the connection is also encrypted (`SNIP_REDIS_TLS=true`), so the password never crosses the network in plain text ([chapter 12.8](../cloud/cloud-security.mdx)). In `snip/docker-compose.yml` it's another labelled development value:

```yaml
      SNIP_REDIS_PASSWORD: ${SNIP_REDIS_PASSWORD:-snip-dev-only}  # local development only
```

**An example file instead of a real one.** `snip/deploy/systemd/snip.env.example` documents every variable for a server install, with a placeholder where the password goes:

```text
# /etc/snip/snip.env — read by snip.service. Never commit the real file.
SNIP_DATABASE_URL=postgres://snip:CHANGE_ME@localhost:5432/snip?sslmode=disable
SNIP_REDIS_PASSWORD=CHANGE_ME
```

**Secret and plain config, split.** For Kubernetes, `snip/deploy/k8s/base/config.yaml` puts the Redis address and log level in a ConfigMap (plain settings), and only the connection string and the Redis password in Secrets, with obviously fake `snip-dev-only` passwords for a local cluster.

**A secret manager in production, readable by one role.** On AWS, `snip/infra/aws/main.tf` stores the connection string and Redis's token in Secrets Manager (`aws_secretsmanager_secret.db_url` and `.redis_auth`), and `snip/infra/aws/compute.tf` lets the container platform read exactly those two secrets and inject them as environment variables:

```hcl
data "aws_iam_policy_document" "read_secrets" {
  statement {
    actions = ["secretsmanager:GetSecretValue"]
    resources = [
      aws_secretsmanager_secret.db_url.arn,
      aws_secretsmanager_secret.redis_auth.arn,
    ]
  }
}

# …and in the task definition's locals:
  snip_secrets = [
    { name = "SNIP_DATABASE_URL", valueFrom = aws_secretsmanager_secret.db_url.arn },
    { name = "SNIP_REDIS_PASSWORD", valueFrom = aws_secretsmanager_secret.redis_auth.arn },
  ]
```

snip's code is identical on your laptop and in the cloud: it reads `SNIP_DATABASE_URL` and `SNIP_REDIS_PASSWORD` both times. That's the secret-manager diagram above, in real files.

**No stored deploy key.** `snip/infra/aws/iam-github.tf` lets GitHub Actions deploy with a short-lived OIDC token instead of a stored AWS access key, and only from the `main` branch of one repository ([chapter 12.4](../cloud/iam.mdx)): workload identity, applied.

**User API keys designed for leaks.** snip's keys start with `snip_` so scanners can spot them, are stored only as hashes, and can be revoked instantly with `snip keys revoke` ([chapter 7.2](./authentication.mdx)). When a key leaks but its owner still needs access, `snip keys rotate` issues a new key for the same owner and stops the old one in the same instant, so the owner keeps their links ([chapter 13.7](../observability/security-incident-response.mdx) runs it in a drill). snip has one key per owner, so there's no overlap: the integration fails until it's given the new key. Services that need rotation without downtime allow two active keys per owner for a while.

:::warning[What can go wrong]
- **Secrets in Git**, including "temporarily". History is forever.
- **Secrets in images or logs.** Copied everywhere, readable by many.
- **Treating Base64 or Kubernetes Secrets as encryption.** They're not, by default.
- **Shared, never-rotated credentials.** One password used by every service for years: impossible to revoke without breaking everything, and impossible to know who used it.
- **"Delete the commit" as the leak response.** Revoke first, always.
- **Over-privileged credentials.** A leaked read-only key is an incident; a leaked admin key is a disaster.
:::

## Lab

Free, on your own computer. All secrets below are fake.

:::danger
The last command deletes the practice directory with `rm -rf`, which asks no questions and has no undo. Check the path is exactly `~/leak-lab` before you press Enter.
:::

1. **Prove that Git history keeps secrets.**
   ```bash
   mkdir -p ~/leak-lab && cd ~/leak-lab && git init -q
   echo 'DATABASE_URL=postgres://app:hunter2@db.internal:5432/app' > .env
   git add .env && git commit -qm "Add config"            # the mistake
   git rm -q --cached .env && echo ".env" > .gitignore
   git add .gitignore && git commit -qm "Remove .env, add gitignore"
   ls -a                                                   # .env is still on disk, just untracked
   git log -p --all | grep hunter2                         # still in history!
   ```
   Anyone who clones this repository — now or in five years — can read `hunter2`.

2. **Scan for secrets** with gitleaks (via Docker — nothing to install):
   ```bash
   docker run --rm -v "$PWD:/repo" zricethezav/gitleaks:latest git /repo -v
   ```
   It scans the whole history and reports the leaked connection string, the commit and the line. (If it reports nothing for this made-up value, try a realistic-looking fake: gitleaks recognises specific key formats such as AWS or GitHub tokens.) Many teams run it as a pre-commit hook and in CI.

3. **See how visible environment variables are** (Linux or WSL):
   ```bash
   SECRET_TOKEN=not-really-secret sleep 300 &
   cat /proc/$!/environ | tr '\0' '\n' | grep SECRET      # the variable, readable from outside the process
   kill %1
   cd ~ && rm -rf ~/leak-lab
   ```
   Environment variables are a delivery mechanism, not a vault.

4. **Apply it to snip: read its approach.** Open `snip/deploy/systemd/snip.env.example`, `snip/docker-compose.yml` and `snip/infra/aws/compute.tf`. Find: the placeholder passwords, the comments marking the development passwords as throwaway, and the two secrets the production task may read. Then run `git log -p -- snip/ | grep -i password` in the repository: only placeholders and development values, never a real secret.

<details>
<summary>Design how snip's production database password should be stored, delivered and rotated.</summary>

- **Stored** in a secret manager (for example, AWS Secrets Manager), encrypted and audited — the only source of truth.
- **Delivered** at runtime: the platform (External Secrets Operator into a Kubernetes Secret, or the cloud's task runner) injects it as `SNIP_DATABASE_URL`; nothing in Git, images or logs.
- **Least privilege**: a dedicated database user with rights only on snip's tables.
- **Rotation**: support two valid passwords during a switch — create the new one, update the secret, roll snip's pods ([chapter 10.2](../kubernetes/core-objects.mdx)) so they pick it up, then revoke the old one. Better still, use short-lived, automatically issued database credentials (Vault dynamic secrets or IAM database authentication), so there's no long-lived password at all.
- **Detection**: secret scanning on every push and in CI, alerts on unusual database access.

</details>

<details>
<summary>Why are recognisable prefixes like <code>snip_</code> or <code>ghp_</code> on keys a security feature?</summary>

Because leak detection works by **pattern matching**. A random 32-character string is hard to distinguish from other random text, so scanners either miss it or raise too many false alarms. A distinctive prefix with a fixed format lets GitHub's secret scanning, gitleaks and similar tools **reliably spot** the key in commits, logs or pastes — and, through partner programmes, notify the issuer so the key can be revoked automatically, sometimes within seconds of being pushed.

</details>
