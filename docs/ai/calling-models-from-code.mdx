# 14.4 Calling models from code

You've typed a question into a chat window and watched an answer appear. That's a demo. A product calls models **from code**: thousands of times a day, with nobody watching, with money leaving your account on every call, and with all the ways a network request can fail. This chapter turns the ideas of [chapter 14.3](./how-llms-work.mdx) (a model predicts text one **token**, a word-piece, at a time) into software: what you send, what comes back, what it costs, and how to keep a slow, fallible, paid call from hurting the rest of your system.

Everything here runs **free** if you want it to: you'll call a real open model on your own machine at no cost, and a hosted model (Claude) only if you choose to use your own key. At the end you'll apply it to snip, by building its first AI feature.

## What you'll learn

- What a model **API request** and **response** contain: an order slip and a tray with a receipt.
- Handling **API keys** safely, and what the provider's **SDK** does for you.
- **Streaming**, **tokens**, **thinking** and **cost**: how to estimate a feature's bill before shipping it.
- **Timeouts, retries and rate limits**, and how to **choose a model**.
- Where a model call **belongs** in a system: never in the hot path.
- Applied to snip: one interface for fake, local and hosted models, and fetching user-supplied URLs **safely** (SSRF).

---

## A model API is an HTTP request

:::note[Everyday anchor]
Ordering at a restaurant counter. You hand over an order slip (what you want, how much of it), the kitchen works on it, and you get back a tray with the food and a receipt showing exactly what you're paying for. The kitchen doesn't remember you: next time, you hand over a whole new slip.
:::

Behind every chat app is an HTTP API ([chapter 1.5](../foundations/http-from-zero.mdx): a request with a method, headers and a body; a response with a status and a body). Here's a real request to Anthropic's **Messages API**, as a `curl` command:

```bash
curl https://api.anthropic.com/v1/messages \
  -H "Authorization: Bearer $ANTHROPIC_API_KEY" \
  -H "anthropic-version: 2026-10-21" \
  -H "content-type: application/json" \
  -d '{
    "model": "claude-haiku-5-5",
    "max_tokens": 1024,
    "system": "You write short, factual descriptions of web pages.",
    "messages": [{"role": "user", "content": "Describe https://go.dev in one sentence."}]
  }'
```

The **order slip** has four parts:

- **`model`**: which model to use, by its exact identifier, like `claude-haiku-5-5`. Production code pins a specific one, so the model can't change underneath you.
- **`max_tokens`**: the most output tokens you'll accept (and pay for). The model stops there, even mid-sentence.
- **`system`**: the **system prompt** ([chapter 14.3](./how-llms-work.mdx)): the application's instructions and context.
- **`messages`**: the conversation so far, as a list of turns with **roles** (`user` and `assistant`). For one question, it's one user message.

The **tray and receipt** come back as JSON (trimmed):

```json
{
  "model": "claude-haiku-5-5",
  "content": [
    {"type": "thinking", "thinking": "", "signature": "EqQBCkYI..."},
    {"type": "text", "text": "The official website of Go, an open-source programming language..."}
  ],
  "stop_reason": "end_turn",
  "usage": {"input_tokens": 31, "output_tokens": 64}
}
```

- **`content`** is a **list of blocks**, not a string. Current Claude models **think** before answering: they may produce `thinking` blocks first (the reasoning itself is hidden by default, so the text is empty), then the `text` block with the answer. Later you'll meet tool-call blocks too ([chapter 14.6](./structured-output-and-tools.mdx)). So code picks out the `text` blocks by type, never "the first block".
- **`stop_reason`** says **why** it stopped: `end_turn` (finished), `max_tokens` (cut off: your answer is incomplete), `refusal` (the model declined for safety reasons), and others you'll meet later. **Always check it.**
- **`usage`** is the receipt: tokens in and out, which is what you're billed for. Thinking tokens are **output** tokens: they count toward `max_tokens` and the bill.

The API is **stateless**: the kitchen doesn't remember you. To continue a conversation, you send the whole history again, every time. That's why long conversations get more expensive with every turn.

Every provider's API has this same shape. OpenAI, Google and open-model servers name the fields slightly differently, but it's always: model, limits, instructions, messages in; content, stop reason, usage out.

## API keys: a password that spends money

The `Authorization` header carries your **API key** (older code sends it in an `x-api-key` header, which the API still accepts; `anthropic-version` picks which version of the API's rules the request follows): a long secret that identifies your account and lets anyone holding it **spend your money**. Everything from [chapter 7.6](../security/secrets-management.mdx) (secrets live outside code, in the environment or a secret manager) applies, with extra urgency:

- Keep it in an **environment variable** (`ANTHROPIC_API_KEY`) or a secret manager, **never in code**. Automated bots scan public GitHub for leaked keys within minutes of a push.
- Use **separate keys** per environment and per application, so one leak can be revoked without breaking everything.
- Set a **monthly spending limit** in the provider's console before you write any code. It turns a leaked key or a bug in a loop from a disaster into an annoyance.
- **Never put your key in a browser or mobile app.** Anyone can read it there. Calls go through your server, which holds the key. (One different pattern is **bring your own key**: each user pastes *their own* key, which stays in their own browser and pays for their own usage. This site's Ask panel works that way, which is reasonable for a free learning tool, since users can only ever expose their own account. A product serving the public should still route calls through its server.)

## The official SDK: the same request, with the chores done

You could build that HTTP request yourself with `httpx` ([chapter 14.1](./python-for-ai-engineers.mdx)). Instead, use the provider's **SDK** (software development kit), its official client library (`uv add anthropic`). It builds the same request, but also retries temporary failures, raises typed errors, and handles streaming. A complete program that summarises a text file:

```python title="summarize.py"
"""Summarise a text file in one sentence, with Claude."""

import sys

import anthropic

client = anthropic.Anthropic()  # reads ANTHROPIC_API_KEY from the environment

with open(sys.argv[1]) as f:
    text = f.read()

response = client.messages.create(
    model="claude-haiku-5-5",  # an exact model name, never "latest"
    max_tokens=1024,  # the most output tokens you'll pay for, thinking included
    output_config={"effort": "low"},  # think briefly: this is an easy job
    system="You summarise text in one plain sentence.",
    messages=[{"role": "user", "content": text}],
)

for block in response.content:  # a list of blocks: pick out the text ones
    if block.type == "text":
        print(block.text)
print(response.stop_reason, response.usage.input_tokens, response.usage.output_tokens)
```

Two parameters deserve a word:

- **`effort`** (inside `output_config`) sets how much the model thinks before answering: `low`, `medium`, `high`, `xhigh` or `max`. More effort helps hard problems and costs more output tokens and time. A one-sentence summary is easy, so `low`.
- **`max_tokens=1024`** looks generous for one sentence. It's sized for the sentence *plus* any thinking: set it too tight and the thinking uses it up, and you get `stop_reason: "max_tokens"` with no answer at all.

Notice what *isn't* there: **temperature**. [Chapter 14.3](./how-llms-work.mdx) explained it (how random the next-token choice is), and older APIs accepted it. Current Claude models set sampling themselves and reject non-default values, and current versions of the Python SDK no longer send the parameter at all. That's a small example of a general rule: **check the provider's documentation for the exact model you use**, because model APIs change quickly. (Open models you run yourself still take a temperature; [chapter 14.11](./serving-open-models.mdx) uses it.)

### The same call, free, on your own machine

**Ollama** runs open models on your laptop and exposes them through an HTTP API of the same shape ([chapter 14.11](./serving-open-models.mdx) explains how it works). After installing it from [ollama.com](https://ollama.com/download):

```bash
ollama pull qwen2.5:0.5b              # a small open model, about 400 MB
curl http://localhost:11434/api/chat -d '{
  "model": "qwen2.5:0.5b",
  "stream": false,
  "messages": [{"role": "user", "content": "Describe https://go.dev in one sentence."}]
}'
```

The JSON that comes back has the same ingredients under different names: `message.content` for the answer, `done_reason` for why it stopped, `prompt_eval_count` and `eval_count` for tokens in and out. It costs nothing, nothing leaves your machine, and the answers from a model this small are noticeably worse. That trade-off is the theme of this whole part.

## Streaming: show the answer as it's written

Models generate one token at a time, so a 300-word answer can take several seconds to finish. **Streaming** delivers it piece by piece, as it's generated, so a person sees text start appearing in under a second. The SDK makes it a loop:

```python
import anthropic

client = anthropic.Anthropic()

with client.messages.stream(
    model="claude-haiku-5-5",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Explain DNS in three short paragraphs."}],
) as stream:
    for piece in stream.text_stream:  # a few tokens at a time, as they're generated
        print(piece, end="", flush=True)
print()
```

Under the hood, the server sends **server-sent events**: a long-lived HTTP response that delivers small chunks (`content_block_delta` events, each carrying a few tokens) as they're ready. Use streaming when **a person is waiting** for a long answer. For background work, plain complete-and-return is simpler.

## Tokens are money and time

Every call reports its tokens, and the price is public: dollars per million tokens, with output costing more than input. At the time of writing, Anthropic's current models cost:

| Model | Input, per million tokens | Output, per million tokens |
|---|---|---|
| Claude Haiku 5.5 (`claude-haiku-5-5`) | $0.10 (prompts up to 100K tokens) | $0.50 |
| Claude Sonnet 5.5 (`claude-sonnet-5-5`) | $2 | $10 |
| Claude Opus 5.5 (`claude-opus-5-5`) | $4 | $20 |
| Claude Fable 5.1 (`claude-fable-5-1`) | $10 | $50 |

Prices change; check the provider's [pricing page](https://platform.claude.com/docs/en/about-claude/pricing) before relying on them. The habit that matters is the **back-of-the-envelope estimate**, done before you ship. Say a feature sends about 1,100 input tokens (roughly 4,000 characters of text plus instructions) and gets back about 30 output tokens:

- With Haiku 5.5: 1,100 × $0.10 + 30 × $0.50, per million, is about **$0.000125 per call**, or **$125 per million calls**.
- With Sonnet 5.5: 1,100 × $2 + 30 × $10, per million, is **$0.0025 per call**: 20 times as much, **$2,500 per million calls**.

Then add **thinking**: those tokens are output, invisible in the answer but on the receipt. That's why you *measure* the real `usage` on a sample of real inputs before trusting any estimate.

Time matters as much as money. Input tokens are processed all at once, but output tokens come one at a time, so **long outputs (and long thinking) are slow**, and a call can easily take one to several seconds.

### Where a model call belongs

That leads to the most important design decision of this chapter. **Never put a model call in the hot path** of a request that has to be fast. A model call takes seconds, fails sometimes, and costs money every time. If your checkout page waits on a model to write a "thanks for your order" message, a slow model makes checkout slow, and a model outage breaks checkout.

The pattern that works: do the model call **once**, in the **background**, and store the result. The request that needs to be fast puts a job on a queue ([chapter 8.2](../distributed/queues-and-background-work.mdx): a list of work items that a separate worker process takes one at a time); a worker calls the model and saves the answer; the page shows it when it's ready. If the model is slow, down or out of budget, the core feature still works, just without the AI extra. That's **graceful degradation** ([chapter 13.5](../observability/incidents-and-postmortems.mdx)), designed in from the start.

## When calls fail

Model APIs fail in all the ways networked services do ([chapter 8.1](../distributed/distributed-survival-kit.mdx): slow answers, dropped connections, overloaded servers), plus a few of their own:

| Error | Means | What to do |
|---|---|---|
| **400** bad request | Your request is invalid (unknown parameter, a setting this model doesn't accept, too many tokens) | Fix the code; retrying won't help |
| **401 / 403** | Wrong, revoked or unauthorised key | Fix the configuration; alert someone |
| **404** | Unknown model name (often a typo, or a retired model) | Fix the model name |
| **429** rate limited | Too many requests or tokens per minute for your account | Wait and retry (the response says how long); smooth out bursts; ask for higher limits |
| **500 / 529** | The provider's servers are failing or overloaded | Retry with backoff; consider a fallback model |
| Timeout | No answer in time | Retry once; check your timeout suits the output length |
| `stop_reason: max_tokens` | The answer was cut off (perhaps by thinking) | Raise `max_tokens`, lower `effort`, or ask for shorter answers |
| `stop_reason: refusal` | The model declined for safety reasons | Don't retry blindly; show a sensible message |

The SDK already **retries** 429s, 5xx errors and dropped connections (twice by default, with exponential backoff), and raises **typed exceptions** you can catch precisely (`anthropic.RateLimitError`, `anthropic.AuthenticationError`, and so on). Two things it can't decide for you:

- **The timeout.** The SDK's default is 10 minutes, sensible for very long answers, far too long for anything a person is waiting on. Set your own: `anthropic.Anthropic(timeout=60.0)`.
- **Your budget of retries across the whole system.** Every retry of a model call is paid for again. Wrap retries with limits, and watch the cost ([chapter 14.13](./ai-in-production.mdx)).

## Choosing a model

Providers offer a ladder: small, fast, cheap models, and large, slower, more capable ones. As of this writing, Anthropic's runs from Claude Haiku 5.5 (the smallest and cheapest) through Claude Sonnet 5.5 (fast and capable, for everyday work) and Claude Opus 5.5 (more capable again) to Claude Fable 5.1 (the most capable, for the hardest reasoning and long-running agent work). Every other provider has a similar ladder, and open models ([chapter 14.11](./serving-open-models.mdx)) add a free-to-run option with more work.

The approach that works: **start with the smallest model that could plausibly do the job, measure whether it does, and move up only if it doesn't.** "Measure" means evals ([chapter 14.10](./evals.mdx)), not a gut feeling from three tries. On newer models, also try a *lower effort* before a bigger model: it's often enough. A one-sentence summary of a web page is a simple job, so it gets the smallest model. A complex coding agent does not. And **pin the exact model name** in configuration, so an upgrade is a deliberate, tested change.

## Apply it to snip: describing where a link goes

snip is the URL shortener you build through this handbook: `https://snip.example/x7Kp2` redirects to some long URL. A short link hides where it goes, which is exactly why people hesitate to click one. So snip's first AI feature is: **before someone clicks, show a one-line description of the destination.** It needs everything above: ask a model, check what comes back, know what it cost, keep it off the hot path. And one thing more, because the page comes from a user-supplied URL: fetch it safely.

The code is in **snipai** (`ai/`), the Python project from [chapter 14.1](./python-for-ai-engineers.mdx).

### One interface, three providers

snipai never calls a provider directly from feature code. Every provider fits one small interface, a Python **Protocol** (like a Go interface, [chapter 4.3](../go/packages-modules-interfaces.mdx): any class with these methods qualifies), in `ai/src/snipai/llm.py`:

```python
class LLM(Protocol):
    name: str
    model: str

    def complete(self, prompt: str, *, system: str | None = None, max_tokens: int = 500) -> Completion: ...
    def stream(self, prompt: str, *, system: str | None = None, max_tokens: int = 500) -> Iterator[str]: ...
```

(Simplified: the real Protocol adds a `schema` parameter and a `chat` method, both from [chapter 14.6](./structured-output-and-tools.mdx).) Three things fit it, chosen with the `SNIPAI_PROVIDER` environment variable:

| Provider | Costs | Needs | Good for |
|---|---|---|---|
| **`fake`** (default) | Nothing | Nothing | Tests, CI, first steps, working offline. It "answers" by extracting the first sentence of the text you gave it: dumb, but **deterministic** |
| **`ollama`** | Nothing (your electricity) | Ollama and a downloaded model | Learning, privacy (nothing leaves your machine), development without a bill |
| **`anthropic`** | A fraction of a cent per call | An API key | Real quality |

The Claude provider is `summarize.py`'s call, wrapped:

```python
class AnthropicLLM:
    def __init__(self, model: str = "claude-haiku-5-5", *, effort: str | None = "low",
                 client: anthropic.Anthropic | None = None) -> None:
        self.model = model
        self.effort = effort
        self._client = client or anthropic.Anthropic(
            timeout=60.0,  # the SDK default is 10 minutes: far too long for a web request
            max_retries=2,  # retries 429s, 5xx and connection errors, with backoff
        )

    def complete(self, prompt: str, *, system: str | None = None, max_tokens: int = 500,
                 schema: dict[str, Any] | None = None) -> Completion:
        start = time.perf_counter()
        response = self._client.messages.create(
            model=self.model,
            max_tokens=max_tokens,
            system=system or anthropic.omit,
            messages=[{"role": "user", "content": prompt}],
            output_config=self._output_config(schema),
        )
        # The answer is a list of content blocks; we want the text ones.
        text = "".join(block.text for block in response.content if block.type == "text")
        return Completion(
            text=text,
            model=response.model,
            input_tokens=response.usage.input_tokens,
            output_tokens=response.usage.output_tokens,
            stop_reason=response.stop_reason or "",
            seconds=time.perf_counter() - start,
        )
```

`_output_config` sends `{"effort": "low"}`, plus a JSON schema when one is given ([chapter 14.6](./structured-output-and-tools.mdx)). `effort=None` sends nothing, for older models such as `claude-haiku-4-5` that reject the setting.

This is the same pattern as snip's `Store` interface with its memory and Postgres implementations ([chapter 4.3](../go/packages-modules-interfaces.mdx)), and it pays off the same way. Tests run in milliseconds with no network and no key. Every contributor can run everything for free. And switching models, or providers, is a configuration change, not a rewrite.

The tests go one step further for the Claude provider: they hand the real SDK a **mock HTTP transport** (the [chapter 14.1](./python-for-ai-engineers.mdx) trick) that plays the part of Anthropic's server, so they check the exact request snipai sends (path, key header, model, effort, messages) and that it reads the response correctly, including a thinking block, streaming and a rate-limit error, all without a key (`ai/tests/test_llm.py`). What they can't prove is how good Claude's *answers* are. That's what evals are for ([chapter 14.10](./evals.mdx)).

snipai also keeps the price table from "Tokens are money and time" (`PRICES_PER_MTOK` in `llm.py`) and prints the cost of every call.

### The prompt, and the code that distrusts its answer

The feature itself, `ai/src/snipai/describe.py`, is short. The interesting part is the prompt. This is its first version, which the code keeps as `PROMPTS["v1"]`; [chapter 14.5](./prompt-engineering.mdx) improves it, and the default today is v3. The code around it is the same for every version:

```python
SYSTEM = "You write short, factual descriptions of web pages for a link shortener."

PROMPT = """Describe the web page below in one sentence of at most 25 words, for someone
deciding whether to open a link to it. Use only information in the page text.
If the text doesn't make clear what the page is about, reply with exactly: UNKNOWN

TITLE: {title}

THE PAGE'S OWN SUMMARY: {summary}

TEXT: {text}"""
```

The **summary** is the page's own `<meta name="description">`, a sentence most websites write for search engines: free, high-quality context. The code around the prompt treats the answer with suspicion:

```python
def describe(page: Page, llm: LLM, version: str = DEFAULT_PROMPT) -> Description:
    system, prompt = render(page, version)
    # Room for the ~35-token sentence, plus any thinking a hosted model does first.
    completion = llm.complete(prompt, system=system, max_tokens=300)
    text = completion.text.strip()
    if text == "UNKNOWN" or completion.truncated:
        text = ""  # better no description than a wrong or half-finished one
    return Description(page=page, text=text, completion=completion)
```

Three design choices worth copying:

- **"Use only information in the page text"** narrows the model's job to summarising what's in front of it. That's safer than asking it what it knows about a website, which invites **hallucination** (confident, invented facts, [chapter 14.3](./how-llms-work.mdx)).
- **An explicit escape hatch** (`UNKNOWN`). Without one, a model given a login page or an empty page will invent something plausible. With one, it has an honest answer available, and the code turns it into "no description".
- **A truncated answer is thrown away.** If `stop_reason` is `max_tokens`, the sentence is incomplete. Showing half a sentence is worse than showing nothing.

### What a real (tiny) model actually said

snip's CI runs this feature against real websites with a small open model, `qwen2.5:0.5b` (half a billion parameters, about 400 MB), through Ollama on an ordinary CPU. Here's one of the first runs, unedited:

```text
provider: ollama, model: qwen2.5:0.5b

https://go.dev/
  title: The Go Programming Language
  description: (none)
  94 tokens in, 2 out, 1.55s, stop: end_turn, cost ≈ $0.00000

https://www.python.org/
  title: Welcome to Python.org
  description: The web page is about Python.org, a link shortener, providing information about the website, its features, and how to access it.
  674 tokens in, 29 out, 5.08s, stop: end_turn, cost ≈ $0.00000
```

Three lessons in six lines:

1. **The escape hatch worked.** For go.dev, only 94 tokens went in: the page text was almost empty (more on why below). With nothing to go on, the model answered `UNKNOWN`, and the code turned that into "no description". Without the escape hatch, it would almost certainly have made something up.
2. **The python.org answer is a hallucination, and we caused it.** Python.org is not "a link shortener". The model borrowed that phrase from our own system prompt ("descriptions of web pages **for a link shortener**") and stated it as a fact about the page. Tiny models are especially prone to this, but every model can blur the task's context into its answer. Prompt wording matters: [chapter 14.5](./prompt-engineering.mdx) rewrites this prompt and measures the difference. And the only way to find problems like this at scale is to measure systematically ([chapter 14.10](./evals.mdx)).
3. **Small and local is slow and cheap.** Five seconds for 29 words on a CPU, and it cost nothing. A hosted model answers in about a second, for a small fraction of a cent.

:::warning[What can go wrong: garbage in]
Why was go.dev's text almost empty? Our first text extractor skipped a list of tags that "aren't content" (navigation, headers, footers), counting opening and closing tags. On real pages, that heuristic threw away nearly everything. We couldn't fetch go.dev from the development machine to check, so instead of guessing, we made extraction robust: prefer the page's `<main>` element, where most sites put their content; skip only tags that are never visible and always closed (`<script>`, `<style>`, `<svg>`...); and read the page's own `<meta name="description">`. The command now prints how much text it extracted, and how it starts. **Most bad model outputs start with bad inputs**, so always look at exactly what the model was given before blaming the model.
:::

After the fix, the same tiny model, on the next CI run:

```text
https://go.dev/
  title: The Go Programming Language
  page text: 4000 characters, starting 'Build simple, secure, scalable systems with Go An open-source programm'
  description: The Go programming language is an open-source programming language designed to make it simple to build secure, scalable systems.
  919 tokens in, 23 out, 8.53s, stop: end_turn, cost ≈ $0.00000

https://www.python.org/
  title: Welcome to Python.org
  page text: 4000 characters, starting 'Notice: This page displays a fallback because interactive scripts did '
  description: Welcome to Python.org, the official home of the Python Programming Language. The site offers interactive scripts that did not run, but its content is reliable and up-to-date.
  1040 tokens in, 35 out, 8.55s, stop: end_turn, cost ≈ $0.00000
```

go.dev is now described well. Python.org shows two new problems: the answer is **two sentences** (the prompt asked for one), and the second sentence is invented from the page's "no JavaScript" notice, plus a claim nobody made ("reliable and up-to-date"). Better input fixed one failure and exposed others. [Chapter 14.5](./prompt-engineering.mdx) takes this prompt apart and measures a better one.

### Fetching pages safely

To describe a page, snipai must **download it from the server**, and the URL comes from a user. [Chapter 7.5](../security/web-attacks.mdx) described exactly this feature as an **SSRF** risk (server-side request forgery: tricking a server into fetching an address the attacker can't reach themselves). A user shortens `http://169.254.169.254/latest/meta-data/`, and your server obligingly fetches the cloud's metadata service, which hands out the server's credentials ([chapter 12.4](../cloud/iam.mdx)). `ai/src/snipai/pages.py` follows [chapter 7.5](../security/web-attacks.mdx)'s defences:

```python
def is_public_host(host: str) -> bool:
    """True if every address `host` resolves to is a public internet address."""
    try:
        infos = socket.getaddrinfo(host, None)
    except socket.gaierror:
        return False
    for info in infos:
        ip = ipaddress.ip_address(info[4][0])
        if not ip.is_global:  # private, loopback, link-local (metadata!), reserved...
            return False
    return True
```

It allows only `http` and `https`, **follows redirects itself** so it can check **every hop** (a public page that redirects to `169.254.169.254` is the classic bypass), stops after 1 MB and 10 seconds, and keeps only the first 4,000 characters of visible text (which also caps the cost of the model call). A test proves the redirect trick is refused.

```text
http://169.254.169.254/latest/meta-data/
  skipped: refusing to fetch a non-public address: 169.254.169.254
```

:::warning[What can go wrong]
Checking the address and then connecting are two separate steps, and a determined attacker can exploit the gap. With **DNS rebinding**, their domain answers "a public address" when you check and "127.0.0.1" a moment later when you connect. Production systems close the gap by connecting to the exact IP they checked, or, better, by running the fetcher as a **separate, locked-down service** whose network can only reach the internet ([chapter 7.5](../security/web-attacks.mdx)'s second defence). snipai's checks are a real first layer, not the last one.
:::

### Where the call goes in snip

snip's redirect must take milliseconds (its SLO, the target it promises, is 250 ms, [chapter 13.4](../observability/slos-alerting-on-call.mdx)). So the description is generated **once, when the link is created, in the background**: the same pattern as snip's click worker ([chapter 8.2](../distributed/queues-and-background-work.mdx)). Create the link, queue a "describe this link" job, a worker fetches the page and calls the model, stores the result, and the link page shows it when it's ready. If the model is slow, down or out of budget, links still work; they just don't have descriptions yet.

With Haiku 5.5, the estimate from earlier (about 1,100 tokens in, 30 out) is roughly $125 per million links, before thinking tokens. Cheap, but worth knowing before you ship.

:::info[Honesty label]
**Exists today:** the description feature as a command-line tool and library (`python -m snipai.describe`), with tests. **Not built yet:** wiring it into snip's worker and database, so that new links get descriptions automatically. The design above is how it would fit, and it's a good exercise once you've finished [Part 14](./python-for-ai-engineers.mdx).
:::

<details>
<summary>Estimate the monthly cost of describing every new snip link with Claude Haiku 5.5 if snip gets 50,000 new links a day. Then name three ways to cut it.</summary>

With the chapter's estimate of about $0.000125 per link: 50,000 × 30 days × $0.000125 ≈ **$190 per month**, plus thinking tokens. With Sonnet 5.5 at $0.0025 per link it would be about **$3,750**. (These are estimates: measure real token counts, thinking included, from `usage` on a sample of real pages before trusting them.)

Ways to cut it:

- **Don't describe duplicates.** Many links point at the same popular pages. Cache descriptions by URL (or normalised URL), so each page is described once. This could remove a large share of calls on its own.
- **Send less text.** Cap the page text lower (the first 2,000 characters usually say what a page is about), strip boilerplate better, or use the page's own `<meta name="description">` when it exists and skip the model entirely.
- **Only describe links that get clicked.** Generate descriptions lazily, for links with at least a few clicks, instead of eagerly for every link, most of which may never be opened.
- **Batch APIs**: providers offer discounted asynchronous batch processing (Anthropic's is half price) for work that doesn't need an answer immediately, like this.

And measure quality before and after each change ([chapter 14.10](./evals.mdx)), so the savings don't come from quietly worse descriptions.

</details>

<details>
<summary>Your teammate wants to call the model directly from the browser "to save server load", with the API key in the JavaScript bundle. Explain the problems and propose a design.</summary>

**Problems:**

- **The key is public.** Anything shipped to a browser can be read by anyone (view source, the network tab). Within hours, someone could be spending your budget on their own requests, or abusing the provider with your account.
- **No control.** You can't rate-limit per user, enforce what prompts are sent, log usage, or stop abuse, because requests don't pass through you.
- **No SSRF protection or caching**, and the model's output reaches users without any of your checks.

**Design:** the browser calls **your API**, authenticated as the user. Your server checks the user's permissions and rate limit ([chapter 8.4](../distributed/rate-limiting-and-resilience.mdx)), then queues or makes the model call with a key that only the server holds (from a secret manager, [chapter 7.6](../security/secrets-management.mdx)), validates the output, caches it, logs tokens and cost, and returns the result. "Server load" is small: the server mostly waits on the network, and a model call's real cost is the provider's, not your CPU's.

</details>
