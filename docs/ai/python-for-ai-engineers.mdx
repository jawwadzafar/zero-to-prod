# 14.1 Python for AI engineers

Open any model provider's documentation, any AI tutorial, any research paper's code, and you'll find the same language: **Python**. Every provider's official library, the numerical tools (NumPy), the machine learning frameworks (PyTorch), and the notebooks researchers share are Python first. So AI engineers read and write Python every day, even on teams whose services are written in Go, Java or TypeScript. This chapter gives you enough Python, and enough of the tools around it, to build real AI features without the classic "works on my machine" mess.

It assumes you've written a little code in some language: variables, functions, loops. If you worked through [Part 4](../go/why-go-first-program.mdx), you'll see Go side by side with Python, because comparing two languages is the fastest way to learn the second one. If you haven't, skip the Go column; the Python stands on its own.

## What you'll learn

- How Python runs your file **line by line**, and the **REPL** for trying things instantly.
- Python's spelling of familiar ideas: indentation for blocks, **exceptions** for errors, **context managers** for cleanup.
- **Type hints** checked by **mypy**, and **pydantic** for validating data you don't control.
- **Virtual environments**, `pyproject.toml`, lock files, and **uv**: a separate, reproducible toolbox per project.
- Testing with **pytest** (including fake HTTP servers), and linting and formatting with **ruff**.

## Python runs your file, line by line

:::note[Everyday anchor]
A compiled language is like a translated book: the whole thing is translated before anyone reads it, and translation errors are caught up front. Python is like a live interpreter at a conference: they translate each sentence as it's spoken. You can start immediately and change your mind mid-speech, but a mistake in sentence 40 isn't noticed until sentence 40 is reached.
:::

Go is **compiled**: `go build` turns your whole program into a machine-code binary first, and refuses if anything doesn't type-check. Python is **interpreted**: the `python` program (the **interpreter**) reads your `.py` file and executes it statement by statement. There's no separate build step, which makes Python fast to experiment with. The price is that many mistakes are found only when the faulty line actually runs.

The interpreter also has an interactive mode, the **REPL** (read–evaluate–print loop). Type an expression, see the result immediately:

```text
$ python3
>>> 7 * 6
42
>>> "hello".upper()
'HELLO'
>>> len("https://python.org")
18
>>> exit()
```

The REPL is where Python shines for AI work: load some data, try a prompt, inspect the result, try again, without writing a program first.

:::info[In the real world]
Researchers and data scientists often work in **Jupyter notebooks**: documents that mix code cells, their output (tables, charts) and notes, run in a browser. They're wonderful for exploring. They're also easy to get into a confusing state, because cells can run in any order and the notebook remembers everything from earlier runs. The usual practice: explore in a notebook if you like, then move anything you want to keep into ordinary `.py` files with tests. This handbook uses plain files throughout.
:::

## The same ideas, different spelling

Here's a small, complete Python file: the username rules for a sign-up form. A username is 3 to 20 lowercase letters, digits or underscores, and a few names are taken.

```python title="usernames.py"
"""Username rules for a sign-up form."""

import re

USERNAME = re.compile(r"^[a-z0-9_]{3,20}$")
TAKEN = {"admin", "root", "support"}


class InvalidUsernameError(ValueError):
    """The username breaks the rules."""


def validate_username(name: str) -> None:
    """Raise InvalidUsernameError unless name is an acceptable username."""
    if not USERNAME.match(name) or name.lower() in TAKEN:
        raise InvalidUsernameError(f"invalid username: {name!r}")


def is_valid_username(name: str) -> bool:
    try:
        validate_username(name)
    except InvalidUsernameError:  # only the failure we expect
        return False
    return True
```

Reading it top to bottom, here is what each piece of syntax means, and how Go spells the same idea:

| Idea | Python | Go |
|---|---|---|
| Blocks | **Indentation** (4 spaces). It's part of the syntax, not style | `{ }` |
| Variables | `x = 1`; the variable can later hold anything | `x := 1`, fixed type |
| Naming | `validate_username` (snake_case); a leading `_` means "private, by convention" | `ValidateUsername` (capital = exported) |
| No value | `None` | `nil` |
| Lists, maps, sets | `["a", "b"]` (list), `{"a": 1}` (dict), `{"a", "b"}` (set) | `[]string{...}`, `map[string]int{...}` |
| Records | `class Link:`, usually a `@dataclass` or pydantic `BaseModel` | `type Link struct {...}` |
| Errors | **exceptions**: `raise`, and `try` / `except` | returned values: `if err != nil` |
| Cleanup | `with open(...) as f:` (a **context manager**) | `defer f.Close()` |
| String formatting | f-strings: `f"invalid username: {name!r}"` (`!r` adds quotes) | `fmt.Sprintf("%q", name)` |
| Docs | a **docstring**: a string as the first line of the function | a comment above the function |

Two of these deserve a closer look, because they change how you structure code.

**Exceptions instead of returned errors.** In Go, a function that can fail returns an `error`, and the caller checks it on the next line. In Python, a failing function **raises an exception**, which travels up the call stack until some caller **catches** it with `try`/`except`, or the program crashes with a **traceback** (Python's stack trace, [chapter 13.6](../observability/debugging-playbook.mdx)). Less typing, but you can't see from a function's signature whether it can fail. So read docstrings, and catch *specific* exceptions, as `is_valid_username` does, rather than everything: a bare `except:` would also swallow a typo in your own code.

**Context managers instead of defer.** `with` guarantees cleanup when the block ends, even if an exception is raised inside it. You'll use it for files, network clients and database connections:

```python
with open("notes.txt") as f:      # opens the file
    first = f.readline()
# here the file is closed, whatever happened inside the block
```

:::warning[What can go wrong]
The most famous Python trap: **default arguments are created once**, when the function is defined, not each time it's called. So a mutable default (a list or dict) is *shared between calls*:

```python
def add_tag(tag, tags=[]):
    tags.append(tag)
    return tags

add_tag("go")       # ['go']
add_tag("python")   # ['go', 'python']  ← the list from the first call!
```

Use `tags: list[str] | None = None`, and create the list inside the function. Linters catch this for you (ruff's `B006` rule, below).
:::

## Type hints: a compiler's safety net, if you ask for it

Python is **dynamically typed**: a variable's type is whatever it currently holds, and nothing checks types before the program runs. Since Python 3.5 you can add **type hints**: `name: str`, `-> bool`, `list[Link]`. On their own, they do **nothing** at runtime. They're documentation that a separate tool, a **type checker**, can verify. The standard one is **mypy**.

Here's a file with two type mistakes:

```python title="typo.py"
from usernames import is_valid_username

label: str = is_valid_username("ada")
is_valid_username(42)
```

Python itself runs line 3 without complaint (`label` quietly becomes `True`) and only crashes on line 4, deep inside the function:

```text
TypeError: expected string or bytes-like object, got 'int'
```

mypy finds both before anything runs:

```text
$ uv run mypy --strict typo.py
typo.py:3: error: Incompatible types in assignment (expression has type "bool", variable has type "str")  [assignment]
typo.py:4: error: Argument 1 to "is_valid_username" has incompatible type "int"; expected "str"  [arg-type]
Found 2 errors in 1 file (checked 1 source file)
```

That's a compiler's job, done by a separate tool that you run yourself, and that CI runs on every push. For code that will live longer than an afternoon, write the hints and run the checker. Your editor uses them for autocomplete too.

### pydantic: checking data you don't control

Type hints check *your code*. They can't check *data arriving from outside* (an API response, a file, a model's output), because that data only exists at runtime. For that, AI engineers lean heavily on **pydantic**: you describe the shape of the data as a class, and pydantic **validates** and **converts** incoming data to match, or raises a clear error.

Here's a model for three fields of a public GitHub repository, as GitHub's API returns it:

```python
from datetime import datetime

from pydantic import BaseModel


class Repo(BaseModel):
    full_name: str
    stargazers_count: int
    created_at: datetime
```

Give it bad data and you get every problem at once, with the field names:

```text
>>> Repo.model_validate({"full_name": "octo/demo", "stargazers_count": "lots", "created_at": "yesterday"})
pydantic_core._pydantic_core.ValidationError: 2 validation errors for Repo
stargazers_count
  Input should be a valid integer, unable to parse string as an integer [type=int_parsing, input_value='lots', input_type=str]
created_at
  Input should be a valid datetime or date, input is too short [type=datetime_from_date_parsing, input_value='yesterday', input_type=str]
```

Good data comes out as real Python types: `created_at` becomes a `datetime` you can do date arithmetic on, not a string. Fields you didn't declare (GitHub sends about eighty) are ignored. This will matter a lot in [chapter 14.6](./structured-output-and-tools.mdx), where the data you're validating is a language model's output, which is *often* not quite what you asked for.

## Environments: a separate toolbox for every project

:::note[Everyday anchor]
Imagine every carpenter in a workshop sharing one toolbox. One of them swaps the drill bits for a different size, and everyone else's jobs break. The fix: each job gets its own toolbox, with a list of exactly what's in it, so anyone can rebuild it identically.
:::

Python's traditional default is the shared toolbox: `pip install` puts packages into one place for the whole Python installation, so project A's upgrade can break project B, and "works on my machine" is the norm. (Go avoids this: each project's `go.mod` and `go.sum` pin exactly which versions *that project* uses.) The Python fix has three parts:

- A **virtual environment** (a `.venv` folder inside the project): a private copy of the Python setup with its own installed packages. Each project gets its own toolbox.
- **`pyproject.toml`**: the project's description and the dependencies it needs, with minimum versions (like `go.mod`, or `package.json` in JavaScript).
- A **lock file** (`uv.lock`): the *exact* version of every package, including dependencies of dependencies, with hashes (like `go.sum` or `package-lock.json`). Committed to Git, so everyone and CI install the identical set.

The tool that manages all three is **uv**. It's newer than the classic `pip` + `venv` combination, much faster, and it can install Python itself. Starting a project looks like this:

```bash
uv init demo && cd demo          # creates pyproject.toml, main.py, .python-version
uv add httpx pydantic            # runtime dependencies: pyproject.toml + uv.lock + .venv
uv add --dev pytest ruff mypy    # tools only developers and CI need
```

After those commands, `pyproject.toml` lists what you asked for:

```toml
[project]
name = "demo"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "httpx>=0.28.1",
    "pydantic>=2.14.1",
]

[dependency-groups]
dev = ["mypy>=2.4.1", "pytest>=9.2.0", "ruff>=0.17.3"]
```

The day-to-day commands:

| You want to | Run | Go equivalent |
|---|---|---|
| Create `.venv` and install exactly what `uv.lock` says | `uv sync` | `go mod download` |
| Add a dependency (updates `pyproject.toml` and `uv.lock`) | `uv add httpx` | `go get` |
| Run something inside the project's environment | `uv run pytest`, `uv run python` | `go run`, `go test` |
| Fail if the lock file doesn't match `pyproject.toml` (CI) | `uv sync --locked` | `go mod tidy -diff` |

You don't need to "activate" the environment: `uv run` always uses the project's `.venv`.

:::warning[What can go wrong]
- **`pip install` with the system Python**, often with `sudo`, mixes your packages into the operating system's own Python, which system tools depend on. Recent Linux distributions refuse (`externally-managed-environment`) for exactly this reason. Always work inside a project environment.
- **Committing `.venv/`**. It's big, and specific to your machine. Commit `pyproject.toml` and `uv.lock`, and put `.venv/` in `.gitignore`.
- **Forgetting the lock file.** Without it, `uv sync` next month may install newer versions, and your working code breaks without a single change of your own.
:::

## Calling an API: httpx plus pydantic

Most AI features start by fetching something over HTTP: a model's answer, a web page, your own service's data. **httpx** is a modern HTTP library for Python. Combined with pydantic, a few lines give you a typed, validated result. This program prints a GitHub repository's star count:

```python title="repo.py"
"""Fetch a GitHub repository's public details, validated."""

import sys
from datetime import datetime

import httpx
from pydantic import BaseModel


class Repo(BaseModel):
    full_name: str
    stargazers_count: int
    created_at: datetime


def fetch_repo(name: str, *, client: httpx.Client) -> Repo:
    res = client.get(f"/repos/{name}")
    res.raise_for_status()  # a 4xx or 5xx answer becomes an exception
    return Repo.model_validate(res.json())


if __name__ == "__main__":
    with httpx.Client(base_url="https://api.github.com", timeout=5.0) as client:
        repo = fetch_repo(sys.argv[1], client=client)
    print(
        f"{repo.full_name}: {repo.stargazers_count} stars, created {repo.created_at:%Y-%m-%d}"
    )
```

```text
$ uv run python repo.py astral-sh/uv
astral-sh/uv: 91339 stars, created 2023-10-02
$ uv run python repo.py astral-sh/nope
httpx.HTTPStatusError: Client error '404 Not Found' for url 'https://api.github.com/repos/astral-sh/nope'
```

Habits worth copying, all visible in those lines:

- **`*` in the parameter list** means everything after it must be passed **by name**: `fetch_repo("x/y", client=c)`, never `fetch_repo("x/y", c)`. Call sites stay readable.
- **The client is passed in**, not created inside `fetch_repo`. That one choice is what makes the function testable without the internet (next section).
- **A timeout, always.** A program waiting on a network call with no timeout can hang forever ([chapter 8.1](../distributed/distributed-survival-kit.mdx) explains why networks do that).
- **`with` closes the connection pool** when the block ends.
- **`if __name__ == "__main__":`** runs only when you execute the file directly, not when a test imports it.

## Tests and tidiness: pytest and ruff

**pytest** is Python's standard test runner. Tests are plain functions whose names start with `test_`, using the ordinary `assert` statement. One feature you'll use constantly is **parametrize**: one test, many inputs. It's the Python version of Go's table-driven tests ([chapter 4.4](../go/testing.mdx)):

```python title="test_demo.py (part 1)"
import pytest

from usernames import is_valid_username


@pytest.mark.parametrize(
    ("name", "ok"),
    [
        ("ada", True),
        ("grace_hopper", True),
        ("ab", False),  # too short
        ("Ada", False),  # capitals not allowed
        ("admin", False),  # taken
    ],
)
def test_is_valid_username(name: str, ok: bool) -> None:
    assert is_valid_username(name) is ok
```

To test `fetch_repo` **without the internet**, hand httpx a **mock transport**: a plain function that receives each request and returns a made-up response. A fake server, in five lines:

```python title="test_demo.py (part 2)"
import httpx

from repo import fetch_repo


def fake_github(request: httpx.Request) -> httpx.Response:
    if request.url.path == "/repos/octo/demo":
        return httpx.Response(
            200,
            json={
                "full_name": "octo/demo",
                "stargazers_count": 42,
                "created_at": "2024-03-01T09:30:00Z",
            },
        )
    return httpx.Response(404, json={"message": "Not Found"})


def fake_client() -> httpx.Client:
    return httpx.Client(
        base_url="https://api.github.com", transport=httpx.MockTransport(fake_github)
    )


def test_fetch_repo_turns_json_into_a_repo() -> None:
    repo = fetch_repo("octo/demo", client=fake_client())
    assert repo.stargazers_count == 42
    assert repo.created_at.year == 2024  # a real datetime, not a string


def test_missing_repo_raises() -> None:
    with pytest.raises(httpx.HTTPStatusError):
        fetch_repo("octo/nothing", client=fake_client())
```

The tests are fast, free, and pass on a plane. You'll use the same trick for model APIs in [chapter 14.4](./calling-models-from-code.mdx): a fake model server, so tests never spend money.

**ruff** is the linter and formatter, in one very fast tool: `ruff format` rewrites your code into one standard layout (Go's `gofmt`), and `ruff check` finds likely bugs (unused imports, the mutable-default trap, outdated syntax). Together with mypy and pytest, that's the full check a healthy Python project runs locally and in CI:

```bash
uv run ruff check . && uv run ruff format --check . && uv run mypy --strict . && uv run pytest
```

## Apply it to snip

Every idea above is used in **snipai** (`ai/` in this repository), the Python project that adds AI features to snip, the URL shortener you build through this handbook. It's a uv project like `demo`, with `pyproject.toml`, a committed `uv.lock`, and the same four checks in CI (`uv sync --locked` first, so a stale lock file fails the build).

**The same rule in two languages.** snip's Go code checks custom slugs (the `go` in `snip.example/go`) in `snip/internal/links/link.go`; `ai/src/snipai/slugs.py` is a line-for-line Python twin, so you can compare the languages on real code:

```go
var slugPattern = regexp.MustCompile(`^[A-Za-z0-9_-]{3,32}$`)

var reserved = map[string]bool{"api": true, "app": true, "healthz": true, "readyz": true, "metrics": true}

func ValidateSlug(s string) error {
	if !slugPattern.MatchString(s) || reserved[strings.ToLower(s)] {
		return ErrInvalidSlug
	}
	return nil
}
```

```python
SLUG_PATTERN = re.compile(r"^[A-Za-z0-9_-]{3,32}$")

RESERVED = {"api", "app", "healthz", "readyz", "metrics"}

def validate_slug(slug: str) -> None:
    """Raise InvalidSlugError unless slug is an acceptable custom slug."""
    if not SLUG_PATTERN.match(slug) or slug.lower() in RESERVED:
        raise InvalidSlugError(f"invalid slug: {slug!r}")
```

Its test, `ai/tests/test_slugs.py`, uses `parametrize` with the same cases as snip's Go table test.

**A typed client for snip's API.** `ai/src/snipai/client.py` is `repo.py` grown up: a pydantic `Link` matching the JSON snip returns, and a `SnipClient` wrapping httpx for the endpoints you built in [Part 5](../apis/first-http-server.mdx) (`POST /api/links` to create, `GET /api/links` to list, `DELETE /api/links/{slug}`):

```python
class Link(BaseModel):
    """One short link, exactly as snip's API returns it."""

    slug: str
    url: str
    clicks: int
    created_at: datetime
    short_url: str


class SnipClient:
    def __init__(self, base_url: str, api_key: str, *, timeout: float = 5.0,
                 transport: httpx.BaseTransport | None = None) -> None:
        self._http = httpx.Client(
            base_url=base_url,
            headers={"Authorization": f"Bearer {api_key}"},
            timeout=timeout,  # never wait forever (chapter 8.1)
            transport=transport,
        )

    def create(self, url: str, slug: str | None = None) -> Link:
        body: dict[str, str] = {"url": url}
        if slug:
            body["slug"] = slug
        return Link.model_validate(self._request("POST", "/api/links", json=body))

    def _request(self, method: str, path: str, **kwargs: Any) -> Any:
        res = self._http.request(method, path, **kwargs)
        if res.status_code == 204:
            return None
        if res.is_error:
            try:
                err = res.json()["error"]
                raise SnipError(res.status_code, err["code"], err["message"])
            except (ValueError, KeyError, TypeError):
                # Not snip's error format (a proxy's HTML error page, say).
                raise SnipError(res.status_code, "http_error", res.text[:200]) from None
        return res.json()
```

(Trimmed: the real file adds `get`, `list`, `delete`, and `__enter__`/`__exit__` so it works with `with`.) Three things it does beyond `repo.py`:

- **One place turns HTTP errors into exceptions** (`_request`), carrying snip's own error `code` (snip answers errors as `{"error": {"code": "slug_taken", ...}}`, [chapter 5.3](../apis/validation-errors-status-codes.mdx)), so callers can write `except SnipError as e: if e.code == "slug_taken": ...`.
- **It never trusts the error body's shape.** If something between you and snip (nginx, a load balancer) answers with an HTML page, `res.json()` fails. The code catches that and still raises a useful `SnipError`.
- **`transport` is a parameter**, so `ai/tests/test_client.py` tests it with a mock transport, exactly like `fake_github`. A separate test, `ai/tests/test_live.py`, runs the same round trip against a **real** snip when you set `SNIP_URL` and `SNIP_API_KEY`, and skips itself otherwise.

Using it feels like this, against a running snip:

```text
>>> from snipai.client import SnipClient, SnipError
>>> snip = SnipClient("http://localhost:8080", "snip_...")
>>> link = snip.create("https://www.python.org", slug="python")
>>> link
Link(slug='python', url='https://www.python.org', clicks=0, created_at=datetime.datetime(2026, 9, 24, 23, 42, 26, 320843, tzinfo=TzInfo(0)), short_url='http://localhost:8080/python')
>>> snip.create("https://example.com", slug="api")
snipai.client.SnipError: 400 invalid_slug: slug must be 3-32 letters, digits, '-' or '_', and not a reserved word
```

You'll extend snipai in every chapter of Part 14.

## Lab

Free, on your own computer. Steps 1–4 need nothing but uv and an internet connection; step 5 uses this repository.

1. **Install uv** (it can install Python for you too). On macOS or Linux (and WSL on Windows):
   ```bash
   curl -LsSf https://astral.sh/uv/install.sh | sh   # downloads and runs uv's installer
   uv --version                                      # in a new terminal: prints the version
   ```
   (Or `brew install uv` on macOS.) Piping a script from the internet into `sh` runs it with your permissions. It's a common way to install developer tools, but it's worth opening the URL in your browser first to see what it does.

2. **Make a project and run the API program.**
   ```bash
   uv init demo && cd demo            # a new project
   uv add httpx pydantic              # creates .venv and uv.lock
   uv add --dev pytest ruff mypy
   rm main.py                         # uv's hello-world; we don't need it
   ```
   Create `repo.py` from "Calling an API" above, then run `uv run python repo.py astral-sh/uv` and `uv run python repo.py astral-sh/nope`. **What to notice:** the second one ends in an `HTTPStatusError` traceback. Read it bottom-up: the last line says what went wrong, the lines above say where.

3. **Let mypy catch what Python misses.** Create `usernames.py` and `typo.py` from the chapter. Run `uv run python typo.py` (it crashes on line 4, and only on line 4), then `uv run mypy --strict typo.py` (both mistakes, before running anything). Delete `typo.py` afterwards.

4. **Test without the internet, then break a test on purpose.** Create `test_demo.py` from the two parts above (imports at the top), then:
   ```bash
   uv run pytest -v                                         # 7 tests, all pass
   uv run ruff check . && uv run ruff format --check . && uv run mypy --strict .
   ```
   Now change `("ab", False)` to `("ab", True)` and run `uv run pytest` again. Read the failure: pytest shows the exact input and what `assert` compared. Put it back.

5. **Apply it to snip.** Run snipai's checks, then the live test against a real snip:
   ```bash
   cd ~/code/zero-to-prod/ai
   uv sync                                                  # exactly what uv.lock lists
   uv run ruff check . && uv run ruff format --check . && uv run mypy && uv run pytest
   ```
   One test is `skipped`: the live test, waiting for a real snip. In a second terminal, start snip in memory mode ([chapter 5.1](../apis/first-http-server.mdx)); it prints a development API key:
   ```bash
   cd ~/code/zero-to-prod/snip && go run ./cmd/snip serve
   ```
   Back in the `ai` terminal: `SNIP_URL=http://localhost:8080 SNIP_API_KEY=snip_... uv run pytest -v` (paste the key). Now nothing is skipped. Then try the client from `uv run python`: create a link, read `link.created_at.year`, list slugs with `[l.slug for l in snip.list()]`, and catch the error from `snip.create("https://example.com", slug="api")` with `try: ... except SnipError as e: print(e.code)`.

links, err := store.List(ctx, ownerID, 50)
if err != nil {
	return nil, err

```python
links = store.list(owner_id, limit=50)   # raises if it fails; no err to check
slugs = [link.slug for link in links if link.clicks > 0]
```

- **No error check**: in Python, a failure raises an exception, which carries on up to whoever can handle it. If *this* function should handle it, wrap the call in `try`/`except` with the specific exception.
- **The loop becomes a list comprehension**: `[expression for item in iterable if condition]`. It's idiomatic for "build a list by filtering and transforming". For anything more complicated than one condition and one expression, a plain `for` loop is clearer.
- **Naming**: `owner_id`, `limit=50` as a keyword argument, so the call says what 50 means.
- **No `ctx`**: Python has no standard equivalent of Go's `context` for cancellation in ordinary code. Timeouts are usually set on the client (like `httpx.Client(timeout=5.0)`). Async code has its own cancellation.

<details>
<summary>A teammate's script works on their laptop but fails in CI with "ModuleNotFoundError: No module named 'pydantic'". What are the likely causes, and how does a uv project avoid them?</summary>

The code ran in a Python environment where `pydantic` wasn't installed. Likely causes:

- They installed pydantic **globally** on their laptop (`pip install pydantic`) and never added it to the project's dependencies, so CI's fresh environment doesn't have it.
- CI ran `python script.py` with the system Python instead of the project's environment.
- The dependency was added to `pyproject.toml` but the **lock file wasn't updated or committed**, so CI installed from an old lock.

A uv project avoids all three: dependencies are only added with `uv add` (which updates both `pyproject.toml` and `uv.lock`), everything runs through `uv run` (always the project's `.venv`), and CI runs `uv sync --locked`, which **fails** if the lock file doesn't match `pyproject.toml` instead of quietly installing something different. snipai's CI does exactly this.

</details>
